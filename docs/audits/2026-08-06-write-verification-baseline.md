# DB 쓰기 확인 감사 — 기준선 (2026-08-06)

⚠️ 이 문서는 **기준선**이다 — 다음 감사에서 몇 곳으로 줄었는지 재려면 이 숫자가 필요하다.
같은 방법(패턴 검색 + 사람 정독)으로 재측정해 비교할 것.

## 왜 문제인가

supabase-js(PostgREST)는 쓰기가 실패해도 **throw 하지 않고 `{error}` 를 담아 정상 반환**한다.
`await sb.from(…).update(…)` 만 하고 결과를 안 보면 바깥 try/catch 에 절대 걸리지 않고,
성공 경로(토스트 포함)가 그대로 진행된다. 또한 **0행 매치도 error null** 이다(규칙 20) —
행이 바뀌어야 하는 쓰기는 `.select()` 행 수까지 확인해야 한다.

## 측정 결과 (2026-08-06)

- 전체 DB 쓰기 지점: **145곳**
- 결과(error·행 수) 무확인: **패턴 검색 26곳 + 사람이 읽어 2곳 추가 = 28곳 이상**
  - ⚠️ 검색이 놓치는 형태가 있다 — 추가 2곳(fulfillment 의 `removeItem` delete ·
    팔렛 노트 `height/weight_note` fire-and-forget update)은 패턴에 안 걸렸고 정독으로 찾았다.
    **이 숫자는 하한이다. 숫자를 맞추려고 발견을 빼지 않는다.**

### fulfillment 분할 이동의 순서 결정 (2026-08-06 사용자 결정 — 기각 이력 포함)

부분 이동은 ①원본 수량 감소 → ②새 위치 추가 순서다. "새 위치 먼저(중복 잔여) → 옛 위치 나중"
역전안은 **기각**됐다: 이 화면의 pool 은 rem>0 만 표시하므로 **증식(합계+q)은 숨고,
유실(합계−q)은 pool 로 되돌아와 보인다.** 일반론("중복은 보이고 유실은 안 보인다")이
이 시스템에서는 반대다 — 잔여가 보이는 쪽(현재 순서)을 유지한다.
②실패 시 메시지는 유실 방향에 맞춰 "그 수량은 어느 팔렛에도 배정되지 않았다 —
pool 에서 다시 끌어다 놓아라" 로 안내한다.

## 2026-08-06 후속 ① — 7단계(라인 묶음 upsert) 실패 실측 · 폐기

⚠️ **이 스키마에서 라인 묶음 upsert 는 구조적으로 불가능하다. 같은 접근을 다시 설계하지 말 것.**

```
POST /wms_pack_task_lines?on_conflict=id&columns="id","verified_base"&select=id
→ 400 {"code":"23502","message":"null value in column \"pack_task_id\" ... not-null constraint"}
```

- 원인: Postgres 의 `INSERT ... ON CONFLICT` 는 **NOT NULL 검사를 충돌 판정보다 먼저** 한다.
  행이 이미 있어도 마찬가지 — NOT NULL 컬럼(pack_task_id·order_line_id·expected_base)이
  페이로드에 없으면 **항상** 23502 (2026-08-06 프로덕션 콘솔 재현).
- 근거 등급 교훈: 설계 조사의 "ON CONFLICT DO UPDATE 는 페이로드 키로만 SET 조립" 은
  맞았지만 **검사 시점을 놓쳤고**, "행 부재 시 INSERT 분기가 NOT NULL 로 실패" 를
  fail-closed 안전장치로 썼는데 실제로는 **항상 발동하는 차단벽**이었다 —
  "설명" 등급을 실측 없이 배포한 대가(기록 규칙 「근거의 출처」 위반 사례).
- 커밋 c20c5c7·2cdb973 은 revert 됨. id GENERATED BY DEFAULT 전환(20260806130000)은
  DB 에 남았다가 `20260806140000` 이 ALWAYS 로 복원(왕복 사유는 그 파일 주석).
