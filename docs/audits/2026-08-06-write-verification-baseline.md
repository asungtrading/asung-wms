# DB 쓰기 확인 감사 — 기준선 (2026-08-06)

⚠️ 이 문서는 **기준선**이다 — 다음 감사에서 몇 곳으로 줄었는지 재려면 이 숫자가 필요하다.
같은 방법(패턴 검색 + 사람 정독)으로 재측정해 비교할 것.

## 왜 문제인가

supabase-js(PostgREST)는 쓰기가 실패해도 **throw 하지 않고 `{error}` 를 담아 정상 반환**한다.
`await sb.from(…).update(…)` 만 하고 결과를 안 보면 바깥 try/catch 에 절대 걸리지 않고,
성공 경로(토스트 포함)가 그대로 진행된다. 또한 **0행 매치도 error null** 이다(규칙 20) —
행이 바뀌어야 하는 쓰기는 `.select()` 행 수까지 확인해야 한다.

## 측정 결과 (2026-08-06)

- 전체 DB 쓰기 지점: **145곳**
- 결과(error·행 수) 무확인: **패턴 검색 26곳 + 사람이 읽어 2곳 추가 = 28곳 이상**
  - ⚠️ 검색이 놓치는 형태가 있다 — 추가 2곳(fulfillment 의 `removeItem` delete ·
    팔렛 노트 `height/weight_note` fire-and-forget update)은 패턴에 안 걸렸고 정독으로 찾았다.
    **이 숫자는 하한이다. 숫자를 맞추려고 발견을 빼지 않는다.**

### fulfillment 분할 이동의 순서 결정 (2026-08-06 사용자 결정 — 기각 이력 포함)

부분 이동은 ①원본 수량 감소 → ②새 위치 추가 순서다. "새 위치 먼저(중복 잔여) → 옛 위치 나중"
역전안은 **기각**됐다: 이 화면의 pool 은 rem>0 만 표시하므로 **증식(합계+q)은 숨고,
유실(합계−q)은 pool 로 되돌아와 보인다.** 일반론("중복은 보이고 유실은 안 보인다")이
이 시스템에서는 반대다 — 잔여가 보이는 쪽(현재 순서)을 유지한다.
②실패 시 메시지는 유실 방향에 맞춰 "그 수량은 어느 팔렛에도 배정되지 않았다 —
pool 에서 다시 끌어다 놓아라" 로 안내한다.

## 2026-08-06 후속 — 픽·팩 완료 라인 묶음 upsert 커밋 (⚠️ 현장 미검증)

- **packer 완료 경로의 잔존 무확인 5곳 해소**: `saveLine`(스캔당 1행 — 확인만 추가, 규칙 20) ·
  discrepancy insert 3곳(`mustRows` 패턴 로컬 복사 — error + `.select()` 행 수) ·
  `checkOrderReady`(⚠️ 0행은 멱등 가드의 정상 no-op — error 만 판정).
  → **잔존 12 → 7** (다음 감사에서 같은 방법으로 재측정해 대조할 것).
- **완료 라인 최종 저장 루프(packer·picker)는 순차 PATCH → 단일 upsert 로 대체** —
  60줄=60요청≈9.5초·중단 시 반쪽 상태 문제의 본체. 한 요청 = 단일 문 = 전부 아니면 전무.
  전제 마이그레이션 `20260806130000_pick_pack_line_id_by_default.sql`(GENERATED ALWAYS 는
  PostgREST upsert 를 428C9 로 거부 — 2026-08-06 실측). 상세는 SKILL 규칙 9.
- 실패 시 서버 재조회(`resyncAfterFail`)로 "이미 저장됨/미저장" 구분 안내 — fulfillment 의
  "실패 시 refresh() 재조회" 와 같은 원칙, 단 로컬 수량(실물 카운트)은 버리지 않는다.
- **(커밋 2 — Hold) 정독 추가 발견 +2, 해소 +3**: **packer Hold 라인 루프 · picker Hold 라인
  루프**가 결과 무확인이었다(원래 표의 28+ 에 포함됐는지 재확인 안 함 — 하한 기록 원칙,
  발견을 숫자에 맞춰 빼지 않는다). 둘 다 완료 경로와 같은 묶음 upsert 로 해소.
  추가로 **packer Hold 의 태스크 플립**(pack_tasks → pending)도 error 무확인이었다
  (picker 는 확인하고 있었다 — 비대칭) → error 확인 추가.
