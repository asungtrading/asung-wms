### 1-1. `putaway:DRAFT` = 지연 확정 (①)

Convert 직후 `DRAFT` 였던 PA 블록이 다음 날 아침 `AUTHORISED` 51줄로 바뀌었다.
**화면이 먼저 바뀌고 API 가 따라온다.** 원장은 `AUTHORISED` 만 기표하므로 그 구간의 문서는
**다음 회차에 기표된다 — 유실이 아니라 지연**이다.
⇒ 정본 4부 「신규 미확정」의 해당 항목 닫힘 · 스킬 함정 표에 "PA 는 DRAFT 로 생성 → 승인" 기재.

⚠️ 오늘 아침 **SR 블록이 50줄로 새로 생겼다**(CardID 전부 새 값 · `loc=null`). PA 축을 읽는
현재 구현은 이걸 무시하므로 영향 없다 — **축 선택이 옳았다는 반대 방향의 증거**이기도 하다.

## 2. 미달·초과 처리의 실무 흐름 (③) — 이번 세션 최대 수확

⭐ **정본은 `ledger-design.md` 1부 「미달·초과 입고의 실무 흐름」** — 여기는 관측 사실만.

`ST-01220` (`Reference: Initial Warehousing - Parfums de Coeur, Ltd. (PO-01117)`):

```
CAN01620  201 → 177   (−24)   ← 미달분 되돌림
CAN01547  503 → 527   (+24)   ← 초과분 반영
```

- PA 라인 `CAN01620` 은 **168 → 192**(인보이스 수량)로 채워졌다 — **PO 를 닫기 위한 형식**이지
  재고를 늘리려는 게 아니다. 그래서 차액을 adjustment 로 되돌린다.
- **한 입고가 두 소스에 걸친 사건**을 만든다: `po_in`(발주) + `adjustment`(조정).
- Adjustment 는 **절대값**이라 앞선 오차를 흡수한다 → **창고 총량은 자동으로 맞는다.**
- ⚠️ **bin 단위는 어긋난 채 남는다** — 조정 bin(`E030501`)과 입고 bin(PA `3d3c6295`)이 다르다.
  자리 단위 원장으로 올릴 때 드러난다.

### 2-1. ⚠️ WMS discrepancy 큐는 최종 진실이 아니다

`CAN01547` — WMS `apply_note` 는 초과 **16** 을 클램프했다고 기록했는데, 매니저 실사는 **24** 였고
`ST-01220` 도 **+24** 로 조정됐다. 작업자 보고와 매니저 실사가 다를 수 있고 **Cin7 조정은 매니저
실사 기준**이다.
⇒ 대조에서 「WMS 수량 ≠ 원장 수량」은 **오류가 아니라 구조적 차이**로 분류한다(정본 3부 2단계).
📌 최종 재고의 기준은 **매니저 실사가 반영된 Cin7**, 원장은 그것을 읽으므로 원장이 맞다.

### 2-2. `ON CONFLICT DO NOTHING` — 하루 만에 실례가 나왔다

어제 「실무 빈도 확인 대기」로 열어둔 시나리오 ①(수량 정정)이 **정규 절차로 확인**됐다:
PA `CAN01620` 168→192 · **`CardID`·bin·문서번호 전부 동일, 수량만 다르다.** `DO NOTHING` 이면
192 가 조용히 버려진다.

⚠️ **다만 긴급도는 낮아진다** — adjustment 절대값이 총량을 확정하므로 168 이 남아도 잔고는 맞는다.
총량 ✅ / bin 단위 ❌ / 구간 오차(PO 채움~adjustment 사이) ❌.
⇒ **⑤ 전에는 「키는 같은데 값이 다른 행」 감지·경고만으로 충분**하고, 역분개는 자리 단위 원장 때로
미룬다(정본 4부 3번에 반영).

## 3. ⚠️ cron/EF 건강 판정법 (②) — 오늘 발견

정본은 `asung-wms` 스킬 규칙 12(⚠️ **`asung-ops` 로 옮길 것 — 별건**). 요지:

- `cron.job_run_details.status='succeeded'` = **요청 발송 성공**일 뿐. **EF 가 401 로 죽어도 succeeded.**
- `net._http_response` 는 **매 실행마다 5초 타임아웃**을 남긴다(연결·SSL 은 수십 ms 정상 — 응답만
  못 기다림). EF 는 그 뒤에도 계속 돌아 자기 일을 마친다.
  ⚠️ **이 로그를 보고 "폴링이 죽었다"고 판단하면 멀쩡한 것을 고치게 된다.**
- ⇒ **판정은 결과물로만.** 폴링 = `select max(checked_at) from wms_polled_sales`
  ([실측] 09:09 조회 시 9분 전 갱신 = 정상, 주기 5분).
- ⬜ `product-images`(cron 4·5) 결과물 확인 방법 **미정 — 별건**(`wms_image_sync_runs` 가 후보).

## 4. 오늘 추가로 나온 것 — PO-01117 이 리시빙 목록에 떴다

**현상**: 「READY TO RECEIVE (CIN7)」에 PO-01117 이 `Start` 버튼과 함께 노출
(receipt id=58 · `status=completed` · `applied_at` 2026-08-18 19:41).

**원인 — 오작동이 아니다**:
- Cin7 이 정확하다 — 인보이스 192/입고 168 이라 **부분 입고**로 열려 있었다.
- `listOpenPOs()` ④번(`StockReceivedStatus==="AUTHORISED"` 완전일치)은 Convert 후 값이
  `PARTIALLY RECEIVED` 라 통과 — **어휘 완전일치의 구조적 한계**.
- ✅ **데이터 안전은 이미 확보돼 있었다** — `startPo()` 의 `applied_at` 가드가 토스트만 띄우고
  return. **이중 입고는 구조적으로 불가능.** 남은 건 작업자 시간 낭비뿐이었다.

**판단·처리**:
- ⊘ **목록에서 제외하는 안은 철회** — 숨기면 "내 PO 가 목록에 없다"는 새 혼란이 생긴다
  (PO-01083·PO-01130 실사고 계열). 한 번 구현했다가 되돌렸다.
- ✅ **`Applied` 배지로 표시**(`591b892`) — 카드는 남기고 버튼 자리에 비활성 배지 + 카드 onclick
  비활성 + sub 줄 `Already applied to Cin7`. `startPo()` 가드는 **두 번째 겹으로 유지**.
- ✅ ④번 필터는 유지하되 **주석을 보조 방어선으로 격하**(`2c36107`) — 어휘 나열 확장 금지 명시.
- ⚠️ **배지는 실사용 미검증** — PO-01117 은 오늘 `listSRS=AUTHORISED` 로 바뀌어 ④번에 걸려
  목록에서 빠졌다. **다음 미달 입고가 첫 검증이다.**

📌 부수 확인: 리시빙 `Delete` 는 **물리 삭제**다(admin.html — `wms_rollback_archive` 보존 후
행 delete · 라인 FK CASCADE · soft-delete 컬럼 없음).
