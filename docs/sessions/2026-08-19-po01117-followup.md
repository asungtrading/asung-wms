## 2. 미달·초과 처리의 실무 흐름 (③) — 이번 세션 최대 수확

⭐ **정본은 `ledger-design.md` 1부 「미달·초과 입고의 실무 흐름」** — 여기는 관측 사실만.

`ST-01220` (`Reference: Initial Warehousing - Parfums de Coeur, Ltd. (PO-01117)`):

```
CAN01620  201 → 177   (−24)   ← 미달분 되돌림
CAN01547  503 → 527   (+24)   ← 초과분 반영
```

- PA 라인 `CAN01620` 은 **168 → 192**(인보이스 수량)로 채워졌다 — **PO 를 닫기 위한 형식**이지
  재고를 늘리려는 게 아니다. 그래서 차액을 adjustment 로 되돌린다.
- **한 입고가 두 소스에 걸친 사건**을 만든다: `po_in`(발주) + `adjustment`(조정).
- Adjustment 는 **절대값**이라 앞선 오차를 흡수한다 → **창고 총량은 자동으로 맞는다.**
- ⚠️ **bin 단위는 어긋난 채 남는다** — 조정 bin(`E030501`)과 입고 bin(PA `3d3c6295`)이 다르다.
  자리 단위 원장으로 올릴 때 드러난다.

### 2-1. ⚠️ WMS discrepancy 큐는 최종 진실이 아니다

`CAN01547` — WMS `apply_note` 는 초과 **16** 을 클램프했다고 기록했는데, 매니저 실사는 **24** 였고
`ST-01220` 도 **+24** 로 조정됐다. 작업자 보고와 매니저 실사가 다를 수 있고 **Cin7 조정은 매니저
실사 기준**이다.
⇒ 대조에서 「WMS 수량 ≠ 원장 수량」은 **오류가 아니라 구조적 차이**로 분류한다(정본 3부 2단계).
📌 최종 재고의 기준은 **매니저 실사가 반영된 Cin7**, 원장은 그것을 읽으므로 원장이 맞다.

### 2-2. `ON CONFLICT DO NOTHING` — 하루 만에 실례가 나왔다

어제 「실무 빈도 확인 대기」로 열어둔 시나리오 ①(수량 정정)이 **정규 절차로 확인**됐다:
PA `CAN01620` 168→192 · **`CardID`·bin·문서번호 전부 동일, 수량만 다르다.** `DO NOTHING` 이면
192 가 조용히 버려진다.

⚠️ **다만 긴급도는 낮아진다** — adjustment 절대값이 총량을 확정하므로 168 이 남아도 잔고는 맞는다.
총량 ✅ / bin 단위 ❌ / 구간 오차(PO 채움~adjustment 사이) ❌.
⇒ **⑤ 전에는 「키는 같은데 값이 다른 행」 감지·경고만으로 충분**하고, 역분개는 자리 단위 원장 때로
미룬다(정본 4부 3번에 반영).
→ ✅ **그 감지 장치를 같은 날 오후에 구현했다 — §6-2**(`inv_conflicts`). 이 절은 그 판단이 선
시점의 기록이다.

**판단·처리**:

- ✅ ④번 필터는 유지하되 **주석을 보조 방어선으로 격하**(`2c36107`) — 어휘 나열 확장 금지 명시.

### 5-1. ☑ 게이트 3번(재등장 전제) 닫힘 — 이번 검증의 최대 수확

어제 「⚠️ 이 전제는 미확인」이라 적어둔 바로 그것이다. PO-01117 이 08-18 저녁 `PA=[DRAFT]` 라
기표 보류(`blocks_skipped: putaway:DRAFT 1`)됐다가, 오늘 아침 `PA=[AUTHORISED]` 승인 후
**같은 창의 `ledger_rows` 가 676 → 727 로 정확히 +51**(PA 라인 수) 늘며 들어왔다.
⇒ **「보류하되 커서는 전진」 설계가 유실을 만들지 않는다**는 실증. 정본 4부 체크리스트 ☑3.

### 5-2. 👁 게이트 2번(adv_no_putaway) 하향 — 게이트가 아니라 관찰 대상

**WMS 는 put-away 없이 Apply 하지 않는다**(Caleb 확인 + 코드: Simple 은 Convert 시 SR→PA 이동,
Advanced 는 stage2 가 put-away 를 반드시 호출). ⇒ 「Advanced 인데 PA 없음」은 **우리 시스템이
만들 수 없는 상태**이고, 이 코드는 **예외 감지기**(WMS 밖 직접 입고 · stage2 부분 실패 방치)다.
실패 방향도 안전하다 — 기표를 **안 하는** 쪽이지 틀린 행을 만들지 않는다. ⇒ ⑤ 진입을 막지 않는다.
⚠️⚠️ **복귀 조건: Advanced PO 기본값을 켜면 다시 게이트로.** 그때는 WMS 가 Advanced 경로로 쓰므로
stage1 성공/stage2 실패 문서가 실제로 생길 수 있다.

### 5-3. 새 사실 4건

1. ⚠️ **판매 캡이 3.6배** — 하루치 창에서 후보 145 대 캡 40. 하루치를 따라잡는 데 **4회차**가
   필요하다(유실은 없으나 실시간성 저하 — shadow 대조 때 전날 판매가 아직 안 들어와 있을 수 있다).
   ⇒ **해결은 캡 상향이 아니다**(1,200ms×40=48초로 이미 창의 80%). **회차 주기**를 짧게, 소스별로
   캡·주기를 다르게 두는 안을 ⑤에서 정한다(판매·발주 자주 / 반품 드물게 — 하루 4건).
2. ⚠️ **트랜스퍼의 bin 은 헤더에 있다 — 원장이 안 읽고 있을 뿐이다** (⚠️ 아래 5-4 정정 참조).
   `FromLocation`/`ToLocation` 이 `"창고: bin"` 문자열이다([실측] TR-02645
   `"Asung - Edmonton: EZ01Pallet03"` → `"Asung Trading Inc.: F0300PALLET01"` · 목록·상세 양쪽).
   **문서 하나 = bin 하나 → bin 하나**라 라인에 bin 이 없는 것이 정상이다(트랜스퍼는 문서 하나 =
   자리 하나가 업무의 성격 — WMS 도 Apply 시 **출발 bin 별로 문서를 쪼갠다**).
   현재 코드는 `From`/`To` GUID 만 `resolveLoc` 에 넘겨 창고만 해석 → `bins=[""]`.
   **창고 단위는 지금도 정확** · 자리 단위로 올릴 때 `": "` 파싱 + 매핑 대조로 고친다.
   ⚠️ `Lines[].ProductCustomField1/2` 는 상품 마스터 필드라 쓰면 안 된다(TR-02644 는 null).
3. ✅ **되돌림 트랜스퍼는 이미 정확하게 하고 있다** — 잘못 간 물건은 **WMS 를 거치지 않고 Cin7 에서
   직접** `From`/`To` 를 반대로 한 트랜스퍼 백으로 해결하며, 실물 7건(`Search=error` · 전부
   COMPLETED) **전부 `창고: bin` 으로 출발·도착이 명시**돼 있다(사람이 `ToLocation` 에도 bin 을
   찍는다). `Reference` 에 사유도 남긴다(「EDM Transfer Error」·「Revised Transfer Error -
   TR-01126」). ⇒ 원장이 그 데이터를 안 읽는 것이 문제였을 뿐(2번). ⚠️ 남는 질문 = 실물 이동이
   없는 장부 조정이면 원장은 실제 이동과 구분하지 못한다(총량은 왕복 상쇄 · **자리 단위에서는
   두 번의 이동**으로 기록) — 자리 단위 설계 때 판단. ⇒ 정본 1부 이동 절에 등록.
4. ⚠️ **이동 소스는 커서 seed 가 필수** — `from_cursor` 없이 부르면 TR-00001(2025-10-27)부터
   전량을 훑는다. dry 는 정상이나 쓰기를 켜면 **매 회차 처음부터 재처리** → 게이트 6번으로 신설.

### 5-4. ⚠️ 정정 — 「트랜스퍼는 bin 이 없다」는 오판이었다 (같은 날 재조사)

처음에 **dry 응답의 `bins=[""]` 와 `raw.line` 필드 목록만 보고 "bin 이 없다"고 결론**냈다.
**Cin7 화면에는 bin 이 보인다**는 Caleb 지적으로 GAS 프로브를 돌렸더니 **헤더
`FromLocation`/`ToLocation` 에 `"창고: bin"` 문자열로 있었다.** 「데이터가 없다」가 아니라
**「우리가 안 읽는다」**였다.

📌 **교훈: 응답의 한 부분만 보고 "없다"고 결론내지 말 것** — 발주에서 SR 만 보고 「Advanced 는
bin 이 없다」고 판단했던 것과 **정확히 같은 실수를 이틀 만에 반복**했다. 그때도 답은 다른
블록(PA)에 있었고, 이번에도 다른 위치(헤더)에 있었다.
⇒ 점검 질문: **"이 값이 라인에 없다면, 헤더·다른 블록·다른 엔드포인트에는 없나?"**
그리고 **화면에 보이는데 API 에 없어 보이면 API 를 덜 본 것**이다.

### 6-1. ☑ 게이트 5번(캡·페이싱) 닫힘 — 6종 동시 실행에서 429 0건

`DETAIL_SLEEP_MS=1200` + `_shared/cin7.ts` 백오프를 `Retry-After` 기반(재시도 1회·최대 60초)으로
교체해 배포(공용 파일이라 5개 EF 전부).

- [검증] **단일 소스 발주 `ledger_rows 727` — 페이싱 전과 동일.** 속도만 바뀌고 결과는 안 바뀐다.
- [검증] **6종 동시 실행 `?dry=1`: `rate_limited` 가 전 소스 false.**

⚠️ **다만 `TIME_BUDGET_MS=120초` 안에 6종을 다 돌 수 없다** — 첫 소스(adjustment, 5,009행)가
예산을 거의 소진하고 `transfer` 는 0행 `capped:"time"`, 나머지 4종은
`aborted: "time budget exhausted before this source"` 로 **시작조차 못 했다.**
⇒ **한 회차에 6종을 다 돌린다는 전제 자체를 버린다.** ⑤에서 **소스별 cron 분리**로 간다
(판매·발주는 자주, 반품은 드물게 — [실측] 반품은 하루 4건).

📌 **이것은 페이싱 실패가 아니라 시간 가드의 정상 동작이다 — 판정 기준은 `rate_limited` 다.**
두 가드(시간·레이트)를 섞어 읽으면 멀쩡한 페이싱을 다시 손대게 된다.

### 6-2. 🟡 게이트 4번(ON CONFLICT) — 코드 완료, 실동작 미검증

§2-2 에서 실례를 확보한 그 문제다. **가설 → 실례 → 구현이 하루 안에 진행됐다.**

`inv_conflicts` 테이블 신설(마이그레이션 `20260819000000`) + `inv-collect` 에 감지 로직
(`writeLedgerDetectingConflicts`, `@2026-08-19.1`). 배포·적용 완료.

**동작**: 배치 INSERT 를 `return=representation`(`select=` 키 7종으로 좁힘)으로 보내 실삽입 행을
받고, 보낸 것과 **키 7종으로 매칭**해(배열 순서 아님) 버려진 행을 특정한다 → 그 행들만
**`line_ref` 50개 청크**로 조회해(doc_number 단독은 대형 트랜스퍼 1,376행/문서에서 1000행 캡에
잘린다) `qty_delta`·`occurred_on` 을 비교 → **다르면 `inv_conflicts` 에 INSERT**. 같으면 무동작
(정상적인 재수집). **②-a·②-b 양쪽 삽입 지점 모두** 적용.

- ⚠️ **쓰기를 차단하지 않는다** — 수량 정정은 정상 실무라 차단하면 원장이 자주 멈춘다. 기록만 한다.
- ⚠️ **원장 행은 고치지도 지우지도 않는다**(append-only). 역분개는 자리 단위 원장 과제.
- ⚠️ **첫 검증은 ⑤에서 `commit=1` 을 처음 켤 때다** — dry 는 쓰지 않아 버려짐 자체가 없다.
  그때 볼 것: `insert_skipped ≠ 0` 은 **정상**(재수집) · `conflicts_detected ≠ 0` 이면
  `select * from inv_conflicts order by detected_at desc`.
- 📌 **첫 회차는 `insert_skipped` 가 0**이다(원장이 비어 있으므로) — 두 번째 회차부터 의미가 있다.
- 📌 **부수 의미 변경**: `R.written` 이 「시도 행수」 → **「실삽입 행수」**(재수집 중복 제외).
  `inv_sync_state.note` 에 `rows=N inserted=M` 병기. 소비처 0 확인 후 변경 — ⑥ 대조 화면이
  생기면 이 정의가 기준이다.

### 6-3. ✅ Simple 분기가 실제로 행을 만들었다 (PO-01112)

종전에는 `simple_docs > 0` 이어도 SR 블록이 전부 `NOT AVAILABLE` 이라 걸러졌을 뿐,
**Simple 축이 원장 행을 만든 적은 없었다.** PO-01112 가 13:34 토론토에 Simple 로 Apply 되면서
`sr_block_status_counts={AUTHORISED:1, NOT AVAILABLE:5}` 가 되었고 **102행**이 들어왔다
(같은 창 `ledger_rows` 727 → 829). ⇒ **Simple=SR 축 결정이 실동작으로 검증됐다.**

📌 이 +102 는 코드 변경이 아니라 **데이터 변화**였다 — `candidates`·`docs_processed` 가 20 으로
동일한데 행만 늘어 **처음에 감지 로직을 의심했으나**, `wms_receipts.applied_at` 조회로 확인됐다.
⇒ 점검 순서: **행 수가 늘면 코드보다 그날의 입고를 먼저 볼 것.**

### 6-4. ✅ 분할 인보이스 조사 — 구조적 장벽 없음

어제 「미확인 — 조사 필요」로 남긴 항목의 답이다. GAS 프로브 `ppa_invoiceSplit`,
`UpdatedSince=2026-07-01` · 대상 128건(VOID·`IsServiceOnly` 제외). 세는 조건은 Advanced 게이트와
동일(`Invoice[]` 중 `Status ∈ {AUTHORISED, PAID}` 이면서 `TaskID` 보유).

결과 `{0개: 18, 1개: 101, 2개+: 9}` — 표면상 Apply 불가 **21.1%**. **그러나 성격이 갈린다:**

- **2개+ 9건은 전부 「앞으로 반복되지 않는 것」** — 8건은 **WMS 도입 이전**, 나머지 1건은
  PO-01130(아래 6-5, Apply 안 하기로 정한 건). Caleb 확인: **「한 PO = 한 I&R」을 약속으로 정해
  운영 중**이므로 신규 PO 에서는 발생하지 않는다.
- **0개 18건 중 대부분은 인보이스 미발행**(`ORDERED`·`NOT AVAILABLE`) — **Simple 에서도 Invoice
  First 게이트에 막힌다. Advanced 때문에 새로 생기는 문제가 아니다.**
- ⚠️ **0개 중 3건(PO-00874·00893·01112)은 인보이스가 `AUTHORISED`/`PAID` 인데 `TaskID` 가 없다.**
  셋 다 Simple 이다 — **Simple 의 `Invoice` 블록에는 `TaskID` 가 없는 것으로 보이나 미확인.**
  사실이면 이 조사 방식이 Advanced 기본값 상황을 정확히 반영하지 못한 것이다(처음부터 Advanced 면
  `TaskID` 가 붙는다).

⇒ 남은 확인 2가지: ① `TaskID` 없는 3건의 정체 ② **Advanced PO 1건으로 실물 Apply 검증.**
📌 **①은 ②로 자연히 답이 나온다** — 다음 리시빙 때 PO 하나를 수동으로 `Convert` 해놓고 Apply
하면 **설정을 안 켜고도** Advanced 경로 전체가 검증된다.

### 6-5. ⚠️ 리시빙 — `externally_applied` 신설 (실사고 PO-01130)

Cin7 에서 이미 처리가 끝나 WMS 로 Apply 하지 않기로 정한 receipt 가 `completed` + `applied_at=null`
이라 **Apply 대기 목록에 영구히 남았다.** `Delete` 는 라인별 작업자 기록 등 이력을 지우므로 부적합.

상태값 추가(`20260819100000` — CHECK 4값 → 5값, **baseline 무접촉**). `applied_at` 은 **안 채운다**
— 「WMS 가 Cin7 에 쓴 적 없다」는 사실 보존. 전이는 admin Review 모달에서만
(`Mark externally applied` / `Back to completed`, `canApply`), 사유 **필수** + `apply_note` 에
**덧붙임**([실물] 표시→원복→재표시 3문장이 시간순으로 남는 것 확인).

⚠️⚠️ **누수 봉인 2곳이 이 기능의 핵심이다** — 없으면 새 상태가 **화면 한 번 여는 것으로 소멸**한다:
① `startPo` 의 `status!=="completed"` "미완료" 판정 ② `openReceipt` 의 `in_progress` 되돌림 앞 가드
(⚠️ **`?receipt=N` URL 직접 진입** 때문에 ①만으로는 부족하다).

📌 **A안(status 값) 선택 근거**: 봉인 지점 수는 B안(별도 컬럼)과 비슷하나 **실패 모드의 값이 다르다**
— A 는 놓치면 되돌릴 수 있는 WMS 내부 문제, **B 는 놓치면 Cin7 이중 Apply(재고 사고)**.
상세·잔류 2건은 `asung-wms` 스킬 규칙 20 이 정본.
