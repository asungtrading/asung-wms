# 2026-08-31 (밤) — bin 백필 스위프: 유입이 놓친 자리를 서버가 다시 채운다

커밋 1건(`7c148e0` — `hello` EF + 테스트 스위트 · 마이그레이션 0 · 프론트 0).
**「무엇을」은 커밋 메시지에 있다 — 이 문서는 「왜 그렇게 됐나」다.**

같은 날 앞선 기록: `docs/sessions/2026-08-31-cursor-defects.md` ·
`docs/sessions/2026-08-31-transfer-departure-bin.md`(원장 — 이 건의 발견 출처).

## 1. 발견 경위 — 원장에서 넘어왔다

원장 세션이 트랜스퍼 출발 bin 을 WMS 픽(`wms_order_lines.bin_location`)에서 채우다
**4줄이 안 풀렸고**(TR-04173 3 + TR-04330 1), 그 4줄을 파다 나온 건이다 —
sticky(`wms_sku_bins`)도 Cin7 화면도 자리를 아는데 **오더 라인만 비어 있었다.**

📌 **한 세션의 막힌 4줄이 다른 세션의 구조 결함을 드러냈다** — 세션을 나눠 쓰는 것의
효용이 실물로 나온 사례다. 원장 쪽 경위는 그쪽 문서가 정본이고, 여기서는 가리키기만 한다.

## 2. 원인 규명 (실측)

- **SO-15071 세 줄(WTA00219·220·286)의 `line_flag` 가 전부 `no_bin`** — 유입 순간
  `wms_sku_bins` 조회가 **0행**이었다. 나중에 값이 사라진 것이 아니라 처음부터 없었다.
- **규모**: 2026-08 한 달 **52오더 · 약 180줄 · 거의 매일.** 그중 `now_known`(지금은 sticky 가
  아는데 라인만 빈) **약 110줄** — 자리를 아는데 못 알려준 것이지, 정말 자리가 없던 게 아니다.
- **`no_bin` 과 `flagged_at_intake` 가 모든 행에서 일치** — 유입 시점 미발견이 전부이고
  다른 원인(사후 소실 등)은 없다.
- **구조**: 유입(`assembleLine`)은 그 순간의 `wms_sku_bins`(전일 05:00 Cin7 → 06:30 재적재)만
  보고, `bin_location` 쓰기는 레포 전수에서 유입 한 곳뿐 — **유입 때 못 찾으면 영영 빈다.**
  저녁 유입 오더가 다음날 아침에야 sticky 에 실리는 자리를 못 받는 것이 전형이다.

### ⚠️ 기각된 가설 — 다시 파지 말 것

- **「다중 행 오처리」(유력 후보였다) → 코드로 기각.** 유입 쿼리(`hello` `assembleLine`)에
  `warehouse`·`is_current=eq.true` 필터가 **둘 다** 있고, `available desc` 정렬 후 `[0]` 을
  고른다 — 다중 행은 안전하게 처리된다. 단서였던 에드먼튼 `is_current=false` 행은
  **쿼리에 아예 안 들어온다.**
- **「자리가 틀린 것」(유입 후 이동)은 다른 문제다.** [실측] `wrong_location` 리포트
  주당 5~18건(6주) · **open 전부 0** — 신고→해결 경로가 이미 돈다. 별건으로 둔다.
  📌 섞으면 「비어 있던 것을 채우는 안전한 변경」이 「맞는 값을 덮는 위험한 변경」과
  한 배를 탄다 — 나중에 최신화를 논할 때 이 숫자가 근거다.

## 3. ⚠️ A안(화면 렌더 시점 재조회) 기각 — 이 근거를 남기지 않으면 다시 논의된다

처음 방향은 「픽 화면이 이미 재고(available)를 렌더 시점에 재조회하니 bin 도 얹자」였다.
조사가 셋을 들어 기각했다:

1. **소비처가 픽 화면 하나가 아니다** — packer · manager 분할/미리보기/첫 인쇄 ·
   픽리스트 Zones 요약 · admin Trace · **원장 트랜스퍼 출발 bin**. 표시만 고치면
   나머지는 그대로 빈다.
2. **동선 정렬이 렌더보다 먼저다** — picker 는 정렬 → bcMap → 렌더 → enrich 순서라,
   재조회가 도착했을 때 정렬은 끝나 있고 그 라인은 9999 슬롯(경로 맨 뒤)에 남는다.
   ⚠️ 그때 재정렬하면 **bcMap 이 배열 인덱스를 들고 있어 스캔이 엉뚱한 라인에
   가산된다**(규칙 25 — picker 는 인덱스 기반 잔존).
3. **원장이 「화면=DB」에 기댄다** — 화면만 딴 값을 보여주면 「작업자가 집은 자리」와
   DB 가 갈리고, 트랜스퍼 출발 bin 대조(112/112 일치의 축)가 깨진다.

📌 **「어디까지 닿는가」를 물으니 답이 뒤집혔다** — 화면 고치기가 아니라 DB 고치기여야
했고, 그래서 스위프는 EF(서버 · `wms_order_lines` 의 단일 쓰기 주체 유지)에 들어갔다.

## 4. 설계에서 내가 못 본 것 — 조사가 잡았다

⚠️ **이미 픽된 라인 제외(`picked_base > 0`).** picking 오더에는 안내 없이 이미 집은
라인이 있을 수 있고, 그걸 지금 sticky 값으로 채우면 **「실제로 집은 자리」가 아닌 값이
원장 다리로 흐른다.** 지시 프롬프트에 없던 항목 — 조사 단계에서 나왔고 Caleb 이 승인하며
"내가 못 본 것"으로 확인했다. 구현은 대조 실패 시 그 회차 스위프 전체를 건너뛴다
(덜 채우는 쪽이 안전).

## 5. 조사가 스스로 정정한 것 2건

1. **1차 보고의 「`line_flag` 소비처 0곳」은 틀렸다** → 재grep 으로 **2곳** 확인:
   manager 분할 미리보기(`manager.html:411-413`·`:462-463` — no_bin 칩)와
   `wms_orders.needs_review`(`hello:443` — flags 하나라도 있으면 true).
   확인 안 하고 갔으면 매니저 화면에 이상한 조합이 나왔다.
   ⇒ 스위프는 둘 다 **무접촉**으로 확정 — flag 는 「유입 땐 몰랐다」는 기록이고,
   **no_bin 칩 + 채워진 bin 의 공존이 의도다**(EF 주석·스킬에 명시).
2. **「`sku=in.()` 따옴표+인코딩이 조용히 0행이 되지 않나」는 배포 전에 제기·반증됐다** —
   레포 전수 grep 으로 같은 조립이 프로덕션 4곳에서 돌고 있음을 확인
   (`receiving:227` 은 **같은 sku 컬럼** · `hello:176` 은 5분마다 · `inv-collect:608`
   은 당일 592줄 해결 실측). 📌 의심을 제기한 것은 옳았고, 반증도 실측으로 왔다 —
   「코드 배선 테스트 14개는 PostgREST 응답 검증이 아니다」는 지적이 판정표
   (dry-run 카운터 ↔ `expected_filled` 대조 SQL)를 만들게 했다.

## 6. 앵커 — 「조용한 결함」 1건 계상 (이 세션)

**4조건 판정**: ① 에러 없음 ✅ (유입은 매번 200 — `no_bin` 은 flag 로만 남았다)
② 정지 없음 ✅ ③ 신고 없음 ✅ (작업자는 자리 안내 없이 알아서 찾았다 — `—` 표시를
아무도 문제 삼지 않았다) ④ 데이터 틀림 ✅ — **알 수 있는 자리 110줄/월이 비어 있었고**,
그 결손이 픽 동선(9999 맨 뒤)·픽리스트 Zones(`·`)·원장 트랜스퍼 해결(미해결 4줄)로
번지고 있었다. ⇒ **계상 1건.**

⚠️ **어느 세션에 세나** — 발견의 단서(막힌 4줄)는 원장 세션이 만들었지만, 원장 문서는
이 건을 자기 결함으로 계상하지 않았고(확인함 — 그쪽 소관도 아니다), 규명·처방·계상은
이 세션이 했다. **이 세션에 1건, 중복 없음.** (08-25 전례와 같은 처리 — 앵커는
「세션당」이라 날짜로 합치지 않는다.)

📌 성격: 새 종류가 아니라 **시점성 결손** — 유입 단발 조회 + 사후 보정 부재라는 구조가
매일 만들던 것. 세션 성격 = 깊이 판 조사(원장 파생 → 원인 규명 → 설계 → 구현까지 한 세션).

## 8. 📌 오늘의 교훈

- **「어디서 고치나」는 「어디까지 닿는가」가 정한다** — 증상은 픽 화면이었지만 소비처
  전수를 세니 답은 DB(서버)였다. 화면 수정안은 검증된 스캔 코어(bcMap 인덱스)까지
  건드릴 뻔했다.
- **프로덕션 접속 경로를 임의로 만들지 않는다** — 이 세션에서 psql 직결 시도를 지적받고
  메모리에 재위반 기록을 남겼다. SQL 은 제시하고 Caleb 이 SQL Editor 에서 실행한다.
- **의심은 배포 전에, 반증은 실측으로** — `sku=in.()` 형태 의심이 판정표와 대조 SQL 을
  만들었다. 배선 테스트와 응답 검증은 다른 층이다.
