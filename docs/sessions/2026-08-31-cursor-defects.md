## 1. ⚠️ 결함 C — `Updated` 동률 그룹이 캡보다 크면 커서가 영구 동결

### 증상

판매 수집이 **8/28 11:25(토론토)부터 하루 반** 멈췄다. cron 잡 7 은 5분마다 **350회 넘게 돌며
전부 `succeeded`** 였다. 원장에 판매가 안 쌓여 재고가 실제보다 많게 계산됐다(861 SKU 쌍).

### 원인

**밀리초까지 같은 `Updated`(`2026-08-28T15:25:33.383Z`)를 가진 판매 문서가 238건**이었다.

```
1136  cands.sort(...)                                        // Updated 오름차순
1158  if (cd.updated < cursorBefore) { precisionSkipped++; }  // < 라 같은 값은 통과
1450  if (cd.updated) lastProcessedUpdated = cd.updated;
1457  cursorWouldBe = detailCapped ? (lastProcessedUpdated ?? cursorBefore) : runStartIso
```

캡(40건 / 시간 120초)이 **동률 그룹 안에서 끝나므로** 마지막 처리 문서의 `Updated` 가 언제나
커서와 같다 ⇒ **커서 제자리 · 다음 회차도 같은 앞 40건.**

⚠️ **캡을 올려도 안 풀린다**: 238 × `DETAIL_SLEEP_MS 1200` = **286초** > 시간 예산 120초.

### 기존 가드가 못 잡은 이유

| | |
|---|---|
| 결함 A | 후보 집합이 안 줄어 같은 40건 반복 → 정밀도 필터로 해결 (08-17) |
| 결함 B | `Updated` 가 null 인 문서가 캡을 채움 → `cappedNoUpdated` 로 차단 |
| **결함 C** | **`Updated` 동률 그룹이 캡보다 크다** → ⚠️ 가드 없음 |

`cappedNoUpdated = detailCapped && lastProcessedUpdated == null` 는 **「시각이 없다」**만 본다.
C 는 **「시각이 있는데 다 같다」**라 조건에 안 걸렸다.

### ⚠️ 원인은 통제 불가다 — 재발 전제

[실측] `SO-15485` 의 Cin7 History 마지막 활동은 **8/28 10:08**, `SO-13009` 는 **8/21**.
**11:25 에 해당하는 History 줄이 없다** ⇒ 사람도 워크플로도 건드리지 않았다.
238건이 밀리초까지 같은 것과 합치면 **Cin7 플랫폼 쪽 일괄 갱신**이다. **예고 없고 주기 미상.**

📌 그리고 **`Updated` 는 「문서가 바뀌었다」는 뜻이 아니다.** 우리는 그것을 변경 감지 축으로
쓰는데, Cin7 이 내용 변화 없이 건드릴 수 있다(08-26 `PO-00754` 도 상태 라벨만 바뀌었다).
무해한 방향이지만(더 받는 쪽) **대량이면 커서를 막는다.**

### 수정 (커밋 `e673cc7` · `inv-collect@2026-08-30.1`)

- 커서 형식 **`<Updated>|<문서식별자>`** (`OrderNumber` → `SaleID`/`ID` 폴백)
- ⭐ **마이그레이션 불필요** — `Updated` 가 고정 길이 ISO(24자)라 문자열 비교가 그대로 성립.
  기존 맨 ISO 커서는 **「그 시각 동률 그룹 맨 앞」**으로 해석된다 ⇒ 동률 문서를 **건너뛰지 않고
  재처리**한다(유니크 키가 흡수 — **안전 방향**).
- ⭐ **정렬을 `localeCompare` 에서 코드유닛 비교로 교체** — 필터가 쓰는 `<` 와 순서가 같아야
  하는데 `localeCompare` 는 `|` 같은 문장부호 취급이 ICU·로케일에 좌우된다. **두 순서가
  어긋나면 또 다른 유실**이다. (⚠️ 이 항목은 지시서에 없었다 — Claude Code 가 잡았다)
- ⭐ **증상 가드**: `cursorStalled = detailCapped && wouldBe <= before` → 경고 + commit 차단.
  A·B·C 가 전부 **「캡에 걸렸는데 커서가 안 나갔다」**로 나타났다. 원인별 가드는 매번 사촌을
  놓쳤으므로 **증상을 직접 본다.**
- 응답에 `updated_ties`(동률 조기 신호) · `cursor_stalled_alert` 추가
- `'|'` 근거: [실측] `inv_ledger.doc_number` 중 `|` 포함 **0건** · ASCII 124

⚠️ **②-a(문서번호 커서)는 무접촉**으로 뒀다 — 그것이 §3 의 결함 D 를 못 잡은 이유다.

## 2. ⚠️⚠️ 이중 차감 — `ShipmentDate` 는 실제 차감 시각이 아니다

### 내가 만든 문제

8/29 저녁 응급 조치로 **커서를 `.384Z` 로 밀어 동률 238건을 건너뛰었다.** 그때
「8/21 이전 출하라 어차피 원장에 안 들어온다」고 판단했으나 **검증하지 않은 추정이었고 틀렸다.**

```
SO-15041  주문 8/20 · 출하 8/21   ⚠️     SO-15028  주문 8/20 · 출하 8/20  ✅
SO-15038  주문 8/20 · 출하 8/21   ⚠️     SO-14995  주문 8/19 · 출하 8/20  ✅
SO-15033  주문 8/20 · 출하 8/21   ⚠️
SO-14974  주문 8/19 · 출하 8/21   ⚠️      ← 표본 6건 중 4건이 8/21 이후
```

8/30 에 tie-breaker 를 배포하고 커서를 되돌려 **4문서 522행(−2,261)** 을 회수했다.
⇒ 대조가 **원장 적음 4건 → 416건 · 합 −1,930** 으로 뒤집혔다.

### ⭐ 원인 — 스냅샷 경계

📌 트랜스퍼에서 겪은 **「since 경계 아티팩트」의 판매판**이다. 그때는 무해했지만

## 3. ⚠️ 결함 D — ②-a 커서 홀드 + 캡 = 뒤쪽 문서가 영영 안 들어온다

### 발견

정정 후에도 **「원장이 많다」 270쌍**이 남았다. 최상위 `BMA15710`(토론토)로 검산했다.

```
기초 스냅샷 1,131  −  원장이 뺀 것 392(상쇄 후 386)  =  745
Cin7 601   ⇒  Cin7 이 144 를 더 뺐다
Cin7 이동내역:  TR-04330 · 8/28 · Transfer out · −144 · IN TRANSIT
원장:           없음                                     ⭐ 정확히 일치
```

### 원인

```
transfer 커서   TR-04172 에 고정 (TR-04173·74·75 가 IN TRANSIT = processed_nonterminal)
후보           TR-04173 ~ TR-04330  ≈ 159건
[실측 8/31]    processed 36 · processed_nonterminal 3 · detail_fetched 39
               ⚠️ hold_capped 120 · detail_capped_remaining 120 · reason "time"
```

**매 회차 앞 39건만 보고 뒤 120건은 손도 못 댄다.** `TR-04330` 이 그 안에 있다.

📌 [실측 8/27] 에는 `detail_fetched 36 · capped_remaining 0` 이었다. **그 뒤 트랜스퍼가 늘어
캡을 넘었고, 그 순간부터 뒤쪽이 조용히 누락됐다.**

⚠️ 그리고 **낭비가 크다** — `processed 36` 은 이미 원장에 있는 완료 문서를 매 회차 다시 읽는
것이다. 실제로 재방문이 필요한 건 `processed_nonterminal 3` 뿐이다.

### 왜 새 가드가 안 잡았나

`cursor_stalled_alert` 를 **②-b 에만** 넣었다(지시서에서 ②-a 무접촉). 그리고 ②-a 에 넣었어도
**소음이 된다** — 여기선 커서가 안 움직이는 게 **설계대로**다(비종결 문서 앞에서 멈춤).
진짜 신호는 커서가 아니라 **`hold_capped` 가 0이 아닌 것**이다.

### ⬜ 미해결 — 처방 후보

| | |
|---|---|
| **(A) 기다린다** | `TR-04173·74·75` 가 도착하면 커서가 점프하고 120건이 몇 회차에 소화된다. ⚠️ 10일째이고 그동안 누락이 쌓인다 |
| ~~(B) 커서를 TR-04175 로 민다~~ | ❌ 그 3건의 **도착 다리를 영영 못 받는다** — 에드먼튼 실재고가 틀어진다 |
| **(C) 구조 수정** | 「홀드 목록」과 「커서 바닥」을 분리 — 비종결 문서를 따로 추적하고 커서는 전진시킨다 |
| **(D) 완료 문서 재조회 회피** | 이미 원장에 있는 문서는 상세를 부르지 않는다 ⇒ 캡 여유가 크게 는다 |

📌 (C)+(D)가 근본이다. **다음 세션 최우선.**

## 4. ⭐ 관통하는 교훈

### 4-a. 경고는 응답에만 두면 아무도 안 본다 — 세 번째다

```
inv-sku-types cron 미등록   (08-24) — 돌지 않는데 succeeded
inv-cost placeholder        (08-28) — 401 인데 succeeded
결함 C                      (08-29) — 350회+ succeeded
```

⚠️ **`cron.job_run_details` 의 `succeeded` 는 아무것도 보장하지 않는다.** 전부 **결과물을
읽어야만** 알 수 있었다.

### 4-b. ⭐ 아침 점검에 「수집이 밀렸나」가 없다

결함 C·D 둘 다 **대조가 잡았지만 하루 늦었다.** 커서 상태를 매일 봤다면 즉시 알았다.

⚠️ 그런데 **SQL 만으로는 부족하다** — `hold_capped`·`detail_capped` 는 **EF 응답에만 있고
DB 에 안 남는다.** ⇒ ⬜ **EF 회차 통계를 테이블에 남기는 설계가 필요하다**
(`inv_snapshot_runs` 가 스냅샷에 한 역할과 같다).

### 4-c. 내가 틀린 것 (기록 규칙)

1. ⚠️⚠️ **「건너뛰기 안전」을 검증 없이 판단해 데이터를 잃었다.** 근거로 든 둘이 다 약했다 —
   「원장에 없다 = 8/21 이전 출하」(경계가 정확히 8/20~8/21에 걸쳐 있었다) ·
   「대량 갱신 전에 이미 수집됐다」(갱신 시각과 출하 시각은 다르다).
2. ⚠️ **「회수 완료」라고 했으나 이중 차감을 만들었다.** 8/21 행 수 1,419만 보고 단정했는데
   **before 값을 갖고 있지 않았다** — 비교 대상 없이 「늘었다」고 했다.
3. **회차 수를 「6회차」로 계산했다** — `<` 필터 때문에 경계 문서가 매 회차 재조회되어
   순전진은 캡−1 이다(Claude Code 정정).
4. **`localeCompare` 를 그대로 두라고 지시했다** — 정렬과 필터가 다른 순서를 쓸 뻔했다.

📌 관통: **검증 없이 「안전하다」고 말한 것이 가장 비쌌다.** 확인 한 번(출하 승인 시각)이면
막을 수 있었다.
