## 1. 검증된 것 (정정 아님 · 기록)

- ⭐ **운영 마이그레이션 13개 적용 완료** (`20260908195949` ~ `20260910152545`).
  - [Caleb 판정] **원가 레이어를 운영에 올리지 않는다는 방침을 뒤집었다.** 근거: 필요한 건 `inv_doc_cost` 표 하나인데 `db push` 가 갈라 올릴 수 없고, 파일을 옮기거나 `repair` 로 우회하는 것보다 **전부 올리는 쪽이 실수의 여지가 적다.** cron·트리거가 없어 **아무것도 자동으로 돌지 않는다**([실측] 네 표 전부 0행).
  - ⚠️ ⇒ 아침 점검 ⑭ 의 「의도한 차이」 기준선을 갱신해야 한다 — 운영·테스트 차이가 이제 「원가 레이어는 테스트에만」으로 설명되지 않는다. ⚠️⚠️ **「운영에 있는데 아무도 안 쓴다」를 사람이 기억해야 한다.**
  - 📌 push 끝의 `failed to cache migrations catalog`(pgdelta 인증서 ENOENT) — **DB 영향 없음**(`Applying` 13줄 뒤에 발생 · `schema_migrations` 13행 정상).
  - 📌 `NOTICE (42P07) relation "inv_doc_cost" already exists` — **의도된 것**(`141553` 이 만든 표를 `152545` 가 `if not exists` 로 건너뜀).
- ⭐ **EF 호출은 헤더 둘이 맞다** — `Authorization: Bearer <anon>` + `x-wms-cron-key`. EF 코드는 `x-wms-cron-key` 만 검사하지만 **게이트웨이가 `Authorization` 을 요구한다**(`UNAUTHORIZED_NO_AUTH_HEADER`). `cron.job` 의 `net.http_get` 은 DB 내부 호출이라 헤더 하나로 도는 것이고, **밖에서 `curl` 로는 둘 다 필요하다.**
- ⭐ **추출 로직 실물 재확인** — `TR-03975` · `398.75` · `B6900109` · `_59_`/`_136_` · `occurred_on 2026-08-27`(저널 Date) · `completion_date 2026-08-26`. 📌 `occurred_on` ≠ `completion_date`(인보이스 날짜 ≠ 물건 날짜) — 기존 서술과 일치.
- ⭐ **`inv-cost` 는 하루 한 번**(`33 4 * * *` · 토론토 00:33 · jobid 16). 스킬 ⑤ 의 「`purchase` 15분」은 `inv-collect-purchase`(jobid 8)이고 **원가 축이 아니다** → 스킬 ⑤ 에 잡 이름·jobid 병기(반영).
- ⚠️ **`inv-doc-cost` 는 cron 미등록**(운영 `cron.job` 실측) — 손으로 부른다. 등록은 ③ Cin7 대조 다음(설계 §12 「남는 미결」).
- ⚠️⚠️ **문서 필터 실측** — `From <> To`(GUID)는 창고간 이동을 좁히지 못한다(bin 마다 GUID). 4,680건 전수 모양·창고 이름 둘·GUID·정정 방향(콜론 앞 창고 이름)은 설계 §12 「조회 함정」 정정과 `index.ts` 헤더에 있다 — 여기 반복하지 않는다. ⬜ 코드 미수정(cron 등록 때 함께).

## 2. ⚠️⚠️ 오늘 내가 만든 것 — 삽질 기록 (「내가 틀린 것」 · 앵커에 세지 말 것)

**(가) `recheck_since` 로 시각을 네 번 밀었다.**
목표는 「운송비가 있는 트랜스퍼를 처리한다」였는데 「오늘 갱신된 문서에서 저널을 찾는다」로 바꿔 놓고, `2026-09-10T00:00Z` → `16:00Z` → `04/08/12:00Z` 로 창을 흔들었다.
⚠️⚠️ **`LastModifiedOn` 과 사건 날짜가 독립된 축이라는 것을 문서에서 읽고도 그랬다.** 9월 2일자 운송비를 오늘 시각 창에서 찾고 있었다.
⇒ ⭐ **`recheck_since` 는 「특정 문서에 닿는」 도구가 아니다.** 커서를 전진시키면 순서대로 지나간다.
📌 [지난 챗과 같은 모양] `docs_processed 0` 을 「도달 실패」로 오진하며 회차를 반복한 것과 같다 — **파라미터를 흔들어 특정 문서를 찾으려는 충동**이 공통 원인이다.

**(나) 목표가 「필터를 일반적으로 옳게 만들기」로 옮겨갔다.**
Caleb 이 「지금 하려는 게 정확히 뭐야」를 **세 번** 물어 되돌렸다. 실제 목표는 **8월 20일 이후 다섯 건**(`TR-03975`·`03976`·`04173`·`04174`·`04175`)이었고 Caleb 은 그것을 이미 알고 있었다.
⇒ ⭐ **작업 시작 전에 「끝났다」의 정의를 숫자로 적는다.** 「다섯 건이 `inv_doc_cost` 에 있다」.

**(다) 검증 단계를 불필요하게 끼워 넣었다.**
「오늘 붙은 운송비가 제대로 들어오나 먼저 보자」고 제안했으나, 추출 로직은 **어제 이미 `dry` 로 검증됐다**(`398.75`). 이미 닫힌 것을 다시 열었다.

**(라) 확인하지 않은 것을 사실로 적었다 — 세 건.**
- 「레포가 없어 `ledger-design.md` 를 읽을 수 없다」 → ⭐ **읽을 수 있었다**(공개 레포 · `raw.githubusercontent.com` 접근 가능). 세 번 반복해 말했다.
- 「`inv-cost` 가 15분 주기인데 반나절 멈췄다」 → 하루 한 번이었다(§1).
- 「`cron.job` 헤더가 하나이니 `curl` 도 하나로 된다」 → 게이트웨이가 거절했다(§1).
⇒ ⭐ **Rule 29 그대로다: 단정 전에 실제 값을 읽는다.** 오늘 오전 `IsSystem` 사고와 같은 모양.

**(마) 시간을 두 번 잘못 계산했다.** 14회차를 「5분」이라 했다(회차 48초 + sleep 을 빼고 sleep 만 더했다). 실제 11~14분. ⚠️ **그 숫자가 「EF 를 고칠까 돌릴까」 판단의 근거였다.**

**(바) 키를 대화에 노출시켰다.** `cron.job` 의 `command` 를 보라고 했고, 그 안에 `x-wms-cron-key` 평문이 있는 것을 **알고 있었다.** 다른 경로를 줘야 했다(`jobid, jobname, schedule, active` 만 select).
📌 백로그 14번(`x-wms-cron-key` 교체 · 시스템 완성 후)에 **노출이 반복된다는 사실** 추가(반영).

### 4-1. 필터 수정 결과 — 예측과 실측 일치
커밋 `fix(inv-doc-cost): 문서 필터를 창고 이름 기준으로 — bin GUID 가 창고를 못 가른다`(`index.ts` +15/−4 · `scripts/test-invdoccost.mjs` +34/−8 · 테스트 27 PASS · 배포 완료).

### 4-2. ⚠️⚠️ 105 와 7 은 다른 축 — 캡·주기 설계는 불필요했다
09-10 문서의 「후보 558 → 105」의 105 는 **전 기간 창고간 이동 수**. 실제 후보에는 하한(기초선 8/20)이 한 번 더 걸린다.
```
[실측 2026-09-11 · recheck_since=2026-08-20T00:00:00Z]
  list_total 4,680 · below_floor 4,122 · skip_same_warehouse 551 · candidates 7
    → processed 5      (TR-03975 · TR-03976 · TR-04173 · TR-04174 · TR-04175)
    → skip_no_journal 2 (TR-04330 · TR-04331 · 09-10 자 · 운송비 아직 안 붙음)

4,680 전체 COMPLETED → 105 창고간(전 기간) → 7 기초선 이후(실제 상세 호출) → 5 운송비 있음
```
⇒ 회차당 40건 캡에 걸릴 일이 사실상 없다(3주치가 7건 = 하루 한두 건). 105 로 캡·주기를 설계했으면 과대 설계였다 — 09-10 저녁 서술의 「3회차 · 사흘」은 이 혼동에서 나왔다(문서에 취소선으로 남김).

### 4-3. cron 등록 — jobid 19
```sql
select cron.schedule('inv-doc-cost', '45 4 * * *', $$
  select net.http_get(
    url     := 'https://gftpcnkxbdjzzfvzwcfl.supabase.co/functions/v1/inv-doc-cost?commit=1',
    headers := jsonb_build_object('x-wms-cron-key', '<WMS_CRON_SECRET>')
  );
$$);
```
| | |
|---|---|
| jobid | **19** (17 결번 · 18 = `inv-balance-diffs`) |
| schedule | `45 4 * * *` = UTC 04:45 = 토론토 00:45(EDT) · 겨울 EST 면 23:45(기존 잡 전부 같은 성질) |
| active | true |
| 첫 자동 실행 | **2026-09-12 새벽** — ⬜ 아침 점검 ⑤ 에서 `cost_transfer` `last_run` 갱신 확인 |

자리 근거: `inv-cost`(jobid 16 · `33 4`) 뒤 · `inv-snapshot-compare`(jobid 12 · `21 5`) 앞 — 원가 → 운송비 → 스냅샷, 아침 점검 시점엔 둘 다 끝나 있다. ⚠️ 순서 의존을 코드로 확인한 것은 아니다(`inv-doc-cost` 는 `inv_doc_cost` 표에만 쓰고 `inv_cost` 를 읽지 않아 독립으로 본다 · 배분은 cron 에 없는 `inv_layer_apply` 소관). `from_since` 는 붙이지 않았다 — 커서가 이미 서 있고 붙이면 충돌한다.

**확정 사실 — 빈 회차에도 커서는 전진한다.** [실측] `commit=1 · candidates 0 · docs_processed 0` 인데 `cursor_before 2026-09-10T21:07:43.939Z` → `cursor_after 2026-09-11T12:15:53.269Z`(회차 시각). `decideCursor`: 비캡 = 회차 시각 · 캡 = 마지막 키(테스트 ⑩). ⇒ 할 일이 없어도 커서가 나아가므로 매일 볼 후보가 쌓이지 않는다.

### 4-4. ⚠️⚠️ 아침 점검 ⓪·⑤ 의 `cost_transfer` 예외 문구를 되돌렸다
09-11 아침 스킬 ⓪·⑤ 에 「`lag_source` 가 `cost_transfer` 면 그 값으로 판정하지 말고 ⑤ 를 직접 볼 것」을 넣었다 — 근거는 cron 미등록. 오전에 그것이 해소됐다.
[실측 12:16Z · 등록 + `commit=1` 직후] `ledger_lag_source: "purchase"`(← `cost_transfer` 에서 넘어감) · `ledger_collected_at: 2026-09-11T12:08:02.527Z`.
⇒ 이제 `lag_source` 가 `cost_transfer` 로 뜨면 「무시할 예외」가 아니라 **「수집이 실제로 멈췄다」는 신호**다. 예외 문구를 그대로 두면 진짜 신호를 무시하게 된다 → 스킬 두 곳 취소선 + 정정.
⬜ 내일 아침(09-12)이 진짜 확인 — 오늘 전진은 손으로 돌린 `commit=1` 이고 cron 첫 실행이 아니다. 09-12 ⓪ 에서 `purchase` 유지 확인.
