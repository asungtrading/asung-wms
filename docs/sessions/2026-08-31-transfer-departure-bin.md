# 2026-08-31 (오후 후반) — 트랜스퍼 출발 bin: 답은 우리 안에 있었다

⚠️ 이 문서는 **막다른 길 다섯**을 담고 있다. **다시 파지 말 것.**
같은 날 앞선 기록: `docs/sessions/2026-08-31-cursor-defects.md`(커서 결함 C·D · 오후 세 건).

## 1. 무엇이 문제였나

창고 간 트랜스퍼의 **출발 bin** 이 원장에 비어 있었다.

```
[실측] bin 단위 대조 (기초 스냅샷 + 원장 델타  vs  당일 스냅샷 · IN_TRANSIT 제외)
  토론토    8,141칸 중 1,201칸 어긋남 · 격차 15,640
  에드먼튼  6,738칸 중    12칸       · 격차     80
```

⚠️ **한 건의 결손이 두 곳을 어긋나게 한다** — 유령 `bin=''`(−7,530 · 546칸)과 안 뺀 실제
bin(+6,710 · 544칸)이 **거울상**이다. 545 ↔ 544 로 짝이 맞는다.
📌 **창고 단위 합은 맞으므로 매일 대조(⑥)에는 안 걸린다.** 그래서 오래 몰랐다.

**대상은 5문서 734행** — `TR-04173`·`04174`·`04175`·`04330`·`04331`(전부 IN TRANSIT).

### ⚠️ 시작할 때 내가 갖고 있던 전제가 틀렸다

스킬에 「트랜스퍼가 헤더 `"창고: bin"` 을 **안 읽는다**」고 적혀 있었다. **틀렸다** —
같은 창고 안 bin 이동은 이미 읽고 있고(`TR-04166` `E050202 → E050103` · 335행), 문제는
**창고 간 이동에는 헤더에 bin 이 아예 없다**는 것이었다.
📌 확인 없이 옛 메모를 옮긴 것이다. 데이터를 보자마자 틀린 것을 알았다.

## 2. ⚠️⚠️ 막다른 길 다섯 — 다시 파지 말 것

| 시도 | 결과 |
|---|---|
| `GET /stockTransfer` → `Lines` | bin 없음 |
| 같은 응답의 `Order.Lines` | 키가 **완전히 동일** · bin 없음 |
| `GET /stockTransfer/order` → `Lines` | 키가 **완전히 동일** · bin 없음 |
| 공식 `dearinventory.apib` **Stock Transfer Line Model** | **`Bin`·`Location` 정의 자체가 없다** |
| **엔드포인트 102개 전수** | **재고 이동(movement) 조회 API 가 존재하지 않는다** |
| 픽용 SO 에서 읽기 | ⚠️ **VOID 하면 `Pick`/`Pack`/`Ship` lines 가 0이 된다**(실측 `SO-15482`) |
| WMS 픽 라인(`wms_pick_task_lines`) | bin 컬럼 없음 |

📌 추측한 이동 엔드포인트 4개(`ref/stockMovementDetails` 등)는 **HTTP 200 + HTML 404 페이지**를
돌려준다 — JSON 이 아니면 파싱 전에 걸러야 한다.
📌 `BinID` 는 apib 전체에서 **10개 절에만** 나오고 전부 생산 계열(Disassembly · Finished
Goods · Inventory Write-Off)이다. sale·purchase·transfer·adjustment 에는 **0건**.
⚠️ 그런데 **발주는 bin 을 받는다** — `PutAway.Lines` 의 `Location`/`LocationID` 다.
⇒ **Cin7 은 필드 이름이 둘이다**: `BinID`(생산) vs `Location`(입출고). 그리고 Cin7 에서
`Location` 은 **트리**다 — bin 도 Location 이다(`ref/location` 2,676건 · `ParentID` 로 창고에 매달림).

## 3. ⭐ 그런데 Cin7 은 기록하고 있다 — 화면 Export

트랜스퍼 화면의 **`Export`** 가 주는 CSV 에 **라인별 `Location`** 이 있다.

```
SKU,Name,BatchSerialNumber,ExpiryDate_YYYYMMDD,Transfer Quantity,Comments,⭐Location
ADG68236,…,,,6,,Asung Trading Inc.: F020802
```

### 결정적 실측 — 기록값인가 실시간 조회인가

`TR-04166` 은 `CON78011` 을 **`E050202` → `E050103`** 로 옮긴 문서다(8/21 · 1줄).
그 제품은 **지금 `E050103` 에 있다.**

```
CSV Location = "Asung Trading Inc.: E050202"   ← 출발 bin
⇒ 실시간 조회였다면 E050103 이 나왔어야 한다 ⇒ **기록값 확정**
```

⚠️ 화면의 `LOCATION` 컬럼 자체는 **현재 재고 조회**다 — `TR-04331` 네 줄이 오늘 스냅샷의
현재 bin 과 4/4 일치했다. **화면과 Export 가 다르다.** Export 가 문서 데이터다.

## 4. ⭐⭐ 답은 우리 DB 안에 있었다

```
[실측] TR-04331 CSV 112줄  vs  wms_order_lines.bin_location
  csv_lines 112 · found_in_wms 112 · bin_match 112 · bin_diff 0 · not_in_wms 0
```

**완전 일치.** Cin7 이 기록한 출발 bin = 우리 WMS 의 `bin_location`.

### 업무 흐름이 그 이유다 (Caleb 설명)

```
1. 매니저가 트랜스퍼 문서를 만든다
2. 같은 내용으로 **픽용 SO** 를 만든다 (가상 손님 `ASUNG EDM TRANSFER`)
3. Release to WMS → 분할 → 여러 사람이 픽·팩
4. 끝나면 그 SO 를 **VOID**
5. 트랜스퍼를 확정해 내보낸다 → 에드먼튼에서 리시빙·풋어웨이로 도착 bin 지정
```

⇒ **WMS 가 보여준 자리에서 작업자가 뺐고, Cin7 이 그 자리에서 차감했다.**
📌 줄 수도 맞는다: `SO-15482`(234) + `SO-15483`(46) = 280 = `TR-04330`(168) + `TR-04331`(112).

### 연결 고리 — 트랜스퍼 `Reference`

```
TR-04173  "P3_(SO-15071)"                              → SO-15071
TR-04174  "P1_(SO-15070-1,2,3,4,5,6,7)"                → SO-15070   ⚠️ 한 SO 가
TR-04175  "P2_(SO-15070-8,9,10,11,12)"                 → SO-15070      두 트랜스퍼로
TR-04330  "P1_(SO-15482-1,2,3,4,5,6,8)"                → SO-15482
TR-04331  "P2_(SO-15482-7,9,10,11,12 / SO-15834-1,2,3)"→ SO-15482 · SO-15834
```

⚠️⚠️ **`Reference` 는 사람이 손으로 넣는다. 자동으로 붙지 않는다.**
📌 **파트 번호(`-1,2,3`)는 무시한다** — bin 은 SO 라인당 하나라 어느 팔레트로 갔든 같다.

## 5. 참고 — 규칙 재현(추정)도 검증했다

「그 SKU 가 있던 단일 bin 에서 뺐을 것」이라는 추정도 함께 쟀다.

```
토론토 재고 SKU 7,447개 중  단일 bin 7,437 (99.87%) · 2개 bin 10
TR-04331 (사흘 차)   정답 112 · 오답 0 · 침묵 0
TR-04173 (열흘 차)   오늘 스냅샷 정답 63 · 오답 0 · 침묵 1
                     기초 스냅샷 정답 64 · 오답 0 · 침묵 0
                                              합계 176/176 · **오답 0**
시뮬레이션: 토론토 어긋남 1,201 → 188 · 격차 15,640 → 1,171 (93% 해소)
```

⭐ **성질이 좋다 — 규칙은 틀리지 않고 가끔 침묵할 뿐이다.**
📌 그래도 **채택하지 않았다.** §4 의 WMS 값이 **사실**이고, 추정은 다중 bin SKU 에서 침묵한다.
⚠️ 다만 **폴백으로 남겨둘 값은 있다** — 기록해 둔다.

## 6. 구현 (커밋 `45c833e` · `cc27031` · `inv-collect@2026-08-31.4`)

### 6-a. 해결 규칙

```
대상 = 창고 간 이동의 출발 다리 && 출발이 WMS_PICK_WAREHOUSE(토론토) && 헤더 bin 없음
  1. Reference 에서 /SO-\d+/g 를 **전부** 파싱
  2. wms_orders(order_number) → wms_order_lines(base_sku → bin_location)
  3. 라인 sku 로 조회해 채운다
못 찾으면 → bin='' 유지 + 사유별 카운트   ← ⚠️ 안전한 실패
```

⚠️⚠️ **「손님 이름 + 날짜」 폴백을 만들지 않았다.** 잘못 이으면 **틀린 bin 이 그럴듯하게**
들어가고, 그것은 비어 있는 것보다 나쁘다(같은 날 오전 이중 차감 522행의 교훈).
⭐ **그 판단이 곧 검증됐다** — §7 의 오타 사건.

⚠️ **여러 SO 에서 같은 SKU 의 bin 이 갈리면 비운다**(하나로 정할 근거가 없다).
⚠️ **1,000행 캡에 닿으면 해결을 통째로 끈다** — 잘린 맵으로 채우면 틀린 판정이 된다.
⚠️ **조회 실패는 해결만 끄고 수집은 계속**한다(오늘 네 번 쓴 원칙).

### 6-b. 미해결 사유 3분류 — ⚠️ 섞으면 「사람이 빠뜨린 것」이 안 보인다

| | |
|---|---|
| `transfer_bin_no_reference` | ⭐ **매니저가 Reference 를 빠뜨렸다 — 진짜 신호** |
| `transfer_bin_no_source` | 역방향(에드먼튼→토론토) — 픽용 SO 가 **구조적으로 없다**. 대부분 잘못 보낸 수량을 되돌리는 조정 성격이다(Caleb 확인) · [실측] 관측 0건 |
| `transfer_bin_so_missing` | Reference 의 SO 가 `wms_orders` 에 없다 |
| `transfer_bin_skip_same_warehouse` | 같은 창고 안 이동 — 대상이 아니다 |

⚠️ **역방향은 `unresolved` 에도 안 센다** — 「Reference 를 채워라」가 무의미하고
에드먼튼 출발 `bin=''` 는 정상 모양이다.
⭐ **방어 한 겹**: 역방향 문서에 SO 가 어쩌다 붙어 있어도 **채우지 않는다** —
`wms_order_lines` 의 bin 은 **토론토 픽 bin** 이라 에드먼튼 출발에 넣으면 틀린 bin 이 된다.

### 6-c. ⚠️ 「내부 풋어웨이」 함정 — 처음엔 소음으로 잡혔다

`TR-04260`~`04264` 가 `no_reference` 로 잡혔는데, **우리 WMS 가 API 로 만든 문서**였다.

```
Reference  "WMS putaway TR-03976"
User       "Data Management (API Application)"
From "Asung - Edmonton"  →  To "Asung - Edmonton: EG020102"
```

⇒ 픽이 아니라 **SO 가 없는 것이 정상**이고, 도착 bin 은 헤더 `To` 에서 이미 읽는다.
출발 `bin=''` 도 정상이다 — **에드먼튼 도착 대기 자리에는 bin 이 없다**
(에드먼튼 bin 대조가 6,478칸 중 12칸만 어긋난 이유).

📌 **`Reference` 가 `"WMS putaway …"` 로 시작하면 우리가 만든 문서다.** 다음 사람이 SO 를
찾다가 헤맬 자리라 코드 주석에 박았다.

⚠️ 창고 비교는 **`resolveLoc` 가 GUID 로 푼 `warehouse`** 로 한다 — 콜론 파싱은 이 파일의
**확립된 금지 관례**다(「창고 판정은 문자열 파싱 금지 — 이름이 바뀌면 조용히 깨진다」).

### 6-d. ⭐ 소멸 감지 `bin 변경` 예외 — 스킬 경고의 처방

유니크 키의 bin 이 바뀌면 **옛 행이 매 회차 「사라짐」으로 검출**돼 회차 캡 500 을 소진하고
**진짜 소멸을 가린다.** ⚠️ 상쇄로도 안 없어진다 — 옛 `cin7` 행은 B 집합에 그대로 남는다.

```
partitionBinChanged: B−A 후보 중 **bin 만 다른 6키**
  (doc_type · doc_number · line_ref · event_type · warehouse · sku)가 A 에 있으면
  → 소멸이 아니라 missing_lines_bin_changed 로 카운트만. **캡보다 앞에서 거른다.**
```

⚠️ **`event_type` 까지 일치를 요구해야** IN_TRANSIT 다리(같은 `line_ref`·`sku`)가 창고 다리를
면책하는 오판이 **구조적으로 불가능**하다.
📌 스킬의 **「키 변경 시 소멸 감지가 원장 전체를 삭제됨으로 잡는다」** 경고의 처방이다.
앞으로의 어떤 bin 규칙 변경에도 이 예외가 방어한다.
⚠️ 다만 **`line_ref`·`sku`·`warehouse` 가 바뀌면 여전히 마이그레이션이 필요하다.**

### 6-e. ⚠️ 결합 — 잠정 조치임을 명시

**원장이 WMS 테이블을 읽는다.** `ims-principles` 원칙 2(접점은 사건을 남긴다)와 어긋난다.

```
· 읽기 전용 · 같은 Supabase · WMS 스키마 변경에 취약하다
· ⭐ 목표는 **WMS 픽이 원장에 사건을 남기는 것**이다. 그때 이 조회는 사라진다
· 그리고 Reference 라는 다리 자체가 「트랜스퍼 → 가짜 SO → 픽 → VOID」 우회 때문에 있다.
  WMS 가 트랜스퍼를 직접 픽하면 다리도 사라진다
```

### 6-f. 보정 도구 `scripts/fix-transfer-bins.mjs`

⚠️ **자가 치유가 안 된다** — Reference 를 나중에 채워도 옛 `bin=''` 행이 남아 이중 계상된다.

```
① 대상 조회 → ② 같은 함수로 해결 → ③ 계획 출력(--commit 없으면 여기서 끝)
④ 상쇄(:binfix) → ⑤ 재삽입(:binfixed) ⚠️ **조건부**
```

⚠️ **⑤가 조건부인 이유**(Claude Code 판단): 대상 5문서는 IN TRANSIT = 커서 위라 **매 회차
재수집된다.** 배포 후 수집기가 올바른 bin 의 `cin7` 행을 이미 쓰므로, 그 위에 `manual` 행까지
넣으면 **이중 계상**이다. ⇒ 같은 키의 `cin7` 행이 실재하면 **④만** 한다.
📌 **권장 순서: 배포 → 한 회차 대기 → 보정 도구.**
⚠️ Reference 가 원장 `raw` 에 없어 문서당 Cin7 1콜을 읽는다(`doc_task_id` → `/stockTransfer`).

```
[실측 계획 모드 1차]
  상쇄만        592   = transfer_bin_resolved 592 와 일치   (살아 있는 라인)
  상쇄 + 재삽입 138   ⚠️ 08-25 에 삭제된 라인 — **이미 :reversal 로 상쇄돼 있다**
  대상 문서     141   ⚠️ 5개가 아니다 — 내부 풋어웨이가 다수 섞였다
```

⚠️ 도구는 **`:binfix` 접미만** 확인했다. `TR-04175` 라인 소멸 실사고(08-25)의 상쇄 행은
`:reversal` 이라 **안 보였다.**

```
원본       −Q  (bin='')
reversal   +Q  (bin='')   ← 08-25 · 합 0 ✅
binfix     +Q  (bin='')   ⚠️ 중복 상쇄
binfixed   −Q  (bin=F…)   ⚠️ 삭제된 라인을 되살린다
⇒ bin='' 에 +Q 유령 · 실제 bin 에 −Q 허위 차감
```

📌 **판별 신호가 계획 출력에 이미 있었다** — 「상쇄만」은 수집기가 새 bin 행을 쓴
**살아 있는 라인**이고, **「상쇄 + 재삽입」이 삭제된 라인**이다. 그 수가 정확히 138이었다.

### 수정 (커밋 `2561fa8`)

- **재실행 안전을 접미 무관으로**: 같은 원본에 `source='manual'` 행이 **하나라도** 있으면
  건너뛴다(`:reversal`·`:binfix`·`:binfixed` 무관) · `skip_already_reversed` 로 행마다 표시
  ⭐ **키에서 `event_type` 을 뺐다**(Claude Code 판단) — 상쇄 행의 `event_type` 관례가
  문서마다 갈려 확정할 수 없었다. `warehouse` 가 키에 있어 IN_TRANSIT 다리 면책은 막힌다
- **대상을 창고 간 이동으로** — EF 의 `isCrossWarehouseTransfer` 를 **원문 추출**(로직 두 벌 금지)
  ⚠️ `ref/location` 이 잘리면 **중단**한다 — 잘린 맵은 창고 간 문서를 「같은 창고」로 오판해
  **조용히 제외**한다
