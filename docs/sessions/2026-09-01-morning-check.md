## 2. ⚠️ bin 대조는 **아침에만** 유효하다

같은 날 세 번 쟀는데 값이 딴판이었다.

```
아침 08시 (필터 없음)   토론토   9칸 ·  52    ⭐ 이것이 맞는 값
오후    (필터 없음)     토론토 128칸 · 532
오후    (occurred_on 필터) 토론토  49칸 · 228
```

**원인**: 스냅샷은 **01:21 의 한순간**인데 원장은 **그 뒤로 계속 쌓인다.**
⇒ 낮 판매가 전부 「원장이 과하게 뺐다」로 잡힌다.

⚠️ **`occurred_on < 오늘` 필터는 답이 아니다** — 01:21 스냅샷은 그날 00:00~01:21 사건을
이미 포함하는데 필터가 그것까지 빼버린다. **날짜 단위 필터로는 순간을 맞출 수 없다.**

📌 **판정 근거**: 이번 보정과 무관한 **에드먼튼도 12 → 359 로 같이 늘었다.** 드리프트의 증거다.

⇒ ⑧은 **아침 점검에서만** 돌린다. 오후에 재고 「망가졌다」고 오해하지 말 것.

## 3. 기초 스냅샷 경계 오더가 **또** 들어왔다

`ANN01111` 이 **재고 −4**(음수)로 나왔다. 원장 행이 **단 하나**였다.

```
SO-15039 · 8/21 · −24 · ⚠️ 8/31 15:29 수집
기초 스냅샷(8/20 19:42) 토론토 B030902 = 20  ← 이미 출하가 반영된 값
20 − 24 = −4
```

⇒ **8/20 저녁에 출하 승인된 오더**인데 `ShipmentDate` 가 8/21 이라 `since` 필터를 통과했다.
**08-30 에 상쇄한 `SO-14974`·`15033`·`15038`·`15041` 과 같은 부류**다.

📌 **말씀하신 44 는 출하 직전 값**이었다. 스냅샷은 그 뒤(20)를 찍었다.

### 전수 — 세 문서가 더 있었다

```
SO-14975     2행    −9      8/31 15:29 수집
SO-15039   118행  −1,120    8/31 15:29
SO-15042    37행    −318    8/31 15:04
           ─────  ──────
            157행  −1,447     vs 대조의 ledger_low −1,475
```

⚠️ 판정 근거는 **「8/21에 수집 안 됐다」** 하나다 — 그때 `Updated` 가 8/20 이었다는 뜻이고,
곧 **모든 활동이 8/20 에 끝났다**는 뜻이다.
✅ **157/157 이 대조의 ledger-low 목록에 있었다.** 상쇄 후 `ANN01111` 델타 0(= 기초 20) 확인.

### ⭐ 왜 8/31 오후에 들어왔나 — Cin7 이 또 대량 갱신했다

```
8/31 13:25(토론토)부터
  updated_ties   0 → 46 → 64 → 25 → 33
  candidates     0 → 47 → 66 → 27 → 33
  cursor         …Z → …Z|SO-15339 → …Z|SO-15067
```

⇒ **8/28 에 이어 사흘 만이다.** 그 갱신이 경계 오더를 다시 끌어올렸다.

⭐ **그리고 tie-breaker 가 실제로 작동했다** — 커서에 `|SO-…` 가 붙어 전진했다.
**08-30 에 안 고쳤으면 그날 오후에 또 동결됐다.**

### 방어 — 아침 점검 ⑨

```sql
select l.doc_number, count(*) as rows, sum(l.qty_delta) as qty,
       min(l.created_at at time zone 'America/Toronto') as first_collected
from inv_ledger l
where l.doc_type='sale' and l.source='cin7' and l.occurred_on='2026-08-21'
group by l.doc_number
having min(l.created_at) >= '2026-08-22'
   and not exists (
     select 1 from inv_ledger m
     where m.source='manual' and m.doc_number = l.doc_number
       and m.occurred_on = '2026-08-21'
   )
order by 1;
```

**0행이면 정상.** 뜨면 또 들어온 것이다.
📌 경계 오더는 **유한한 집합**(8/20 승인분)이라 다 나오면 끝난다.

## 4. ⚠️⚠️ 「수집 후 취소」를 아무도 안 본다 — 구조적 구멍

`UNF18050`~`53` 네 SKU 가 각 −6 어긋났다. 조립 세 건을 파다가 나왔다.

```
FG-00129  VOIDED     8/24   ← 원장에 없다 (수집 때 이미 취소였다)
FG-00130  COMPLETED  8/24   ← 원장 −6  ✅
FG-00131  ⚠️ VOIDED  8/28   ← 원장 −6  **취소를 못 봤다**
FG-00132  COMPLETED  8/28   ← 원장 −6  ✅
```

**검산이 정확히 맞는다**: `UNF18050` 기초 84(8/20) − 우리 18 = 66, 그런데 Cin7 은 72.
**한 건 몫(6)이 딱 남는다.** 상쇄 후 델타 −12 ⇒ 84 − 12 = 72 ✅

### 원인

```
1112행   수집 시 VOIDED 는 제외한다 (skip_voided)   ✅
그런데   **이미 들어온 문서가 나중에 VOIDED 로 바뀌면 아무것도 안 한다**
```

⚠️ `raw.header.status` 의 `COMPLETED` 는 **수집 당시(8/28 13:13) 값**이다. 그 뒤의 취소는
어디에도 안 남는다.

### ⭐ VOID 의 정체 — 업무상 취소가 아니다

```
SO 묶음  취소+완료 공존 30 · 취소만 12 · 완료만 6
```

거의 모든 SO 가 **「VOIDED 몇 건 → COMPLETED」** 형태다. **기제 둘이 확인됐다:**

**① SO 편집 → 재생성.** SO 를 고치면 Cin7 이 기존 자동조립을 VOID 하고 새로 만든다.
`Notes` 가 **`by System`** 인 것이 증거다.
```
SO-15502   FG-00131 VOIDED  →  FG-00132 COMPLETED   (같은 날 · 같은 제품 UNF18261)
SO-15205   FG-00129 VOIDED  →  FG-00130 COMPLETED
```

**② 트랜스퍼 픽용 SO 를 VOID.** [실증 `SO-14692`] `wms_orders` 에 **`ASUNG EDM TRANSFER` ·
8/13 · 66줄**로 실재한다. 픽이 끝나면 SO 를 VOID 하는 그 흐름이고, 딸린 자동조립
`FG-00115~00120` **6건이 전부 VOID** 됐다. ⇒ **설계된 동작**이다.

### ⚠️ 빈도 — 「65% 니까 최우선」은 과대 해석이었다

```
2025-10   완료  0 · 취소 16   100%   ⭐ 완료 0건 — 이관 초기
2026-03~  완료 38 · 취소 60    61%   ⚠️ 최근도 꾸준하다(위 기제 때문)
2026-08   완료 10 · 취소 12    55%
```

⚠️ **비율이 아니라 모수를 봐야 한다** — 조립은 **월 20건 안팎의 드문 작업**이다(Caleb 확인).

### ⭐⭐ 우리가 걸리는 조건은 좁다

```
FG-00131  수집 8/28 13:13   →   FG-00132  수집 8/28 16:13
          그 3시간 사이에 SO-15502 가 편집됐다
```

⇒ **수집 주기(1시간) 안에 상태 변화가 안 끝날 때만** 걸린다.
📌 **8월 VOID 12건 중 잡힌 것은 `FG-00131` 하나**다.

⚠️ **다만 기제 ②는 창이 길다** — 픽 시작과 SO VOID 사이가 **몇 시간~며칠**이라 그 사이에
수집이 들어간다. **트랜스퍼 픽은 정기적이므로 ①보다 잘 걸릴 수 있다.**
📌 `SO-14692`(8/13)는 기초 스냅샷 이전이라 원장에 없었을 뿐이다 — **다음 트랜스퍼부터가 대상.**

⚠️ **그래도 구멍은 실재한다.** 그리고 전 축 공통이다 — 다만 **판매·트랜스퍼는 사람이 Void 할
때뿐**이라 조립(Cin7 이 자동으로 VOID)과 성격이 다르다.

📌 **소멸 감지(`inv_missing_lines`)는 라인 삭제만 잡는다.** 문서 전체 취소는 **다른 축**이다.

### ⬜ 처방 (미착수)

- 감지: 원장에 있는 문서 중 Cin7 에서 `VOIDED` 로 바뀐 것을 찾는다
  ⚠️ **API 를 봐야 해서 SQL 로는 안 된다** — EF 작업이다
- 조립은 목록(`finishedGoodsList`)에 `Status` 가 있어 **상세 없이도 판정 가능**하다
- 상쇄: 소멸 감지와 같은 방식(`:voided` 접미 · `source='manual'`)
- ⚠️ 어느 축부터 볼지, 얼마나 거슬러 볼지는 미정

## 5. 트랜스퍼 출발 bin — 잔고 규칙으로 바꿨다 (커밋 `90af1b6`)

### ⚠️ 어제 방식의 한계가 실물로 드러났다 — `SKL01861`

```
8/20 18:50   SO-15071 유입 → wms_order_lines.bin_location = D110302
8/21 10:27   ⭐ TR-04169 : D110302 → D110301 (픽커의 wrong_location 신고 → 매니저 정정)
8/21 14:52   TR-04174 픽 — Cin7 은 **D110301** 에서 뺐다
8/31         원장이 유입 시점 값 D110302 를 채웠다   ⚠️ 두 칸이 동시에 어긋남
```

📌 **신고 경로가 잘 작동해서 생긴 어긋남**이다. 고장이 아니라 **정정이 픽보다 먼저 끝나서**
값이 갈렸다.

### ⚠️ WMS 에서 더 얻을 것이 없다 — WMS 세션이 코드로 확정

```
픽 화면은 wms_order_lines 를 진입 시 한 번 읽고 끝까지 쓴다 (렌더 재조회는 수량만)
sticky 는 05:00 배치라 **당일 정정을 모른다**
⇒ 세 경로(화면 · bin_location · sticky)가 전부 같은 낡은 값
```

⇒ 「화면 값 저장」은 **원장이 이미 아는 값의 복사**이고, sticky 저장은 **「집은 자리」 보증이 없다.**

### ⭐ 관점 정정 — 재현할 것은 「Cin7 의 bin 기록」이다

「작업자가 간 자리」가 아니다. **Cin7 은 자기 기록대로 뺀다.** `TR-04169` 뒤 Cin7 의 기록은
`D110301` 이었다. 그리고 **원장은 그 이동을 이미 갖고 있다.**
⇒ **WMS 를 한 줄도 안 고치고 잡는다.**

### 처방 — 잔고 우선 + WMS 교차

```
① 그 시점 bin 잔고 = 기초 스냅샷 + occurred_on 이하 델타 (⚠️ 자기 문서 제외)
② 잔고가 **정확히 한 칸**  →  그 칸 (+wms_stale 보고)
③ 여러 칸  →  WMS 값이 그중 하나면 그것, 아니면 비움 (+ambiguous)
④ 0칸  →  WMS 폴백      ⑤ 그래도 없으면 비움
```

⚠️ **알려진 한계**: 같은 날 안의 순서를 못 가린다(`TR-04169` 10:27 · `TR-04174` 14:52 가
둘 다 `occurred_on = 8/21`). 자기 문서만 빼면 이번 건은 맞지만, **같은 날 여러 트랜스퍼가
같은 SKU 를 건드리면 서로를 못 가린다.** ⇒ **유일할 때만 확정**하고 애매하면 비운다.

⚠️ 1,000행 캡에 닿으면 규칙을 끈다(잘린 잔고로 판정하면 틀린다).
⚠️ 실패는 WMS 폴백 + `balance_off` 보고 — 진단이 수집을 막지 않는다(여섯 번째).

### ✅ 실물 결과

```
transfer_bin_resolved      592 → 596        ⭐ unresolved 4 → 0
transfer_bin_by_balance    588 · by_wms 8
transfer_bin_wms_stale     [SKL01861]       ⭐ 정확히 그 한 건
transfer_bin_ambiguous     [] · balance_off null
```

⇒ **이 부류의 빈도가 측정됐다 — 596건 중 1건.**
⇒ 그리고 **잔고 규칙을 WMS 맵 없는 문서에도 적용**했더니(Claude Code 판단)
`no_reference`·`so_missing` 부류가 자동 해결됐다 — 어제 손으로 고친 4줄이 그 대상이었다.

### ⚠️ 배포 직후의 함정 — `:binfixed` 와 `cin7` 행이 겹친다

어제 손으로 넣은 `:binfixed` 행과 수집기가 이제 쓸 `cin7` 행은 **`line_ref` 가 달라
유니크 키가 막지 못한다** ⇒ 같은 bin 에 −2Q.
⇒ `:superseded` 로 손으로 넣은 4행을 상쇄해 **자리를 비워줬다.** 그 뒤 수집기가 정확히 채웠다.

📌 **`SKL01861` 은 재삽입이 필요 없었다** — 잔고 규칙이 스스로 `D110301` 을 썼다.
손으로 한 것은 **틀린 값 지우기 하나**뿐이다.

## 8. 📌 오늘의 교훈

**아침 점검이 세 가지를 잡았다.** 어제 만든 ⑦(수집 회차)이 첫날부터 일했고, ⑧(bin 대조)이
1,201 → 9 를 보여줬으며, 음수 재고 하나(`ANN01111`)를 당기니 **157행짜리 이중 차감**과
**「수집 후 취소」 구조적 구멍**이 딸려 나왔다.
⚠️ 다만 그 구멍의 **크기는 처음에 과대 평가했다** — 「65%」는 Cin7 의 기계적 VOID 를 센 것이고,
실제로 우리가 걸린 것은 8월 12건 중 1건이다(§4). **비율이 아니라 모수와 기제를 봐야 했다.**

⚠️ 그리고 **측정 자체가 함정일 수 있다**(§2). 같은 날 같은 쿼리가 9 · 49 · 128 을 냈다.
**언제 재느냐가 무엇을 재느냐만큼 중요하다.**
