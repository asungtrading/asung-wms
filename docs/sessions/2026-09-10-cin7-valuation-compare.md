## 0. 먼저 — 재복사를 했다 (모든 숫자의 전제)

절차(§테스트 DB + 비우는 단계 ②′)대로 재복사했다. **⭐ 절차에 한 단계가 늘었다:**

```
① 운영에서 덤프 (--linked · 읽기만)
②′ 테스트에서 덤프 대상 표 truncate ... cascade
③ 테스트에 복원
③′ ⬜ supabase db push --db-url  ← ⚠️ 이번엔 「up to date」라 건너뛰었다(§3 (나))
④ inv_layer_seed_baseline → inv_layer_apply
```

⚠️⚠️ **문서의 「`inv_layer` 계열은 운영에 없으므로 덤프에 안 들어온다」가 더 이상 맞지 않다.**
오늘 낮 운영에 표가 생겨서 **덤프 표가 31개 → 35개**가 되었다(늘어난 넷: `inv_doc_cost`·`inv_layer`·`inv_layer_consume`·`inv_layer_cost_add`).
⭐ 결과는 같다 — 운영 것이 0행이라 **빈 `COPY` 가 덮고 ④에서 다시 만든다.** 📌 `pg_dump` 순환 FK 경고에 `inv_layer` 가 추가된다(`wms_pallets` 와 같은 성격 · 무해).

⚠️⚠️ **`seed_baseline(key, true)` 로는 덮어쓸 수 없다** — 소진 기록이 있으면 거부한다:
```
ERROR: refusing to replace baseline: 5364 layer(s) have consume rows ...
```
⇒ ⭐ **재생성은 `truncate inv_layer, inv_layer_consume, inv_layer_cost_add cascade;` 먼저.**
📌 `inv_layer_apply_reset_done()` 은 **임시 테이블(`on commit drop`)** 이라 `psql -c` 한 줄로는 아무 효과가 없다 — 처리 이력은 DB 에 남지 않고 `apply` 는 매번 처음부터 훑는다.

### 0-b. ⭐ 운송비가 처음으로 레이어에 얹혔다 (대조의 또 하나의 전제)

`inv_layer_apply('2026-09-09')` · 7.5초.

⭐ 검산: **807.64 + 627.95 = 1,435.59 = `inv_doc_cost` 5행 합계** — 전액이 설명된다.
⚠️⚠️ **`freight_no_basis` 실물 비중 43.7%**(⏸ 표본 둘뿐이라 몰랐던 값). 버려진 둘 `TR-03975`(398.75)·`TR-03976`(229.20)은 둘 다 **8/14 출발 · 8/26 완료 — 기초선(8/20)을 가로지른다.** 8/20 에 물건은 이미 창고를 떠나 있었다 ⇒ 출발지 레이어 없음 ⇒ 도착 사건만 원장에 들어와 **원가 미상 레이어**. [실측] `cost_source='unknown'` · `unit_cost=0` · 144+115 = 259개 레이어 · 1,550+1,009 = **2,559개** = `transfer_unknown_qty 2559` 와 정확히 일치.
⇒ ⭐ **결함이 아니라 기초선을 가로지르는 구조적 그림자다. 재기준선이 지운다.**
⚠️ 다만 `unit_cost` 가 **null 이 아니라 0** 이다 — 「모르면 비워둔다」·`fx_rate ?? 0` 교훈에 비추면 null 자리. 지금은 `cost_source='unknown'` 과 카운터가 창구지만 `sum(unit_cost*qty)` 를 그대로 쓰는 새 코드가 생기면 조용히 틀린다 ⇒ ⬜ 파생 항목.

## 3. ⚠️ 오늘 밤 내가 만든 것 (앵커에 세지 말 것)

**(가) 「토론토 −0.13% 면 예상 범위」라고 판단했다.** 절대합을 보고 뒤집혔다 — 65,710 vs 3,587.
⇒ ⭐ **대조에서 순액만 보고 판정하지 않는다.**

**(나) 「테스트에는 `session_guard` 마이그레이션이 없을 것」을 확인 없이 받아들였다.** 확인 쿼리를 먼저 드려놓고 건너뛴 채 절차를 짰다. 실제로는 **이미 적용돼 있었다**(`db push` 「up to date」). 손해는 없었으나 같은 패턴이 절차를 틀어지게 한다.

**(다) 원인 추적이 「Cin7 문서 하나씩 열어보기」로 흘렀다.** 8/29 하락의 범인을 찾으려 PO 를 차례로 열었고 셋 다 날짜가 안 맞았다. **낮의 `recheck_since` 시각 밀기와 같은 모양**(특정 사건에 닿으려고 후보를 흔든다). Caleb 이 「마무리하자」로 끊었다.
⇒ ⭐ **원인 규명은 「지문으로 집단을 가르기」가 먼저다** — 실제로 그렇게 229개로 좁혔고, 그 뒤 개별 추적으로 넘어갔어야 했다.

**(라) 컬럼 이름을 세 번 추측해 오류를 냈다**(`snapshot_date`·`qty`·`doc_type`). ⇒ ⭐ `information_schema.columns` 를 먼저 본다(WMS 규칙 29 계열 · 스킬 함정 표에 진실 기록).

**(마) 원인 순서를 거꾸로 잡았다.** 단가 2배를 보고 **Cin7 재평가부터** 의심했다. 정본은 「① 내 쿼리 ② 미처리 사건 ③ 데이터」 — 우리 쪽을 먼저 봐야 했다(결과적으로 Cin7 쪽이 맞았지만 순서는 틀렸다).
