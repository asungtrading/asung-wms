## 1. ⚠️⚠️ 오늘 최대 발견 — `⟳ Stock` 체인이 12일 이상 죽어 있었다

### 실측

`wms_refresh_requests` 최근 5건이 **전부** 같은 에러로 `status='error'`:

```
Exception: This script has too many triggers.

8/20 22:37  Changmo Ku
8/21 17:03  Changmo Ku
8/24 15:51  Changmo Ku
9/1  20:49  Caleb
9/1  20:58  Caleb
```

⚠️ **최근 5건만 봤다** — 그 이전은 확인 못 함. 「12일 **이상**」인 이유다.

### 구조 — 왜 반쪽만 죽나

버튼은 아무 일도 하지 않는다. `wms_refresh_requests` 에 **행 하나를 넣을 뿐**이고
(`admin.html:343~364` — insert 후 15초 간격으로 그 행의 `status` 를 폴링),
실제 작업은 GAS 1분 폴러가 집어가는 **2단 체인**이다
(`~/asung/gas-system-automation/Wmsstockrefresh.js`):

```
sr_pollRefreshRequests_()          1분 폴링 트리거
  ├ pending 1건 선점 (pending → running)
  ├ ① runBinStockSync()            Cin7 → BQ asung_bin_stock      ← 성공
  └ sr_installStep2_()             ⚠️ ScriptApp.newTrigger(...).create()
                                      → "too many triggers" throw
       catch → status='error'

sr_step2_()                        ② runWmsMasterSync() (BQ → Supabase)
                                   ⚠️ 아예 실행되지 않는다 — 트리거가 안 생겼으므로
```

⭐ **①과 ②를 나눈 것은 옳은 설계다**(GAS 6분 실행 제한 — 파일 헤더 주석에 명시).
문제는 **그 이음새가 「트리거 생성」이라는 유한 자원**이라는 것이다. GAS 트리거 20/20 한도에
걸리면 ①은 이미 성공한 뒤라 되돌릴 수 없고, ②는 시작조차 못 한다.

### ⚠️ 정확히 하자 — 무엇이 죽었고 무엇이 살아 있었나

이 구분이 앵커 판단(아래)과 피해 산정 모두에 걸린다.

| | 상태 |
|---|---|
| 매일 06:30 정기 배치 (`setupWmsSyncTrigger` · WmsSync.js:216) | ✅ **살아 있었다** — 이미 설치된 트리거라 한도와 무관 |
| `⟳ Stock` 온디맨드 갱신 | ❌ **12일 이상 죽어 있었다** — 매번 트리거를 **새로 만들어야** 한다 |

⇒ 재고 데이터가 「12일 낡은」 것이 아니다. **매일 아침 갱신됐고, 「지금 갱신해줘」만 안 됐다.**
그래서 남는 상태가 이것이다:

```
BigQuery   최신 (21:07)          ← ①이 성공했으므로
Supabase   ⚠️ 그날 06:30 값 그대로  ← ②가 안 돌았으므로
```

⚠️⚠️ **그 어중간한 상태가 어디에도 표시되지 않는다.** 버튼을 누른 사람은 실패 토스트를
보지만 **탭을 닫았으면 그것도 못 본다**(15초 폴링이라 화면이 살아 있어야 한다).
「BQ 만 최신」이라는 사실은 **아무 화면에도 안 뜬다.**

### 📌 왜 12일간 아무도 신고하지 않았나 — 날짜가 말해준다

[실측] Changmo Ku 가 **8/20 · 8/21 · 8/24 세 번** 누르고, 그 뒤 **8일간 아무도 안 눌렀다.**

📌 **추론**(날짜는 실측, 해석은 추론): 세 번 눌러 세 번 다 안 되면 사람은 **신고하는 대신
그 도구를 그만 쓴다.** 「신고가 없었다」를 「문제가 없었다」로 읽으면 안 된다 —
**도구를 포기한 것일 수 있다.**

⇒ 이 레포가 이미 두 번 적어둔 원리의 세 번째 판이다:
「무시되는 경고는 없는 것과 같다」(규칙 43 unack 축) ·

### 발견 경위 — 8줄을 파고들어서야 드러났다

## 4. 원장 요청 3건 처리

| 요청 | 결론 |
|---|---|
| 픽 시점 자리(bin) 저장 | ❌ **WMS 무접촉** — 저장할 값이 없다 |
| 재고 이상 화면 | 조건 셋 제시 → 원장이 전부 처리 |
| 재고 마스터 착수 | ⬜ 1단계(조회) 조사·설계 완료 — **구현은 다음 세션** |

### ⚠️ 첫 번째 — 「요청받은 것을 안 하기로」 했으므로 근거가 남아야 한다

화면이 보여주는 bin 은 **유입 시점 값**이고, sticky 는 **05:00 배치**라 당일 정정을 모른다.
⇒ **세 경로가 전부 같은 낡은 값을 준다** — WMS 가 「픽한 자리」라고 저장해도 그것은
**실제로 집은 자리가 아니라 아침에 추천한 자리**다. 틀린 값을 원장에 흘려보내는 쪽이 더 나쁘다.
⇒ 원장 자체 보정(V5)을 권고했다. 별도 답신 문서가 정본.

### 두 번째·세 번째 — 범위가 커졌다

조건 셋(**뷰 계약** · **「매일 빨간불」** · **시간 축**)을 원장이 전부 처리했고,
그 과정에서 대상이 **「어긋난 9칸」에서 「전체 8,060 SKU · 14,432칸」**으로 커졌다.

⇒ **1·2단계로 나눴다**: 1 = 조회(목록·검색·필터·페이징·카드·「○시 기준」) /
2 = 쓰기(`inv_ack_diff` 확인 · `inv_bin_notes` 코멘트).
**나눈 이유**: 1단계만으로 원래 목적(매일 아침 Caleb 이 SQL 을 직접 돌리는 것을 없앤다)이
달성되고, 2단계는 **WMS 가 원장 테이블에 쓰는 첫 사례**라 성격이 다르다.

⚠️⚠️ **2단계를 오래 미루지 않는다** — 「확인」이 없으면 카드 숫자가 안 줄어 **「매일 빨간불」**
문제가 그대로 남는다. `unack` 축이 그것 때문에 생겼다.
⇒ 1단계 설계에 **2단계가 붙을 자리를 비워두는** 것(Ack 열·행 키)을 포함시켰다.
