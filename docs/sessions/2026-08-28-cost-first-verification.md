## 2. ⭐ 아침 점검 ⑥ — 원가가 빠진 입고

경고 장치를 정교화하려다 **더 단순한 답**을 찾았다.

```sql
select l.doc_number, min(l.occurred_on) as received,
       count(*) as ledger_rows, sum(l.qty_delta) as qty
from inv_ledger l
left join inv_cost c
  on  c.doc_number = l.doc_number and c.line_ref = l.line_ref
  and c.sku = l.sku and c.bin = l.bin and c.warehouse = l.warehouse
where l.doc_type = 'purchase' and l.source = 'cin7'
  and l.occurred_on > '2026-08-20'
  and c.id is null
group by l.doc_number order by 2;
```

📌 **이유를 묻지 않는다.** Simple 이든 · 상세 캡에 걸렸든 · 자기검증에 막혔든 ·
우리가 모르는 이유든 — **「재고는 들어왔는데 원가가 없다」는 결과 하나로 잡는다.**
어제 원장 조인 47/47 을 확인한 쿼리의 반대 방향이다.

⚠️ **경고를 정교화하지 않기로 한 이유**:
- EF 경고(`skip_simple_unverified` 13~27건)는 **대부분 아직 안 받은 오더**라 노이즈다.
  매번 뜨는 경고는 아무도 안 본다.
- WMS 에 띄우는 것은 성격이 안 맞는다 — **창고 작업자는 PO 유형을 정하지 않는다**
  (`ims-principles` 원칙 2: 남의 모듈에 남의 일을 넣지 않는다).
- 별도 테이블은 **연 2건 나는 사건**에 과하다.
- ⇒ **아침 점검 쿼리가 이미 그 자리**다. 매일 도는 것에 한 줄을 더한다.

📌 **해결하면 저절로 사라지는 목록**이다. 닫거나 끌 장치가 필요 없다.

⚠️ **⑥이 신뢰를 가지려면 `inv-cost` 가 자동으로 돌아야 한다** — 안 돌면 「원가 누락」인지
「수집 안 함」인지 구별이 안 된다. ⇒ 그래서 오늘 cron 을 등록했다(§5).

## 3. ⭐ 자가 치유 — Simple/Advanced 예외가 시스템을 깨지 않는다

### 발단

[실측] 4년치 1,231건 중 **Simple 인 채로 입고 완료된 것 7건**:
```
PO-01133  order 2026-08-11 · upd 2026-08-27   ← 기초 스냅샷 이후 · 실제 구멍
PO-00893 · PO-00874 · PO-00583 · PO-00229 · PO-00081 · PO-00080   (스냅샷 이전 · 무해)
```

**실무 관행**: 대부분을 Advanced 로 넘긴다(Simple 로는 다 담을 수 없어 자연스럽게 전환).
⚠️ 그러나 **관행이지 규칙이 아니다** — `PO-01133` 은 Simple 로 마무리해도 되는 오더였다.
⇒ **예외는 앞으로도 생긴다.**

### 그런데 스스로 낫는다

📌 **Cin7 은 Simple 로 완료된 뒤에도 Advanced 로 Convert 할 수 있다.**
⇒ 「Simple 로 완료됨」은 **영구 상태가 아니다.** 경고할 필요가 없다.

**[실측 2026-08-28] 고리가 3초에 돌았다** — 매니저가 실무 필요로 Convert 했고,
우리는 전후를 나란히 얻었다:

```
⑥ 쿼리 →  PO-01133 (8/26 입고 · 1,800개 · 원가 없음)
매니저가 Cin7 에서 Convert
inv-cost 1회       →  processed 1 · rows_written 1 · duration 3.0초
⑥ 쿼리 →  0행
```

### 📌 그리고 조용히 통과한 것 — `CardID` 가 Convert 를 넘어 유지된다

`PO-01133` 의 원장 행은 **Simple 시절 `StockReceived` 축**으로 만들어졌고,
원가 행은 **Convert 후 `PutAway` 축**으로 만들어졌다. **그런데 조인이 맞았다**:

```
ledger  line_ref 90bc0304-… · TSK00001 · A070801 · 1800 · 2026-08-26
cost    line_ref 90bc0304-… · TSK00001 · A070801 · 1800 · 2026-08-26 / goods
```

⇒ **Cin7 이 라인 신원을 유지한다.** 실무의 예외가 원장·원가 정합을 깨지 않는다.

## 4. ⭐ 급감 판정 — 축이 하나로 좁혀졌다

회차 로그가 2행이 되어 **첫 뺄셈**을 했다.

```
list_total   21,976 → 22,009    +33   (8/27 → 8/28)
insert_rows  13,833 → 13,788    −45
```

⚠️ **두 값이 반대로 움직인다.** 「자연 감소 −34/일」이라던 추정이 틀렸다 —
`list_total` 은 **Cin7 의 product availability 행 수**이고 `insert_rows` 는 **우리가 합쳐 만든
재고 행 수**다. **다른 물건**이라 같은 방향으로 움직일 이유가 없었다.

| 축 | 정상(8/28) | 불량(8/24 밤) | 판정 |
|---|---|---|---|
| **`list_total` 일일 변화** | **+33** | **−202** | ⭐ 유일한 축 |
| `duration_ms` | 45.1초 (전날 53.3) | 104초 | 보조 축 |
| ~~`pages_scanned`~~ | 23 | **22** | ❌ `list_total÷1000` 올림값 |
| ~~`insert_rows`~~ | −45 | −42 | ❌ 다른 물건 · 방향 무관 |

⚠️⚠️ **`pages_scanned` 는 독립 정보가 아니다.** 22,009 는 22,000 을 넘어 23페이지가 됐을 뿐이고,
**8/24 불량(21,877)과 8/27 정상(21,976)은 똑같이 22페이지**였다. 페이지로는 못 가른다.

⬜ **임계값은 아직**. 정상 표본이 2점뿐이다 — `+33` 하나로 「자연 증가」라 단정할 수 없다.
며칠 더 쌓아 변동 폭을 본다.

## 5. cron 등록 — `inv-cost` jobid **16**

```
'33 4 * * *'  (UTC)  =  토론토 00:33
URL: .../inv-cost?commit=1&since=2026-08-20
```

**근거**: 빈 분 · 스냅샷(05:21)과 **48분** 떨어짐(23페이지를 몰아 치는 회차라 멀수록 429 위험이
낮다) · `inv-sku-types`(03:26)와 67분 · **아침 점검 전**에 돌아 ⑥이 간밤 결과를 본다.

⚠️⚠️ **`since=2026-08-20` 이 URL 에 반드시 있어야 한다** — 빠지면 기초 스냅샷 이전 입고까지
원가가 들어온다.

📌 **하루 1회로 시작한다**(6시간마다는 보류). 지금 회차가 3~9초라 부담이 없고,
`detail_capped` 가 반복되면 그때 늘린다. 되돌리기 쉬운 쪽부터.
⚠️ 상세 캡은 **회차당 40건**이다 — 8/20 같은 일괄 마감이 또 있으면 밀린다.

⚠️ 등록 시 **placeholder 를 실제 값으로 바꾸는 것을 한 번 놓쳤다**
(`still_placeholder: true`). 401 로 매일 조용히 실패할 뻔했다 — `cron.job_run_details` 는
`succeeded` 로 찍힌다. **같은 이름으로 `cron.schedule` 을 다시 부르면 덮어쓴다**(jobid 유지).
확인 쿼리:
```sql
select jobname, command like '%WMS_CRON_SECRET%' as still_placeholder,
       command like '%since=2026-08-20%' as has_since,
       command like '%commit=1%' as has_commit
from cron.job where jobname = 'inv-cost';
select length((regexp_match(command, 'x-wms-cron-key'',\s*''([^'']*)'''))[1]) as secret_len
from cron.job where jobname = 'inv-cost';   -- 24 여야 한다(공백 섞임·잘림 탐지)
```

## 7. 📌 설계 방향 — PO 를 하나로

Cin7 이 Simple/Advanced 로 나눈 것은 **범용 소프트웨어의 사정**이다. 소규모 사업자는
「주문→인보이스」만 필요하고 창고를 쓰는 곳은 입고·풋어웨이가 필요하니, 둘 다 팔려고
두 제품을 만든 것이다.

**우리 IMS 는 우리 하나만 맞추면 된다** — Caleb 판단(2026-08-28).

📌 근거가 실무와 코드 양쪽에 있다:
- **실무**: 대부분을 Advanced 로 넘긴다 ⇒ 우리 요구사항은 Advanced 쪽 하나다
- **코드**: 우리 원가 사슬이 **`PutAway` 의 bin·CardID** 에 걸려 있다. Simple 에는 그게
  없거나 다르다. **PO 가 하나면 이 분기 자체가 사라진다**(`inv-cost` 의
  `skip_simple_unverified` 도 함께)

⚠️ 「자꾸 예외 규정이 만들어지는 것은 시스템에 좋지 않다」 — 이것이 `ims-principles` 원칙 1의
구체적 사례다: **Cin7 의 문서 종류를 그대로 물려받지 않는다.**

## 8. 📌 오늘의 방법론

**경고를 정교화하려다, 결과로 잡는 쪽이 더 낫다는 것을 확인했다.**

```
경고 방식   왜 스킵했나를 코드가 판단해 알린다
            → 조건이 늘고, 노이즈가 끼고, 볼 자리를 새로 만들어야 한다
결과 방식   재고는 있는데 원가가 없는 것을 조인으로 찾는다
            → 이유를 안 가리고, 고치면 사라지고, 볼 자리가 이미 있다
```

📌 그리고 **오늘 코드를 한 줄도 안 고쳤다.** 어제 만든 것이 예상보다 잘 돌았고,
발견한 구멍(`PO-01133`)은 기존 장치가 **스스로 잡고 스스로 닫았다.**

📌 앵커 「세션당 조용한 결함 발견」 08-28: **1건** — `PO-01133`(재고는 원장에 있는데 원가가
없었다 · 에러 없음 · 정지 없음 · 신고 없음). 세션 성격 = **검증 세션**(어제 만든 것의 첫 실물 확인).
