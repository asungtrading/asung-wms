# 2026-08-20 — 재고 원장 ⑤ 가동: 기초 스냅샷 · 커서 seed · commit=1 · pg_cron

같은 날의 `docs/sessions/2026-08-20-admin-warehouse-boundary.md` 와 **문서를 나눈다** — 주제가 다르다.
그쪽은 admin/리시빙(SO-13893 사고 계열), 이쪽은 **원장 가동**이다. 서로 포인터만 단다.

**이날의 성격**: ③ 검증 단계였는데 **⑤ 가동까지 한 번에 넘어갔다.** ⑤ 진입 게이트 6개가 전부 닫혔고,
그 6번(커서 seed)이 ④ 스냅샷과 짝이라 스냅샷을 앞당긴 것이 연쇄를 열었다.

설계 정본은 `docs/design/ledger-design.md` — 2부 「② 기초 스냅샷」 · 4부 「commit=1 을 켜기 전에
닫아야 하는 것」 · 4부 「⑤ 쓰기 가동」. 이 문서는 **그날의 경위와 판단 근거**다.

## 1. ④ 기초 스냅샷 — 8/22 예정을 8/20 저녁으로 앞당겼다

⚠️ **왜 앞당겼나**: 스냅샷의 조건은 「토요일」이 아니라 **「창고가 멈춘 시각」**이다. 평일 저녁도
같은 조건이므로 이틀을 기다릴 이유가 없었다. 그리고 게이트 6(커서 seed)이 스냅샷 `taken_at` 을
필요로 해서, 스냅샷을 미루면 ⑤ 전체가 미뤄진다.

```
snapshot_key : 2026-08-20-initial
taken_at     : 2026-08-20T23:42:47.855Z  (19:42:47 토론토)
13,844행 · 토론토 7,523 / 에드먼튼 6,321
소요 44초 · truncated false · rate_limited false · unexpected_warehouses []
```

**리허설을 먼저 했다** — 같은 날 낮 dry 로 41초·13,871행 확인. 실촬영과 **27행 차이**는 그사이
5시간의 실제 재고 변동이다(정상).
📌 리허설의 목적은 **같은 값을 내는 것이 아니라 경로가 도는지**를 보는 것이다 — 값이 같기를
기대했다면 27행 차이를 이상으로 오해했을 것이다.

**DB 검증 일치** — `inv_snapshot` 의 행·SKU·수량·금액이 EF 응답과 동일.
📌 `bins` 만 SQL 쪽이 1씩 많다(506→507 · 1467→1468) — **빈 문자열 bin 이 `distinct` 에 세어진 것**
이지 불일치가 아니다.

### ⚠️ 자리 미상 재고가 기준선에 포함된다 — 알고 시작한다

`null_bin_nonzero` **15건**(수량은 있는데 bin 이 없음). 토론토 1,421개 · 에드먼튼 6개.

| SKU | 수량 | 비고 |
|---|---|---|
| `AS00879BLA` | **1,200** | **$12,065** — 최대 |
| `AIA*` 7종 | 각 6 | 전부 $0.0831 로 같은 패턴 — 샘플·디스플레이 추정 |
| `SUN31504` | 159 | **원가 $0** |

⇒ 원장은 이를 **그대로 기록하고** ⑥ 대조에서 드러난다. 고치고 시작하지 않는다 — 원장은 Cin7 을
읽는 장부이고, 원본의 상태를 바꾸는 것은 원장의 일이 아니다.

📌 ~~`null_bin_nonzero` 에 샘플 상한이 있는지 미확인 — 실제로는 15건보다 많을 수 있다~~ →
**상한 없음 (코드 확인)**: `supabase/functions/inv-snapshot/index.ts` 의 `nullBinNonzero` 는
조건 없이 `push` 되고 어디서도 `slice` 되지 않는다(응답 주석 "전체 목록"과 일치).
**15건이 전량이다.**

⚠️ **`inv-snapshot` 은 `key` 파라미터가 필수다** — 자동 생성을 하지 않으며 **dry 에도 요구**한다.
인증은 `inv-collect` 와 같은 `WMS_CRON_SECRET`.

## 2. 게이트 6 — 커서 seed

`inv_sync_state` 는 **비어 있었다**(`commit=1` 을 한 번도 안 켰으므로) — 충돌 없이 seed 했다.

| `source_key` | `last_cursor` | 근거 |
|---|---|---|
| `transfer` | **`TR-01327`** | 버려진 DRAFT 4건(TR-00303·00708·01073·01327)을 넘긴다 |
| `adjustment` | **`ST-00646`** | 버려진 DRAFT 6건(ST-00339~00646)을 넘긴다. 그 위로는 비종결 없음 |
| `assembly` | **`FG-00128`** | 최대 번호 · **비종결 0건** |
| `sale`·`purchase`·`creditnote` | **`2026-08-20T23:42:47.855Z`** | 스냅샷 `taken_at` |

⚠️ **`since=2026-08-20` 은 커서와 별개이며 매 호출에 필요하다.** 코드가 `occurred_on > since`
(**엄격히 큼** — `makeSink` 의 "경계일 제외" 주석)를 쓰므로 **8/20 전체가 제외된다** — 그날 낮
사건은 스냅샷에 이미 녹아 있고, 19:42 이후에는 창고가 멈춰 사건이 없다.
`since=2026-08-19` 로 하면 8/20 낮이 **이중 계상**된다.

### ⚠️ floor 선택의 원칙 — 되돌릴 수 있는 쪽

transfer 의 `TR-03539(ORDERED)` 는 **버려진 것으로 보이나 미확인**(에드먼튼 문의 대기)이다.
두 선택의 실패 방향이 대칭이 아니다:

- `TR-03539` 로 seed → 그 이하는 **영영 안 본다.** 진행 중이었다면 그 이동이 통째로 빠지고,
  **지나간 뒤라 알아채기 어렵다**
- `TR-01327` 로 seed → 커서가 `TR-03539` 앞에서 멈출 뿐 **유실은 없다.** 느릴 뿐이고, 확인 후
  `update inv_sync_state set last_cursor='TR-03539' where source_key='transfer';` 한 줄로 올린다

⇒ **낮은 쪽을 골랐다. 커서를 올리는 건 언제든 되지만 내리는 건 이미 지나간 뒤다.**

📌 `IN TRANSIT` 2건(TR-03975·03976)은 floor 보다 훨씬 위라 도착 행이 유실되지 않는다.
dry 에서 `hold_intransit_before_since: 2` 로 정확히 분류됐다 — 설계 주석의 「since 경계 아티팩트」가
**실제로 작동한다**(주석이 맞았다는 것을 실행으로 확인한 셈이다).

### seed 산출 — GAS 프로브 1회

`ppa_cursorSeed`(목록 전량 + Status 분포 + 비종결 번호).

⚠️ **엔드포인트·필드명을 추측하지 않았다**:
- `stockadjustmentList`(**소문자 a**) · 번호는 `StocktakeNumber`
- assembly 는 `finishedGoodsList` → 배열키 **`FinishedGoods`**(`FinishedGoodsList` **아님**) ·
  번호는 `AssemblyNumber`

응답에서 **배열형 키를 찾아내는 방식**으로 확정했다 — 관례 추정으로 갔다면 조립이 또 `""` 를
냈을 것이다(2026-08-17 dry 실사고와 같은 함정).

⚠️ transfer 42페이지를 400ms 로 돌다 **429** 를 맞았다(분당 150콜 — 한도 60 초과).
산출값은 이미 얻었으므로 **재실행은 불필요**했다. 📌 프로브는 EF 와 달리 페이싱 상수를 공유하지
않는다 — 조사 코드에도 간격이 필요하다는 실측.

## 3. ⑤ commit=1 첫 가동

소스 하나씩 **수동 1회** → 확인 → cron 등록 순.

**수동 1회 결과 — 전 소스 `written=0`.** 스냅샷 이후 사건이 없어서다. 경로는 검증됐다:
`mode: commit` · **커서 전진** · `warnings []` · `conflicts_detected 0`.

### ⚠️ `precision_skipped` 가 「목록은 많은데 후보가 0」을 설명한다

`UpdatedSince` 는 **날짜 단위**라 겹치게 받고(커서 − 1일), 커서 **시각**보다 이전에 갱신된 것을
우리 쪽에서 다시 걸러낸다.

| 소스 | 목록 | 분해 |
|---|---|---|
| 발주 | 88 | 45(서비스 전용) + **43(precision)** |
| 판매 | 273 | **179(precision)** + 78(미출하) + 16(void) |

📌 **이 필드를 검증 커맨드에 넣을 것** — 없으면 「왜 안 들어왔지」를 추적할 수 없다.
숫자가 0으로 나오는 이유가 **정상**인지 **고장**인지를 가르는 유일한 단서다.

### ⚠️⚠️ 회차 소요는 소스마다 다르다 — 캡이 아니라 「상세를 봐야 하는가」가 가른다

- **adjustment**: 후보 586건이 **한 회차에 끝났다**(`detail_fetched: 0`) — `skip_since` 판정이
  **목록 레벨에서** 되므로 상세를 한 번도 안 부른다
- **transfer**: 캡 40에 걸린다(`detail_capped_remaining: 1,787`) — `DepartureDate`·`CompletionDate`
  **두 날짜를 봐야** 해서 목록만으로 판정이 안 되는 문서가 많다

⇒ **「후보 수 ÷ 캡」으로 회차를 추정하면 틀린다.** [실측] transfer 5회차에 **214건 전진**
(`TR-01368` → `TR-01582`) — 회차당 40건이 넘는 것은 목록에서 걸러지는 것이 섞이기 때문이다.

겹쳤다 — 최초 등록값 7·22·37·52 는 **transfer(`2-57/5`)의 부분집합**이라 4회 실행이 전부 동시였다.
둘 다 `inv-collect` 이고 같은 WMS 키를 쓰므로 각각 최대 40콜×1,200ms(≈48초)면
**합산 분당 ~100콜 = 한도 60의 1.7배**였다(드러나는 신호는 `rate_limited` 하나다).

📌 **교훈: `hello` 와의 겹침만 보고 원장 잡끼리를 안 봤다** — **분 집합을 전수 계산할 것.**
잡이 늘면 확인해야 하는 쌍은 제곱으로 는다. 눈으로 세지 말 것.

**현재 겹침 0** (전수 계산 확인):

| 잡 | 분 집합 |
|---|---|
| `hello` `*/5` | 0·5·10·…·55 |
| transfer `2-57/5` | 2·7·12·…·57 |
| sale `4-59/5` | 4·9·14·…·59 |
| purchase `8-53/15` | 8·23·38·53 |
| adjustment 11 · assembly 13 · creditnote 16 | 단발 |

⚠️ **URL 에 `since=2026-08-20` 이 반드시 들어간다** — 빠지면 스냅샷 이전 사건이 원장에 들어온다.
📌 **스냅샷을 다시 찍으면 cron 6줄의 `since` 를 손으로 갱신할 것.** 테이블 영속화(`inv_sync_state`
에 담기)를 미루고 URL 을 고른 대가이고, **알고 고른 것이다** — 재촬영은 드문 사건이라 수작업 6줄이
코드 변경보다 싸다. 빠뜨리면 **조용히 이중 계상**된다.

⚠️ **소스별로 나눈 이유**: `TIME_BUDGET_MS=120초` 안에 6종을 다 돌 수 없다 — 첫 소스가 예산을
소진하면 나머지는 `aborted`(2026-08-19 실측).

📌 **등록 후 검증은 결과물로만 한다** — `cron.job_run_details` 의 `succeeded` 는 아무것도 보장하지
않는다(2026-08-19 실측 — HTTP 요청을 **띄운 것**까지만 본다). `inv_sync_state.last_run_at` 갱신과
`last_cursor` 전진이 **유일한 증거**다.

⚠️ placeholder 잔존 확인은 **값을 노출하지 않는 방식으로**:

```sql
select jobname,
       command like '%SECRET%'             as still_placeholder,
       command like '%since=2026-08-20%'   as has_since
from cron.job where jobname like 'inv-collect%';
```

## 5. ⑤ 진입 게이트 — 6개 전부 통과

**정본은 설계 4부** 「commit=1 을 켜기 전에 닫아야 하는 것」. 오늘 **6개 중 5개가 바뀌었다.**

```
☑1 CardID · 👁2 adv_no_putaway(관찰) · ☑3 재등장 전제 ·
🟡4 ON CONFLICT(코드 완료 — ⚠️ 실동작 미검증, 원장이 비어 있어 첫 회차 insert_skipped=0) ·
☑5 캡·페이싱 · ☑6 커서 seed
```

⇒ **게이트 전부 통과. 단계는 ⑥ shadow 대조로 넘어간다.**

- 👁2 는 **관찰 대기** — WMS 는 put-away 없이 Apply 하지 않으므로 우리 시스템이 만들 수 없는 상태다.
  ⚠️ **Advanced PO 기본값을 켜면 게이트로 복귀한다.**
- 🟡4 만 **실동작 미검증**으로 남는다 — 원장이 비어 있어 첫 회차 `insert_skipped` 가 **구조적으로 0**
  이다. **두 번째 회차부터** 의미가 있다.

📌 이 표기는 **세 곳이 공유한다**: 설계 4부 · `asung-inv-ledger` 스킬 §1 · 이 문서.
한 곳만 고치면 갈라진다.
