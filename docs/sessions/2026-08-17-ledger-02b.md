## 3. 이번 세션 수정 4건 (전부 배포됨)

### ① ②-b 본체 (`2459c02`)

날짜 커서 축 신설(`runDateSource`) · 소스별 수집 · 공유 sink 추출(`makeSink`/`mkRaw`).

⚠️ **`line_ref` 가 판매만 다르다 — 설계 정본 이탈, 의도된 것**
- 정본: `line_ref = ProductID`
- 판매: **`<fulfilment TaskID>:<ProductID>`**
- 이유: **유니크 키에 `occurred_on` 이 없다.** 분할 출하(8/10 에 5개, 8/15 에 3개)면 두 행의 키가

- [실측 2026-08-17] `field_fallbacks` 비어 있음 = `f<순번>` 폴백 한 번도 안 켜짐(TaskID 항상 존재)

### ② creditnote 후보 dedup (`851f2de`)

목록 행이 sale 단위인데 상세가 `CreditNotes[]` 를 전부 순회하므로, 같은 sale 이 여러 후보로 오면
같은 CN 이 한 회차에 여러 번 push 된다 → 보고 숫자 부풀림 + 상세 호출 캡 잠식.

⚠️ [실측] `dup_sale_dropped: 0` — **이번 창에서는 실제로 걸러낸 게 없다.** 목록이 sale 단위라
같은 sale 이 두 행으로 안 나오는 것으로 보인다. **무해하지만 현재 하는 일이 없다.**

### ③ 날짜 커서 정체 결함 2건 (`82fb843`) — ⚠️ dry 로는 재현 불가한 결함이었다

**A. 커서는 시각인데 읽을 때 날짜로 잘렸다 → 영구 정체**
- 저장: `cursorWouldBe = lastProcessedUpdated`(전체 정밀도 시각)
- 읽기: `dateOnly(sinceUsed)` → **10자 절단** → `minusOneDay` → 직전 회차와 같은 `UpdatedSince`
- 결과: 매 회차 **같은 앞 40건만** 처리, 41번째부터 영영 안 들어옴.
  유니크 키가 재삽입을 흡수하므로 **삽입 0행 · ok:true · 커서 갱신(같은 값)** = 완전히 조용함
- 수정: `UpdatedSince` 요청은 날짜 단위 유지(겹침 의도), **거르기는 우리 쪽에서 전체 정밀도로**
  (`cd.updated < cursorBefore` 제외 · `=` 는 남김 · `updated` 없는 후보는 안 거름) → `precision_skipped`

**B. `Updated` 없는 문서가 캡을 채우면 커서 동결**
- `lastProcessedUpdated == null` → `cursorWouldBe = cursorBefore` → 다음 회차도 같은 40건
- `from_cursor` 하한을 만들게 한 실사고(TR-00012~76)와 같은 모양인데 아무도 안 막았다
- 수정: commit 게이트에 `"capped with no usable Updated - cursor would freeze"` 추가 → `cursor_frozen_alert`

📌 **배치 순서 판단** (Claude Code 가 프롬프트를 정정): 정밀도 필터는 **dedup 앞**.
뒤에 오면 dedup 이 남긴 "가장 이른 CN"이 커서 미만이라 오더가 통째로 탈락하고, 뒤쪽 CN 은
이미 후보에서 사라져 회수 경로가 없다.

### ④ 상태 판정 결함 2건 (`f33260f`)

**A. 발주 블록 화이트리스트화** — 통과는 `AUTHORISED` 와 `""` 둘만.
`""` 통과 근거는 실측 PO-01128(재고 들어감). 알려진 어휘 5종 밖 값이면 `warnings` 에 보고.
[실측 검증] `sr_blocks_skipped` = VOIDED 1 · NOT AVAILABLE 3 · `ledger_rows` **1,684 → 1,594 (−90행)**

**B. 반품 목록 단계 `RestockStatus` 필터 제거** — 상태 판정 권한은 상세의 `CreditNotes[]` 순회 한 곳만.
목록 단계는 `list_restock_status_counts` 로 세기만 한다.
[실측 검증] 후보 **60 → 124** · `list_restock_status_counts` DRAFT 63 + NOT AVAILABLE 1 = 64

## 4. ⚠️ 날짜 커서 축과 이벤트 날짜는 분리돼 있다 (세 소스 공통 — 실측 확정)

`UpdatedSince` 는 **어떤 문서를 가져올까**의 축이고, 원장 행의 날짜는 **이벤트 날짜**
(`Lines[].Date` · `CreditNoteDate` · `ShipmentDate`)다. 8월에 갱신된 문서가 4월·6월 이벤트를
품고 있으면 **과거 날짜 원장 행이 생긴다.**

[실측 2026-08-17 dry]

| 소스 | 파라미터 | 원장 행 날짜 분포 |
|---|---|---|
| purchase | `from_since=2026-08-01` | 06-18 ~ 08-13 (6·7월이 대부분) |
| creditnote | `from_since=2026-07-01` | **2026-04-27 포함** |
| sale | `from_since=2026-08-14` | **90% 이상이 7월** · 08-14 이후 0 |

⚠️⚠️ **④ 스냅샷과 정면으로 부딪힌다.** 8/22 스냅샷은 그 시점 잔고를 담고 과거 이벤트는 이미
그 안에 녹아 있다. 수집이 또 더하면 **원장이 조용히 부푼다.**

**방어는 `since=` 파라미터다.** [실측 검증] `only=creditnote&from_since=2026-07-01&since=2026-08-01`
→ `ledger_rows` **0** · `since_filtered_rows` **15** · `date_histogram` 비어 있음 = 정확히 상보적.

⇒ **⑤ pg_cron 등록 시 `since=<스냅샷 날짜>` 는 선택이 아니라 필수.**

⚠️ **이름 혼동 위험** — 저쪽 대화가 스스로 지적한 것:
- `since` = **이벤트 날짜 필터** (스냅샷 경계 방어 · 영구적으로 필요)
- `from_since` = **`UpdatedSince` 커서 시작점** (state 없을 때만 쓰는 씨앗)

cron URL 에서 하나를 빠뜨리거나 바꿔 쓰면 조용히 잘못 돈다.

## 6. 미해결 3건 (코드 아님 — GAS 프로브 실측 · ③에서)

### 1. Simple 발주 분기 미검증

최근 40건이 **전부 Advanced**(`simple_docs: 0`). 명세가 강조한 함정(배열 vs 객체)의 절반이 안 돌았다.
저쪽 대화가 알려준 실물 2건으로 검증할 것:

| PO | 확인 내용 |
|---|---|
| `PO-00874` | 23차 프로브 · Simple · `StockReceived` = **객체** · 키 `Status`,`Lines` · Lines 1줄 |
| `PO-00427` | 3차 프로브 · `purchase?ID=` → 객체 |

⚠️ **`PO-00427` 은 `advanced-purchase?ID=` 로도 조회되고 그때는 배열(1)로 나온다** — 같은 PO 라도
어느 엔드포인트로 읽느냐로 형태가 갈린다.
⚠️ **`purchase?ID=` 는 Advanced PO 에 400 deprecated 를 반환**(PO-00069) — 분기가 필수인 이유.

### 2. `empty_restock` — AUTHORISED 인데 `Restock[]` 이 빔

명세("DRAFT 면 비어 있다")는 **표본 하나(CR-00024)에서 일반화한 것**이었고 반례가 나왔다.
반품 입고가 누락된 것인지, 정상인지(금액만 처리) 실물 확인 필요.
⇒ 저쪽 제안: **판정을 `RestockStatus` 가 아니라 `Restock[]` 실제 길이로** 하는 게 안전.

### 3. 판매 Pick vs Ship 수량 — ⚠️ 성격이 다르다: 검증할 수 없는 것

**`Ship.Lines` 에 SKU·수량 필드가 아예 없다**(3차 프로브 실측:
`ID·ShipmentDate·Carrier·Boxes·TrackingNumber·TrackingURL·IsShipped`).
⇒ Pick 에서 가져올 수밖에 없었다 — **선택의 여지가 없었던 것이지 미검증 가정이 아니다.**

부수 근거(13차): `SO-14532` Order 4·Pick 4·Movements 4 / `SO-14545` 3·3·3
⚠️ 둘 다 단일 fulfilment·전량 출고 — **부분 선적 표본이 아니다.**

⇒ 부분 선적이 실재하면 원장이 과다 차감되지만 **Cin7 API 로는 탐지 불가.**
발견 경로는 **⑥ Movements 대조(SKU 단위)** 뿐이다. "감수하는 한계"로 문서에 남길 것.

## 7. ⑤ 착수 전 결정 필요 4건

### 1. ⚠️ 캡·페이싱 — 429 예산이 진짜 제약이다

- `MAX_DETAIL_PER_SOURCE = 40` 은 **Claude Code 제안값이고 명시적 유도 근거가 없다.**
  역산하면 40 × 700ms ≈ 28초/소스 → 3소스 84초 < 120초 예산(추론이지 기록된 근거 아님)
- **실측 duration 은 14~46초** — 시간 예산(120초)은 제약이 아니었다
- ⚠️⚠️ **`DETAIL_SLEEP_MS = 700ms` = 분당 85콜.** Claude Code 가 근거로 쓴 "한도 60/60" 이
  분당 60콜이면 **페이싱 자체가 초과다**
- [실측 2026-08-17] **429 를 실제로 맞았다** — creditnote 직후 purchase 가 `list_aborted: rate_limited`
  (`list_total` null · `pages` 0). 캡 40 덕에 소스당으로는 안 걸리다가 연속 호출에서 터졌다
- ⇒ **캡을 올리기 전에 Cin7 실제 한도 확인이 선행.** 판매 24회차 문제는 그 다음
- → ✅ **선행 조건 충족(2026-08-18 밤 실측)**: 한도 60콜/60초 · 애플리케이션 키 단위 ·
  700ms 초과 확정 → 간격 1,200ms·캡 40 근거 확립. 정본:

### 2. `since` 를 어떻게 영속시킬 것인가

- `floor` → `last_cursor` 는 **자동 영속**(Claude Code 설계 — ⑤ 별도 주입 코드 불필요)
- **`since` 는 그런 경로가 없다** — 매번 파라미터로 줘야 한다
- cron URL 에 박으면 **스냅샷 재촬영 때 cron 을 손으로 고쳐야 한다** → `inv_sync_state` 에 담는 안 검토
- ⚠️ §4 의 `since` / `from_since` 이름 혼동 주의

### 3. ⚠️ 문서 수정 시 `ON CONFLICT DO NOTHING` 이 수정을 버린다 — 논의된 적 없음

날짜 커서 축 3종은 **수정되는 문서들**이다. `UpdatedSince` 는 수정된 문서를 다시 물어오지만,
유니크 키 충돌로 **DO NOTHING** → 옛 수량이 원장에 남고 대조에서 "설명 불가 차이"로만 나타난다.

유니크 키는 **배치 재실행 멱등성**을 위해 설계된 것이지 수정 반영을 고려하지 않았다.
정석은 **충돌하되 값이 다른 행 감지 → 시끄럽게 알림 → 역분개(reversal) + 재기표.**

📌 관련 Caleb 발언: *"번호는 자동으로 정해지기 때문에 현재는 수동으로 변경이 불가해.
뭔가 변경을 발생시키려면 다시 새로운 번호가 발생하게 되어 있어."*
⚠️ 저쪽 대화는 이것을 "커서로 쓸 수 있다"의 근거로만 썼고, **"문서 내 수량 수정이 일어나지 않는다"로
확장 검증하지는 않았다.** 그 발언이 수량 수정까지 포함하는지 **Caleb 확인 필요** — 포함한다면
이 항목은 소멸하고, 아니면 역분개 설계가 필요하다.

**commit=1 을 처음 켜기 전에 결론이 나 있어야 한다.**

## 12. ②-a 에서 확정된 것 (건드리지 말 것 — v1 §4 유지)

### 조정
| 배열 | `event_type` | `qty_delta` |
|---|---|---|
| `ExistingStockLines` | `adjust_existing` | **`Adjustment − QuantityOnHand`** |
| `NewStockLines` | `adjust_new` | **`Quantity`** 그대로 |

⚠️ `Adjustment` 는 증감분이 아니라 **조정 후 목표 수량**(실측 ST-00755 VARIANCE +50).

### 창고이동 — 한 라인이 4행
```
leg 1  From 창고/빈    −Q   DepartureDate
leg 2  IN_TRANSIT      +Q   DepartureDate
leg 3  IN_TRANSIT      −Q   CompletionDate
leg 4  To 창고/빈      +Q   CompletionDate
```
- `CompletionDate` 없으면 **leg 1·2만** · 같은 창고 안 이동(97%)도 **4행 그대로**
- ⚠️ 빈 이동 날짜 결손은 **구조적**(Cin7 WMS 모바일 빈 이동은 `DepartureDate` 없음).
  같은 창고 → `LastModifiedOn` 대체 + raw 기록 / 다른 창고 → **hold**

### 조립
- `PickLines[]` = `assemble_out`(−) · 헤더 = `assemble_in`(+) · `sku` 는 **`ProductCode`**
- 날짜 = `CompletionDate`(FG-00110 실측) · `Status='COMPLETED'` 만(120건 중 VOIDED 77)

### 공통
- **창고 판정**: `ref/location` 전량 → `ParentID` 없으면 창고. ⚠️ **문자열 콜론 파싱 금지**
- `seq_hint` = `qty_delta > 0 ? 1 : 2`(같은 날 유입 먼저)
- **`Production Facility` 는 하드코딩으로 거르지 않는다** — 원문대로 넣고 예상 밖 창고면 경고
  (근거: "안 쓰는 창고라도 누가 실수로 재고를 넣으면 알아야 한다")
- **커서 하한** `?from_cursor=`: `last_cursor` 있으면 무시. ⚠️ 하한은 옛 데이터를 안 보는 것이지
  **이상 감지를 끄는 것이 아니다**
