# 상쇄 행 관례와 조회 함정 — 오진 둘의 경위와 전수 실측 (2026-09-09)

관련: `asung-inv-ledger` §아침 점검 ③ 「원장을 조회할 때의 함정 둘」 · §상쇄 접미어 규칙 · `docs/design/ledger-design.md`
§「상쇄(정정) 계약」 · §원가 레이어 10번(`inv_layer_apply` 의 `source` 결함 — 여기서 다시 서술하지 않는다).
⚠️ 표기: **[실측]** = 운영 DB 에서 읽은 값 · **[추론]** = 판단. 이 문서의 숫자는 전부 09-09 실측이다.

---

## 1. 경위

1. PO + 원가 창이 「트랜스퍼 5문서 이중 기표 · 순액 −7,537」을 보고했다. 재현 쿼리 전부에 `source='cin7'` 이 있었다.
2. 같은 보고 안에 **모순**이 있었다 — 「⑧ bin 대조가 나흘 연속 깨끗한데 원장이 −7,537」. 그런데 그 창은 쿼리를 의심하지 않고 **감지 창구가 뚫렸다**는 쪽으로 갔다.
3. `source` 필터를 특정했다. `manual` 을 포함하면 5문서 `doc_net` 전부 **0** — 상쇄는 이미 있었다.
4. 이어서 「상쇄가 원본을 못 찾는다 · 순액 양수 681」 보고 — `line_ref` 를 키에 넣은 것이 원인이었다(접미어 `:reversal`).
5. 상쇄 관례를 전수 조사했다 — 「관례가 둘인가 · 시기별로 바뀌었나」를 물었더니 **용도가 다른 둘**이고 `manual_reversal` 은 **사건 하나**였다.

## 2. 오진 ① 전문 — `source='cin7'` 필터 → 「이중 기표 · −7,537」

- 재현 쿼리 전부에 `source='cin7'` 이 있어 **`manual` 상쇄를 전량 제외**했다. `cin7` 만 보면 옛 벌(`bin=''`)과 새 벌(`has_bin`) 두 벌이 남아 이중 기표로 보인다.
- [실측 `ADG68596` · `TR-04331` 원장 3행] `cin7 −36`(빈 bin) / `manual_reversal +36` / `cin7 F021002 −36` ⇒ 순액 −36 · 정확히 한 번 출고.
- [실측 `doc_net` · `source` 무관]

| 문서 | `doc_net` |
|---|---|
| `TR-04173` | 0 |
| `TR-04174` | 0 |
| `TR-04175` | 0 |
| `TR-04330` | 0 |
| `TR-04331` | 0 |

- ② `unknown_count 0` · ⑧ 토론토 0칸도 정확했다. ⇒ ⚠️ 지시대로 `manual_reversal` 을 **넣었다면 이중 상쇄로 실제 +7,537 오류**를 만들었을 것이다.
- 정본 `inv_balance` 뷰의 정의 — `source` 조건이 **없다**:
  ```sql
  delta AS (
    SELECT l.sku, l.warehouse, COALESCE(l.bin,'') AS bin, sum(l.qty_delta) AS qty
    FROM inv_ledger l                      -- ⚠️ source 조건 없음
    GROUP BY 1,2,3
  )
  ```
- ⭐ 스킬에 이미 있던 경고를 **정확히 반대 방향으로** 위반했다: 「⑧ 에 없으니 상쇄됐겠지로 넘어가지 말 것 — 원장 순액을 직접 볼 것」. 이번엔 ⑧ 이 깨끗한데 원장이 어긋나 보였고, 그때도 답은 「원장 순액을 직접 볼 것」이었다.

## 3. 오진 ② 전문 — `line_ref` 를 키에 넣음 → 「상쇄가 원본을 못 찾는다」

판매 상쇄는 `line_ref` 에 `:reversal` 접미어가 붙는다. [실측 · 같은 데이터를 세 방식으로]

| 묶는 키 | 키 수 | 완전 상쇄 | 부분 | ⚠️ 순액 양수 |
|---|---|---|---|---|
| `doc_number, line_ref, sku, warehouse` | 13,865 | **0** | 3 | **681** ⚠️ |
| `doc_number, sku, warehouse, bin` + `replace(line_ref,':reversal','')` | 13,187 | 680 | 3 | 1 |
| ⭐ **`doc_number, sku, warehouse`** | **13,183** | **681** | 3 | **0** |

⭐ 세 번째가 답이다 — 순액 양수 0(초과 상쇄 없음)이고 `line_ref` 를 만지지 않는다. 📌 키 13,183 = `cin7 sale_out` 행 수 ⇒ `(doc_number, sku, warehouse)` 가 판매에서 이미 유일하다.
⚠️ `replace(line_ref,':reversal','')` 는 동작하지만 문자열을 만지고 접미어 규칙이 바뀌면 조용히 깨진다 — 「SKU 접미사 파싱 금지」와 같은 정신이 `line_ref` 축에도 적용된다.

## 6. 판정

**용도 구분 — 「둘이 있다」가 아니라 「용도가 다르다」**

| 방식 | 쓰는 상황 | 이유 | 접미어 |
|---|---|---|---|
| **`manual_reversal`** | 같은 사건을 **다른 키로 다시 기표**해 옛 벌을 무효화 | 원래 타입을 쓰면 「또 하나의 출고」로 읽힌다 ⇒ **구분되는 이름이 필요** | **불필요**(타입이 구분) |
| **원래 타입 유지** | 사건 자체를 **취소·정정** | 부호만 반대인 **같은 종류의 사건** | **필요**(`:reversal`) |

**접미어 규칙 — 이미 일관돼 있다.** 타입으로 구분하면 접미어 불필요(`manual_reversal` 592 중 **0**) · 타입을 유지하면 접미어 필요(`sale_out` **680/684** · `transfer_in` **138/138** · `transfer_out` **138/151**). 예외는 §5-③ 13행뿐이고 손으로 이어붙인 후속 정정이다. ⇒ 「통일할지」가 아니라 **이미 통일돼 있다.**
⚠️ 스킬 「재생성 짝을 상쇄할 때 접미어를 바꿀 필요가 없다」는 **`doc_number` 가 다른 경우**(조립 `FG-00133`/`FG-00134`)다 — 같은 문서 안 상쇄는 `:reversal` 을 쓴다.

**키 순액 방식 — 함수가 관례를 알 필요가 없다.** 소진량은 원장 행이 아니라 `(doc_number, sku, warehouse)` 순액으로. `source` 무관 · `line_ref` 키 제외. 트랜스퍼도 성립한다(§5 처럼 섞여 있어도 `doc_net` 0) — 단 `warehouse` 는 키에서 빼지 않는다(출발·도착이 상쇄돼 이동이 사라진다). 구현은 `ledger-design.md` §「상쇄(정정) 계약」 · §원가 레이어 10번.

## 7. ⚠️ 틀린 것

**(PO + 원가 창)**
1. `source='cin7'` 필터로 상쇄를 제외 → 「이중 기표 · −7,537」 오진. **모순(⑧ 깨끗한데 원장 어긋남)을 스스로 적어놓고 쿼리를 의심하지 않았다.**
2. `line_ref` 를 키에 넣어 「상쇄가 원본을 못 찾는다 · 순액 양수 681」 오진.
3. `inv_layer_apply` 세 함수가 `source='cin7'` 로 필터 — 레이어가 원장보다 **+3,619** 남아 있었다(정본 `ledger-design.md` §원가 레이어 10번).

**(나 — 원장 창)**
4. 보고를 받고 처음에 **가설 셋**(빈 bin 특별 취급 / bin 갈림 / 스냅샷 동방향 오류)을 세웠으나 **전부 아니었다.** `inv_balance` 뷰 정의를 먼저 읽었으면 두 단계 줄었다.
5. 상쇄 관례를 「시기별 변화인가」로 물었으나 **`created_at` 이 0.4초 안에 몰려 있어 사건 하나**였다. 시기 축을 의심한 것은 맞았지만 「관례」 프레임이 틀렸다.
6. 접미어를 `sale_out` 만의 것으로 읽을 뻔했다 — `transfer` 축에도 있다(138/138 · 138/151).

⇒ ⭐ **공통점: 「내 계산이 이상하다」를 「데이터가 이상하다」로 읽었다.** 의심할 순서는 **① 내 쿼리 ② 미처리 사건 ③ 데이터**다. **모순이 보이면 전제를 의심한다.**
