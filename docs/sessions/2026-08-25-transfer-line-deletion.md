# 2026-08-25 — 라인 소멸: `TR-04175` 실사고와 소멸 감지 도입

⑥ shadow 대조가 **가동 후 처음으로 원장의 구조적 결함을 잡아냈다.**

```
아침 01:36 자동 대조   unknown 138
→ 원인 규명 (수 시간)  TR-04175 라인 삭제
→ 정정                 상쇄 276행 (append-only 유지)
→ 구조 보완            inv_missing_lines 배포 · 첫 검출 276 = 예상값 일치
```

**"무엇을 했나"는 커밋 메시지에 있다. 이 문서는 「왜 그 판단이 됐나」와 「내가 틀렸던 것」을 남긴다.**
오늘 갈림길마다 답을 준 것은 **Cin7 화면과 실측**이었고, 추론은 반복해서 빗나갔다.

정본 포인터: 규칙·함정은 `asung-inv-ledger` 스킬 · 설계는 `docs/design/ledger-design.md`.

## 1. 사건 — 무엇이 일어났나

**금 2026-08-21 14:58 (토론토)** — 트랜스퍼 `TR-04175` 를 IN TRANSIT 으로 확정.
원장이 **6분 뒤 195줄을 읽어 기록**(토론토 −Q · IN_TRANSIT +Q = 390행).

**월 2026-08-24 10:15** — 업로드한 목록에 `TR-04174` 와 겹치는 품목이 있음을 발견.
undo → 겹친 **138줄 삭제** → 다시 IN TRANSIT(57줄).

**원장은 그 사실을 알 방법이 없었다.** append-only 이고, 삭제된 라인은 **재수집 세트에 오지 않아
비교 대상 자체가 없다**. 195행이 그대로 남아 토론토가 138 SKU 에서 **두 번 차감**됐다.

**화 08-25 01:36** — 대조가 `unknown 138` 로 잡아냈다.

### 원인 규명의 결정적 단서 — 2배 관계

`unknown` 의 `diff` 와 IN_TRANSIT 잔량이 **138건 전부 정확히 2.0 배**였다(예외 0).

```sql
ratio_2x = 138 / 138   non_toronto = 0   no_intransit = 0
```

⚠️ **예외 0 의 정밀함은 사람의 일이 아니라 코드의 일**이라는 것이 방향을 정했다.
그리고 `TR-04173`(64 SKU · 같은 날 출발 · 같은 IN TRANSIT)이 **깨끗한 대조군**이었다 —
⇒ **트랜스퍼 4행 모델 자체는 정확하다. 문제는 모델이 아니라 「수집 후 편집」이다.**

### 숫자가 닫힌 방식 (세 경로 교차 검증)

| 검증 | 값 |
|---|---|
| 대조 `sum(diff)` | **−1,247** |
| 원장의 공유 138 SKU 중복량 | **−1,247** |
| `TR-04174` 전용 57 SKU 합 = 624 / `04175` 전용 = **1,255** | 상쇄 후 04175 잔량과 일치 |
| 집합 일치 | shared 138 = unknown 138 · 차집합 **양쪽 0** |

## 2. 정정 — 왜 지우지 않았나

`source='manual'` 상쇄 **276행**(138 SKU × 2 leg). `FINAL-SALE`(08-24) 선례를 그대로 따랐다:
유니크 7키 중 **`line_ref` 에만 `:reversal` 접미**를 붙이고 `qty_delta` 부호를 뒤집는다.
`occurred_on` 은 정정일이 아니라 **원본 날짜(8/21) 유지** · `raw` 에 `reverses_ledger_id`.

⚠️ **물리 삭제는 하지 않았다** — append-only 의 첫 위반이 「사소한 1건」인 것이 가장 위험하다.

⚠️ **상쇄는 반드시 두 행 모두**여야 한다(토론토 `transfer_out` + IN_TRANSIT `transfer_in`).
한쪽만 되돌리면 IN_TRANSIT 에 유령이 남는다. 처음에 「138행」이라고 말했다가 **276이 맞다**로
정정한 지점이 여기다(§5-⑤).

**결과**: `TR-04175` 토론토 `net −1255` · IN_TRANSIT `net +1255` · 양쪽 333행.
남은 1,255 는 Cin7 의 실제 57줄이라 정상 — 도착하면 leg 3·4 가 그 기준으로 들어와 0 으로 닫힌다.

## 3. ⚠️ 방향 전환 — 「재수집 경로가 없다」에서 「소멸 감지가 없다」로

**처음 세운 진단**: 커서가 문서 번호로 전진하니 지나간 문서는 다시 안 읽힌다 →
그래서 `inv_conflicts` 가 한 번도 안 밟혔다 → 재수집 경로부터 만들어야 한다.

**코드가 그 진단을 뒤집었다.** `inv-collect` 41~43행 주석에 이미 적혀 있었다:

> 「마지막 처리 번호보다 큰 것만」을 그대로 구현하면 IN TRANSIT 이동의 3·4행이 영영 안 생긴다
> — 커서는 **비종결 문서 앞에서 멈춘다**

구현도 그렇다(`processed`·`skip_voided`·`skip_since` 만 커서를 넘긴다).
⇒ **`TR-04175` 는 5분마다 이미 다시 읽히고 있었다.**

📌 **그렇다면 왜 못 잡았나** — `writeLedgerDetectingConflicts` 는 **다시 보내온 행**을 기존 행과
비교한다. 삭제된 라인은 **다시 보내지지 않으므로 비교 자체가 일어나지 않는다.**

> **`inv_conflicts` 는 「변경」 감지지 「소멸」 감지가 아니다.**
> 변경은 양쪽이 있고, 소멸은 한쪽만 있다.

⇒ 필요한 것은 새 수집 축이 아니라 **이미 도는 재읽기에 집합 뺄셈 한 겹**이었다.

### 그리고 그 재읽기는 「설계 의도」가 아니라 「교착의 덕」이었다

`TR-03975`·`03976` 이 `hold_intransit_before_since` 로 커서를 `TR-03974` 에 묶고 있어서
그 위 ~205건이 매 회차 다시 읽힌다. **두 문서가 도착해 커서가 풀리면 이 재읽기도 끊긴다.**
⚠️ 다행히 편집은 IN TRANSIT 중에 일어나고, IN TRANSIT 문서는 **자기 자신이 커서를 잡으므로**
소멸 감지가 붙을 자리는 구조적으로 보장된다 — 교착과는 무관하다.

## 4. ⚠️ 설계 판단 — 왜 이렇게 지었나

### (a) 넓게 vs 좁게 → 넓게

처음엔 트랜스퍼만 하자고 권했다(표본 없이 규칙을 만들지 않는다는 원칙).
**Caleb 판단이 바꿨다**: 조정은 재편집이 거의 없지만(새 조정을 만든다) **발주·판매는 변동이 잦고
수량만 바뀌기도 한다.** ⇒ 트랜스퍼에서 터진 것은 우연히 눈에 띈 하나일 뿐일 수 있다.

⚠️ 전제 하나가 미확인이었다 — 「**라인을 지워도** `Updated` 가 갱신되는가」.
**GAS 프로브 실측으로 닫았다**(§6 표).

### (b) 중복 폭주 → 유니크 키에 `last_modified_on` 포함

`TR-04175` 는 5분마다 재검출된다. 그대로 두면 **하루 4만 행**이 쌓여 아침 화면이 무의미해진다.

단순 7키 + `do nothing` 으로 막으면 **2차 삭제를 놓친다**(같은 키라 조용히 막힌다 —
`inv_ledger` 유니크 키에 시간 축이 없어 분할 출하가 뭉개졌던 것과 같은 문제).
⇒ **`last_modified_on` 을 키에 넣으면 둘 다 해결된다**: 같은 편집이면 값이 같아 dedup,
다시 편집하면 값이 달라져 새 행.

### (c) 자동 정정 없음

기록과 경보만 한다. **오늘도 어느 문서가 유령인지는 Caleb 이 Cin7 화면을 보고 갈렸다** —
원장 숫자만 보고 `04174` 를 지목했다면 실재 차감을 지웠을 것이다(§5-③).

### (d) ⚠️⚠️ 진단이 수집을 막지 않는다 — 검토에서 잡은 것

`detectMissingLines` 는 `!r.ok` 에서 throw 하는데 호출부에 try/catch 가 없었고, 예외가
**최외곽 핸들러(387→1434행)까지** 올라간다. 호출 위치가 **원장 쓰기보다 앞**이다.

```
REST 순단 1회 → 소스 회차 abort → 원장 쓰기·커서 전진 없음
                                   cron.job_run_details 는 succeeded  ← 조용한 정지
```

⇒ **읽기 전용 진단이 본업을 멈추게 하고 그게 조용하다.** 검출·기록 4곳 전부 try/catch 로 감쌌다.
📌 배포 당일 이 방어가 곧바로 값을 할 뻔했다 — grep 출력의 `MISSING_MAX_PE_RUN` 오타 의심건
(붙여넣기 artifact 로 판명, `grep -c` 0). 실물이었다면 **500건 초과 = 대량 삭제가 일어난 바로 그때**
`ReferenceError` 가 났고, try/catch 가 그것을 흡수했을 것이다.

## 5. ⚠️ 내가 틀렸던 것 (감추지 않는다 — 일곱 건)

**① 시간대를 −8 로 계산했다.** 토론토는 여름 −4 · 겨울 −5 다(−8 은 태평양 겨울).
이어서 만든 변환 쿼리에 `at time zone 'UTC' at time zone 'America/Toronto'` 로 **이중 캐스팅**을
넣어 4시간이 밀린 값을 보게 했다(`+00` 표기가 증거였다). 앞선 답변에서 맞게 썼던 것을 굳이 고쳐
망가뜨렸다.
📌 교훈: **결과의 타임존 표기(`+00` vs `-04`)를 먼저 볼 것.** 값이 아니라 표기가 오류를 드러낸다.

**② `TR-04174`/`04175` 를 뒤집어 읽었다.** 「04174 가 유령」이라고 단정했는데 실제는 반대였다
(Cin7: 04174 = 195줄 · 04175 = 57줄). Caleb 이 화면을 보고 정정해줬다.
⚠️ **그대로 갔으면 실재 차감 138 SKU 를 지웠을 것이다.**

**③ 「복제 후 편집」이라고 추론했다.** 138 SKU 의 수량이 완전히 같아서였다. 실제는
**업로드 목록이 겹친 것.** 대칭은 「같은 원천」이지 「사본」이 아니다.

**④ 「커서가 지나가면 재방문 불가」로 진단했다.** 코드에 정반대가 명문으로 적혀 있었다(§3).
⚠️ **코드를 읽기 전에 구조를 단정했다** — 레포가 public 이라 언제든 읽을 수 있었는데 안 읽었다.

**⑤ 「배포 첫 회차에 138행이 쌓인다」고 했다.** 실제는 **276**(SKU 당 2 leg).
같은 계산 실수를 상쇄 설계에서 한 번 더 할 뻔했다.

**⑥ 「since 경계 아티팩트가 도착 전에 손봐야 할 위험」이라고 경고했다.** 코드를 읽고 계산해보니
**대조에 영향 없는 흉터**였다(운송 중은 Cin7 도 ON HAND 에서 뺀다). 철회했다.

**⑦ 죽은 코드를 만드는 프롬프트를 썼다.** 「문서 캡 200→1500, 회차 캡 500 유지」 —
문서 캡이 회차 캡 **안쪽**이라 영원히 발동하지 않는다. 두 숫자의 관계를 안 따졌다.
📌 Claude Code 가 테스트 실패로 이것을 발견하고, **임의로 숫자를 바꾸지 않고 사실만 보고**했다.
「1500 이 안 먹으니 회차 캡을 2000 으로」로 갔다면 폭주 방어가 헐거워질 뻔했다 — 옳은 처리다.

### 📌 관통하는 패턴

일곱 건 중 **②③④⑥** 은 전부 같은 모양이다 — **읽을 수 있는 것(화면·코드)을 읽기 전에 추론했다.**
스킬에 이미 「화면에 보이는데 API 에 없어 보이면 API 를 덜 본 것이다」가 있는데, 오늘은 그 확장판이다:

> **읽을 수 있는 원본이 있으면 추론보다 먼저 읽는다.**
> 레포는 public 이고 Cin7 화면은 Caleb 이 볼 수 있다. 둘 다 오늘 결론을 바꿨다.

그리고 ①⑤⑦ 은 **산술을 검산하지 않은 것**이다 — 2 leg, 타임존, 캡 관계.

## 6. 실측 (추측 금지 — 전부 이날 확인)

### `stockTransferList.LastModifiedOn` 은 라인 삭제도 갱신한다

| 문서 | `LastModifiedOn`(토론토) | 원장 수집 시각 | |
|---|---|---|---|
| `TR-04175` | **08-24 10:15:51** | 08-21 14:58:03 | 삭제 시각 — 수집 **사흘 뒤** 수정 |
| `TR-04174` | **08-21 14:50:55** | 08-21 14:52:44 | **대조군** — 수집 2분 전이 마지막 수정 |

목록 행 키: `TaskID, From, FromLocation, To, ToLocation, Status, Number, CompletionDate,
DepartureDate, InTransitAccount, CostDistributionType, Reference, SkipOrder, LastModifiedOn`

⚠️ ②-b(판매·발주·CN)에 `LastModifiedOn` 이라는 **이름의** 필드가 있는지는 미확인 —
코드는 실측된 갱신 필드(`cd.updated`)를 쓴다. **필드명을 ②-a 에서 ②-b 로 옮겨 추측하지 않았다.**

### 증분 축 재수집은 실동작한다

`?dry=1&only=purchase&since=2026-08-20` → `list_total 9` · **`precision_skipped 9`**
⇒ 이미 원장에 있는 문서 9건이 `UpdatedSince` 로 **다시 왔다**(커서보다 오래된 갱신이라 되걸렀을 뿐).
📌 재수집 여부는 **DB 로 볼 수 없다** — 내용이 같으면 `insert_skipped` 로 버려져 흔적이 안 남는다.
**EF 응답으로만 확인된다.**

### 트랜스퍼 회차 실측 (커서 교착 상태)

```
list_total 4179 · pages 5 · detail_fetched 36 · detail_capped_remaining 0
dispositions: hold_intransit_before_since 2 · skip_since 166 · processed 33 ·
              skip_voided 1 · processed_nonterminal 3
cursor_held_by: { TR-03975, hold_intransit_before_since }
```
📌 `processed_nonterminal 3` = `TR-04173`·`04174`·`04175` — IN_TRANSIT 순합이 0 아닌 셋과 일치.
📌 캡 40 우려는 닫혔다 — 166건이 목록 레벨에서 `skip_since` 라 상세가 필요 없다.

### 배포 후 콜드스타트

배포 직후 첫 dry 는 `detail_capped: time` → G3 가 검출을 건너뛰었다(**설계대로**).
`sleep 90` 후 재실행에서 `processed 33` · `detail_fetched 36` · **`missing_lines_detected 276`** ·
`missing_check_skipped_reason: null`. ⇒ **일회성 콜드스타트**였다.
