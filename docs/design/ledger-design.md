## 이 문서의 전제

원장은 **재고 수량의 변동을 사건 단위로 쌓는 장부**다. "지금 몇 개"를 저장하지 않고 "무슨 일이 있었다"만 쌓아서, 현재 재고는 그것들을 더해 구한다.

1단계 범위는 **수량만·창고 단위**다. 원가는 값을 받아 저장하되 계산은 하지 않는다. 자리(빈)는 기록하되 잔고 계산에는 쓰지 않는다. **둘 다 나중에 소급이 불가능하기 때문에 지금부터 담는다.**

기준은 **Cin7 문서**다. WMS 는 보조다 — WMS 를 안 거치는 재고 이동이 한 달에 수백 건 있어서, WMS 를 기준으로 삼으면 처음부터 구멍이 있는 원장이 된다.

📌 **자체 IMS 설계 원칙 (2026-08-18 승격) — Cin7 의 목록/상세 2단 구조를 자체 API 에 복제하지
말 것.** 이날 캡·페이싱·커서·429 로 씨름한 것의 상당 부분은 **목록이 요약만 주고 라인을 보려면
문서마다 상세를 또 불러야 하는 구조** 때문이다(발주 40건 = 41콜). 이것은 **남의 제약이지
우리 설계가 아니다.** 자체 IMS 의 API 는 호출자가 필요한 데이터를 한 번에 받게 설계한다.
같은 이유로, 변경 감지는 **폴링이 아니라 이벤트(webhook)** 를 기본으로 둔다 — 지금 `hello` 가
5분마다 묻는 것은 Cin7 이 알려주지 않기 때문이지 그것이 옳은 설계여서가 아니다.
⚠️ 다만 **자체 API 에도 한도는 둔다** — 잘못 짠 클라이언트 하나가 시스템 전체를 죽인다.
차이는 그 선을 우리가 정한다는 것뿐이다(내부는 넉넉히, 외부 파트너는 보수적으로).

### 각 사건의 주의사항

**1. 판매 출고** — 픽·팩·Finalize 단계에서는 재고가 안 빠진다. 배송 처리된 것만 기록한다. 배송일이 문서에 있고, 그 날짜가 Cin7 이 실제로 재고를 움직인 날과 정확히 일치하는 것을 세 건 전수로 확인했다.

⚠️ **수량은 `Pick.Lines` 기준인데, 이것은 검증된 선택이 아니라 선택의 여지가 없었던 것이다**
(2026-08-17 성격 확정): **`Ship.Lines` 에는 SKU·수량 필드가 아예 없다**(3차 프로브 실측 —
`ID·ShipmentDate·Carrier·Boxes·TrackingNumber·TrackingURL·IsShipped` 뿐). 부분 선적이 실재하면
원장이 과다 차감되지만 **Cin7 API 로는 탐지 불가** — 발견 경로는 대조 단계의 Movements 검산
(SKU 단위)뿐이다. **감수하는 구조적 한계**로 둔다. 부수 근거(13차): SO-14532 Order 4·Pick 4·
Movements 4 / SO-14545 3·3·3 — 단 둘 다 단일 fulfilment·전량 출고라 부분 선적의 표본이 아니다.

**2. 반품 입고** — 크레딧 노트에 재입고 목록이 붙어 있을 때만 재고가 돌아온다. 목록이 비어 있으면 금액만 조정한 것이라 원장 대상이 아니다. 한 오더에 크레딧 노트가 여러 개 붙을 수 있으므로 전부 훑어야 한다.

⚠️ **정정 2건 (2026-08-17 실측)**:
- **"승인 상태면 재입고 목록이 차 있다"는 표본 하나(CR-00024)의 일반화였다** — 승인(AUTHORISED)
  인데 `Restock[]` 이 빈 크레딧 노트가 실재한다(2~4건 · 반품 누락인지 금액만 처리인지 실물 확인
  미완 — 검증 단계 항목). 판정은 상태값이 아니라 **`Restock[]` 실제 길이**가 안전하다.
- **크레딧 노트 목록(`saleCreditNoteList`)의 행은 CN 단위가 아니라 sale 단위다** — 행의
  `RestockStatus` 단일값으로 오더를 통째로 거르면 **같은 오더 안의 승인된 CN 이 함께 조용히
  유실된다**([실측] 목록 단계 필터 제거로 후보 60→124 · 상세 40건에서 CN 54개). 상태 판정
  권한은 상세의 `CreditNotes[]` 순회 **한 곳**에만 둔다. 원장 문서번호는 오더번호가 아니라
  **CreditNoteNumber**(다중 CN 이 유니크 키를 깬다).

두 정정의 직접 근거가 **`SO-00062`** 다 — CN 이 둘이고 `RestockStatus` 가 각각 달랐다:
`CR-00024` = DRAFT · Restock 0줄 / `CR-00007` = AUTHORISED · Restock 2줄.
⚠️ 그 오더의 **목록 행** `RestockStatus` 가 무엇이었는지는 미확인이다(첫 번째 CN 값인지
대표값인지 합성인지 모른다) — 목록 값으로 거르면 안 되는 이유가 하나 더 있는 셈이다.

**3. 발주 입고** — 날짜는 **입고 기록의 라인마다 붙어 있다.** 헤더가 아니라 라인이라 더 정확하다 — 한 발주를 여러 번 나눠 받으면 각각의 날짜가 따로 잡힌다. 네 건 전수로 확인했다.

⚠️ 주문일·인보이스 날짜·최종수정일은 전부 어긋난다. 그중 하나가 우연히 맞는 경우가 있어 **한 건만 보고 판단하면 안 된다.**

⚠️⚠️ **축 (2026-08-18 재설계 — `docs/sessions/2026-08-18-purchase-putaway-axis.md`·
`2026-08-18-purchase-source-redesign.md` 가 근거): Advanced = `PutAway` / Simple = `StockReceived`.**
목록 `Type` 으로 가른다(엔드포인트 분기와 동일 기준 — `purchase?ID=` 는 Advanced 에 400
deprecated 를 반환한다: `PO-00069`. Simple 근거: `PO-00874` — SR 객체·`LocationID` 있음.
**두 번째 실측 = PO-01117 (2026-08-18)**: Apply 직후 Simple SR 51줄 전부 `LocationID` 보유,
같은 빈에 여러 SKU 공존(`eedb7d88` 빈에 4개 SKU) — Simple=SR 축에서 bin 이 실제로 얻어진다).

**SR 을 쓰면 안 되는 이유 둘** (2026-08-17 까지의 SR 축 구현이 이래서 틀렸다):
① SR 라인의 `LocationID`·`Location` 은 null 이거나, 값이 있어도 **bin 이 아니라 창고 GUID** 다 —
  창고 판정이 `UNMAPPED(no-id)` 또는 bin 없음을 낸다. **bin 이 구조적으로 안 얻어진다.**
② SR 의 `Status` 는 **stock receiving 단계의 워크플로 상태**이지 재고 반영 여부가 아니다 —
  PO-00703 SR=DRAFT/PA=AUTHORISED 62줄 `FULLY RECEIVED` · PO-01131 SR=NOT AVAILABLE/
  PA=AUTHORISED 3,570u · PO-01128 SR=""/PA=AUTHORISED 84줄.

SR·PA 는 **같은 입고의 두 표현**이다(15건 표본 `srLines==paLines`) — **둘 다 읽으면 정확히 두 배.**

**`Convert` 는 라인을 재생성하지 않고 SR → PA 로 옮긴다** [실측 2026-08-18 PO-01117 51줄].
Convert 직후 SR 블록은 **빈 상태(`""`) · 0줄**로 남고 PA 블록에 51줄이 그대로 들어간다
(`TaskID` 는 양쪽 동일). 📌 이것이 PO-01128 에서 본 `SR=[""]` 패턴의 정체다 — 빈 상태 SR 은
"이상한 문서"가 아니라 **Convert 를 거친 문서의 정상 흔적**이다.
그리고 **PA 블록은 `DRAFT` 로 생성된 뒤 승인된다** — 진행 중 상태가 존재한다.

보느냐**가 틀렸던 것이다 — 아래 「−90행 판정 무효」 참조.

**목록 게이트 없음**: `StockReceivedStatus` 로 문서를 거르지 않는다. 목록 값과 상세 블록 값은

**4·5. 창고 이동** — 한 문서가 원장 두 줄이 된다. 출발일과 도착일이 다르고(열흘 정도 벌어진다), 그 사이 물건은 어느 창고에도 없다. 아직 도착 안 한 이동은 출발 줄만 만든다.

⚠️ 이동의 97%는 **같은 창고 안에서 자리만 옮기는 것**이다. 창고 단위 잔고로는 더하고 빼서 0이 되지만, **두 줄 다 기록한다** — 나중에 자리 단위로 올릴 때 필요하고, 그때 가서는 복구할 수 없다.

⚠️⚠️ **트랜스퍼의 bin 은 라인이 아니라 문서 헤더에 있다 (2026-08-19 실측 · GAS 프로브).**
`FromLocation`/`ToLocation` 이 **`"창고: bin"` 문자열**이다(목록·상세 양쪽). [실측] TR-02645:
`FromLocation="Asung - Edmonton: EZ01Pallet03"` · `ToLocation="Asung Trading Inc.: F0300PALLET01"`.
`From`/`To` GUID 는 창고가 아니라 **그 bin 의 GUID 로 보인다**(관찰 — 확정 아님).
📌 **문서 하나가 bin 하나 → bin 하나** 이므로 **라인에 bin 이 없는 것이 정상**이다. 발주처럼
라인마다 자리가 갈리는 구조가 아니다 — **트랜스퍼는 문서 하나 = 자리 하나가 업무의 성격**이고
(2026-08-19 Caleb), WMS 도 같다: 「토론토 여러 bin → Asung - Edmonton」으로 받아 **Apply 시
출발 bin 별로 트랜스퍼 문서를 쪼개 생성**한다(리시빙 Apply 의 bin 그룹 분할과 같은 패턴 ·
도착지는 창고 단위 지정). ⇒ 자리 단위 원장에서도 **문서 단위로 자리를 해석**하는 것이 맞다.

⚠️⚠️ **현재 원장은 이 값을 읽지 않는다** — `From`/`To` GUID 만 `resolveLoc` 에 넘겨 창고만
해석하고 bin 은 빈 값이 된다(dry 전량 3,172행의 `bins` 가 `[""]` 하나).
**데이터가 없는 게 아니라 안 읽고 있는 것이다.** 발주에서 「SR 이 아니라 PA」를 찾은 것과 같은 계열.
⇒ **자리 단위 원장으로 올릴 때 여기부터 고친다.** ⚠️ 다만 `FromLocation` 은 GUID 가 아니라
**문자열이라 `": "` 파싱 + 매핑 대조**가 필요하다(발주의 `LocationID` 처럼 깔끔하지 않다).
⚠️ `Lines[].ProductCustomField1/2` 에 비슷한 값이 보이나 **상품 마스터 필드이므로 쓰지 말 것**
(TR-02644 는 `ProductCustomField1=null`).
📌 **창고 단위 원장에서는 지금 그대로도 정확하다** — 3창고(토론토·에드먼튼·`IN_TRANSIT`)로
정확히 갈리고 4행 구조(출발 − / IN_TRANSIT + / IN_TRANSIT − / 도착 +)도 정상이다.

#### 되돌림 트랜스퍼 (2026-08-19 Caleb + Cin7 실물)

잘못 간 물건은 **WMS 를 거치지 않고 Cin7 에서 직접** 트랜스퍼 백으로 해결한다 —
에드먼튼 → 토론토로 `From`/`To` 를 반대로 설정한 새 트랜스퍼를 만든다.
✅ **bin 은 제대로 지정된다** — 실물 7건(`Search=error`, 전부 COMPLETED) 전부 `창고: bin` 형태로
출발·도착이 명시돼 있고, `Reference` 에 사유도 남긴다(「EDM Transfer Error」·
「Revised Transfer Error - TR-01126」). 📌 **사람이 `ToLocation` 에도 bin 을 찍는다.**
⇒ **실무 절차 자체는 정확하다.** 원장이 이 데이터를 안 읽고 있는 것이 문제였다(위 항목).
⚠️ 남는 질문: 이 되돌림이 **실물 이동이 없는 장부 조정**인 경우, 원장은 실제 이동과 구분하지
못한다. 창고 총량에는 영향이 없으나(왕복 상쇄) **자리 단위에서는 두 번의 이동으로 기록**된다.
그것이 옳은지는 자리 단위 설계 때 판단한다.

**6. 조정 — 기존 재고** — 문서에 적힌 값은 증감분이 아니라 **조정 후 목표 수량**이다. 실제 변동은 목표수량에서 당시수량을 뺀 값이다. Cin7 화면의 차이 값과 일치하는 것을 확인했다.

당시수량이 조정 시점 값으로 박제돼 있어서, 몇 달 전 조정도 정확히 계산할 수 있다.

**7. 조정 — 신규 재고** — 구조가 다르다. 당시수량이 없고 수량 하나만 있으며, 그게 그대로 증가분이다. **6번 규칙을 여기 적용하면 틀린다.** 단가가 함께 들어 있다.

**8. 조립** — 구성품 여러 줄이 빠지고 완제품 한 줄이 들어온다. 번들 판매를 하면 **오더가 만들어지는 시점에** Cin7 이 자동으로 조립 문서를 만들어 구성품을 차감한다. **그래서 우리가 번들 구성을 알 필요가 없다** — 조립 문서에 이미 다 들어 있다.

조립일과 출고일은 다르다. 조립은 오더 생성 때, 출고는 배송 때다. 그 사이 **번들이 재고로 존재하는 구간**이 생긴다(실측 0~15일, 대부분 0~3일).

⚠️ **조립은 다른 사건과 성격이 다르다.** 물건이 물리적으로 움직이는 게 아니라 창고 안에서 구성품 여러 개가 완제품 하나로 **재분류**되는 것이다. 잔고 계산에는 문제가 없지만, 실사할 때 장부에는 완제품 1개인데 선반에는 구성품 수십 개가 있어 보인다.

⚠️ **번들이 조립 없이 팔리는 경우도 있다.** 조정으로 재고를 잡아두고 파는 경우다(세 건 확인). 원장은 조정도 판매도 다 기록하므로 놓치지 않는다.

### ⭐ 미달·초과 입고의 실무 흐름 (2026-08-19 Caleb 확인 + 실물 ST-01220)

**원장이 발주·조정 두 소스를 함께 읽어야 하는 이유가 여기 있다.**

Cin7 은 **인보이스 수량과 입고 수량이 정확히 같아야** PO 를 닫을 수 있다. 그런데 실제 입고는
자주 어긋난다. Asung 은 이렇게 처리한다:

1. **WMS 는 실제 받은 수량으로 받는다** — 부족/초과를 `discrepancy` 로 걸러 기록한다.
   ⚠️ **"어차피 조정할 거니 인보이스 수량대로 받자"로 하지 않는 이유**: 그러면 **무엇이 부족했는지
   확인할 수 없다.** 사실을 사실대로 남기는 것이 우선이다.
2. **Cin7 에는 실제 수량을 쓴다** — 초과분은 인보이스 수량으로 클램프(`recv_over` 는 discrepancy 큐).
3. **PO 를 닫기 위해 PO 수량을 인보이스 수량으로 채운다** — 미달분이 남으면 I&R 이 계속 열려
   **PO 관리가 불가능**해지기 때문이다. ⚠️ 이것은 재고를 늘리려는 것이 아니라 **문서를 닫기 위한 형식**이다.
4. **차액을 stock adjustment 로 되돌린다** — 실물 예: `ST-01220`
   (`Reference: Initial Warehousing - Parfums de Coeur, Ltd. (PO-01117)`),
   `CAN01620` 201→177(−24, 미달) · `CAN01547` 503→527(+24, 초과)를 **한 문서에 함께** 담았다.

**⇒ 원장 관점**: 한 번의 입고가 **두 소스에 걸친 사건**을 만든다 — `po_in`(발주) + `adjustment`(조정).
⚠️ **Adjustment 는 증감분이 아니라 조정 후 수량(절대값)** 이므로 앞선 오차를 흡수한다.
그래서 **창고 총량은 자동으로 맞는다.**
⚠️ **그러나 bin 단위는 어긋난 채 남는다** — 조정이 걸린 bin(`E030501`)과 입고 bin(PA 의
`3d3c6295`)이 다를 수 있다. 자리 단위 원장으로 올릴 때 이 차이가 드러난다.

### 재고를 안 움직이는 것 (기록하지 않음)

원가만 바뀌는 사건이 여섯 종류 있다. 발주 원가 변경, 이동 원가 변경(들어오는 쪽·나가는 쪽), 조정 원가 변경, 조립 원가 변경, 판매 원가 변경. **수량이 전부 0이다.**

수량 원장에서는 무시한다. 원가 단계로 가면 그때 처리한다.

### 원장 대상이 아닌 것

- **아직 배송 안 된 판매** — 재고를 안 건드린다. WMS 에 없는 것도 정상이다
- **발주 잔량** — 주문했지만 안 온 물건
- **Production Facility 창고** — 삭제만 안 될 뿐 안 쓰는 창고다. 재고가 0인 것을 전수로 확인했다. ⚠️ 다만 여기 재고가 생기면 **경고**해야 한다
- **묶음 단위 상품** — 자체 재고를 갖지 않는다. 낱개 상품 재고에서 나눠 표시하는 값일 뿐이다. 원장은 낱개 상품만 기록한다

## 2부. 스키마 설계

### 테이블 다섯 개

#### ① 원장 본체

**한 줄이 재고 변동 하나**를 뜻한다. 한 번 쓰면 고치거나 지우지 않는다.

담는 것:

- **언제** — 사건이 일어난 날. 문서의 배송일·출발일·실효일 등을 쓴다. 우리가 처리한 시각이 아니다
- **순서** — 같은 날 같은 상품에 여러 사건이 겹칠 수 있다. 유입인지 유출인지를 값으로 저장해 정렬에 쓴다 (아래 「순서를 어떻게 보장하나」 참조)
- **무엇** — 상품 코드. 묶음 단위가 아니라 낱개 기준
- **어디** — 창고. 그리고 자리(빈)도 함께. 자리는 지금은 안 쓰지만 나중에 필요하다
- **얼마나** — 부호가 붙은 수량. 나가면 음수, 들어오면 양수
- **왜** — 사건 종류 (위 여덟 가지 중 하나)
- **근거** — 문서 종류, 문서 번호, 문서 내부 식별자, 라인 위치
- **금액** — 그 사건의 재고 가치 변동. 계산에는 안 쓰지만 저장한다
- **출처** — Cin7 문서에서 왔는지 WMS 에서 왔는지

**중복 방지**: 문서 종류 + 문서 번호 + 라인 위치 + 사건 종류를 묶어 유일하게 만든다. 같은 문서를 두 번 읽어도 두 번 쌓이지 않는다. 수집 배치가 실패해서 다시 돌려도 안전해야 하기 때문이다.

⚠️⚠️ **라인 위치(line_ref) 규칙 (2026-08-18 승격): 소스마다 그 문서가 제공하는 가장 안정적인
라인 식별자를 쓴다.** ~~"ProductID 로 소스 간 통일"~~ 은 폐기됐다 — 통일보다 정확성이 우선이다.
공통 원인은 하나: 유니크 키에 **날짜(occurred_on)가 없어서**, 같은 상품·같은 자리의 두 사건이
날짜만 다르면 키가 완전히 같아져 **두 번째가 조용히 사라진다.**

| 소스 | line_ref | 근거 |
|---|---|---|
| 판매 | `<fulfilment TaskID>:<ProductID>` | 분할 출하(8/10 5개 · 8/15 3개)가 뭉개진다. TaskID 는 GUID — 배열 인덱스는 void·재정렬에 흔들림([실측] 폴백 0회) |
| 발주 | **`CardID`** (2026-08-18) | PA 는 같은 SKU 를 **빈 단위로 쪼개** 여러 줄로 담고, **같은 빈·같은 SKU 가 날짜만 달라** 두 줄인 사례 실재(PO-00944 KUZ77036: 7/15 894 · 7/16 6). 유일성 실측 ProductID 94/97·109/110 vs CardID 97/97·110/110·62/62. [실측] `.7` 의 8/01 창 dry 에서 `merged_lines: 5` — **가설이 아니라 실제로 뭉개지고 있었다**(`.1` 에서 0) |
| 조정·이동·조립·반품 | `ProductID` | 뭉개짐 사례 미발견 — 나타나면 merged_lines 가 시끄럽게 잡는다(문서 내 합산 경보) |

✅ **[실측 2026-08-18 · 체크리스트 1번 닫힘] `CardID` 는 Convert 를 통과해도 유지된다.**
PO-01117 51줄 전부가 Apply 직후(SR) → Convert 후(PA) → 승인 후까지 동일한 `CardID` 를 유지했다
(`LocationID`·순서까지 동일). Convert 는 **재생성이 아니라 이동**이므로 이중 계상 위험은 없다.
⚠️ 남는 미확인: 수량 **수정** 시의 거동(4부 3번 `ON CONFLICT` 항목과 같은 축).
**이유 없이 ProductID 단독으로 되돌리면 분할 출하·빈 분할이 다시 뭉개진다 — 되돌리려는 사람은
이 문단을 먼저 반박할 것.**

⚠️ **원본 응답을 통째로 한 칸에 함께 저장한다.** 나중에 "이 줄이 왜 이렇게 됐지" 할 때 원본이 없으면 추적이 안 된다. 조사 과정에서 여러 번 겪은 일이다.

#### ② 기초 스냅샷

시작하는 날의 재고를 한 번 찍어 둔다. 약 1만 4천 줄이고 1분이면 받는다.

담는 것: 상품, 창고, 자리, 수량, 평가액, 찍은 시각.

⚠️ 조건이 단순하지 않다. **자리가 지정된 것은 자리별로, 자리 없이 떠 있는 재고는 그것대로** 담아야 한다. 자리 없는 재고가 11건 있는데, 자리 있는 것만 담으면 이 물량이 통째로 빠진다.

#### ③ 현재 잔고

기초 스냅샷에 원장을 더해서 나오는 값이다. **따로 저장하지 않고 필요할 때 계산**하는 것을 기본으로 한다.

⚠️ 다만 원장이 수만 줄을 넘어가면 매번 계산하는 게 느려진다. 그때는 "어느 시점까지 더한 결과"를 중간 저장하는 방식으로 바꾼다. **처음부터 그렇게 만들지는 않는다** — 없어도 되는 복잡도를 미리 넣으면 틀렸을 때 찾기 어려워진다.

#### ④ 대조 결과

매일 우리 원장과 Cin7 재고를 비교한 기록이다.

담는 것: 비교한 날, 상품, 창고, 우리 수량, Cin7 수량, 차이, 그리고 **차이의 분류**.

분류가 이 테이블의 핵심이다. 차이가 나는 이유는 셋 중 하나다 — 우리가 놓친 사건, 우리 계산 오류, 설명되는 정상 차이(운송 중이라든지). **설명되는 것을 자동으로 걸러내야** 사람이 봐야 할 것만 남는다.

#### ⑤ 수집 상태

어느 문서 목록을 어디까지 읽었는지 기록한다.

판매와 발주는 "언제 이후 갱신된 것"으로 증분 조회가 되는데, 조정·이동·조립은 그게 안 돼서 **매번 전량을 받아 우리 쪽에서 날짜로 걸러야** 한다. 어디까지 처리했는지 알아야 중복 없이 이어갈 수 있다.

**커서는 두 축이다 (2026-08-17 구현 확정)**:
- **문서번호 커서** (조정·이동·조립 — 전량 축): 비종결 문서(운송 중·미승인) 앞에서 멈춘다 —
  도착 후 회차가 나머지 두 줄을 만들려면 재방문이 필요해서다. 시야 하한(`from_cursor`)이
  스냅샷 이전 문서를 제외한다([실사고] 날짜 없는 초기 트랜스퍼 40건이 상세 캡을 정확히 소진해
  뒤 3,000건이 안 보였다 — 하한은 옛 데이터를 안 보는 것이지 이상 감지를 끄는 것이 아니다).
- **날짜 커서** (판매·발주·반품 — 증분 축): `UpdatedSince = 커서 − 1일`(겹치게 받는다 — 경계
  유실 방지, 중복은 유니크 키가 흡수). 문서 상태로 멈추지 않는다 — 미완료 문서는 갱신되면
  다시 잡힌다. ⚠️ 캡에 걸린 회차만 커서 = **마지막 처리 문서의 갱신 시각**(후보를 갱신 시각
  오름차순으로 처리하는 것이 전제) — 회차 시작 시각으로 옮기면 캡 밖 후보가 영영 유실된다
  (판매는 하루 40~90 오더라 캡 초과가 일상). ⚠️ 커서는 시각 전체 정밀도로 저장하고 **거르기도
  우리 쪽에서 전체 정밀도로** 한다 — 날짜로 절단해 다시 요청만 하면 매 회차 같은 앞 40건만
  반복 처리하는 **완전히 조용한 정체**가 된다(삽입 0행 · 정상 응답 · 커서 동일값 갱신).
  갱신 시각 없는 문서가 캡을 채우면 커서가 동결되므로 그 회차는 쓰기를 차단한다.

### 날짜 커서 축과 이벤트 날짜는 분리돼 있다 (2026-08-17 실측 확정 — 스냅샷 경계와 직결)

`UpdatedSince` 는 **어떤 문서를 가져올까**의 축이고, 원장 행의 날짜는 **이벤트 날짜**(입고 라인
날짜 · 크레딧 노트 날짜 · 배송일)다. 8월에 갱신된 문서가 4월·6월 이벤트를 품고 있으면 **과거
날짜의 원장 행이 생긴다.**

[실측 2026-08-17 dry]

| 소스 | 커서 시작점 | 원장 행 날짜 분포 |
|---|---|---|
| 발주 | 2026-08-01 | 06-18 ~ 08-13 (6·7월이 대부분) |
| 반품 | 2026-07-01 | **2026-04-27 포함** |
| 판매 | 2026-08-14 | **90% 이상이 7월** · 08-14 이후 0 |

⚠️⚠️ **기초 스냅샷과 정면으로 부딪힌다.** 스냅샷은 그 시점 잔고를 담고 과거 이벤트는 이미 그
안에 녹아 있다 — 수집이 또 더하면 **원장이 조용히 부푼다.** 방어는 이벤트 날짜 필터(`since=`)다.
[실측 검증] 반품에 `since=2026-08-01` 을 걸자 원장 행 0 · 걸러진 행 15 · 날짜 분포 빈 것 =
정확히 상보적. ⇒ **쓰기를 켤 때(cron 등록) `since=<스냅샷 날짜>` 는 선택이 아니라 필수다.**

⚠️ **이름 혼동 위험**: `since` = 이벤트 날짜 필터(스냅샷 경계 방어 — 영구 필요) /
`from_since` = 갱신 커서의 시작점(저장된 커서가 없을 때만 쓰는 씨앗). cron URL 에서 하나를
빠뜨리거나 바꿔 쓰면 조용히 잘못 돈다.

### 운송 중 물량을 어떻게 다루나

창고 이동은 출발할 때 빠지고 도착할 때 들어온다. 그 사이는 어느 창고에도 없다.

**"운송 중"을 창고처럼 하나 더 둔다.** 출발 줄은 원래 창고에서 빼서 운송 중으로 넣고, 도착 줄은 운송 중에서 빼서 도착 창고로 넣는다. 그러면 전체 합이 항상 맞고, 지금 떠 있는 물량이 얼마인지도 바로 보인다.

⚠️ 이러면 이동 하나가 원장 **네 줄**이 된다. 대신 총 재고가 사라지는 구간이 없어진다.

### 순서를 어떻게 보장하나

같은 날 같은 상품이 여러 번 조정된 사례가 있었다. 하루에 1개에서 82개로, 다시 161개로 바뀌었다.

날짜만으로는 순서를 못 정한다. **문서 번호로도 안 된다** — 문서 종류마다 접두어가 달라서 판매 번호와 조정 번호를 나란히 비교하는 것은 의미가 없다.

⚠️ 실제로 겪었다. 같은 날 조정으로 3개가 들어오고 1개가 팔린 사례에서, 문서 번호로 정렬하니 판매가 먼저 와서 잔고가 잠깐 음수가 됐다. 실제로는 조정이 먼저였다.

**규칙: 같은 날짜면 들어오는 것(+)을 먼저, 나가는 것(−)을 나중에 계산한다.** 재고가 없으면 팔 수 없으니 물리적으로도 그게 맞다. 이 값을 따로 저장해 정렬에 쓴다.

## 3부. 만드는 순서

### 1단계 — 원장 쌓기

기초 스냅샷을 찍고, 매일 문서 목록을 받아 원장에 쌓는다. **어디에도 쓰지 않는다.** 화면에 안 보여주고 판단에도 안 쓴다.

이 단계의 목표는 "수집이 빠짐없이 되는가" 하나다.

**쓰기 게이트 (2026-08-17 구현 확정)** — 소스별 all-or-nothing. 다섯 중 하나라도 걸리면
**그 소스는 한 행도 쓰지 않고 커서도 안 옮긴다**:

1. 목록 불완전 (429 · 수신 부족 · 페이지 오류)
2. 창고 맵에 없는 위치(UNMAPPED) 1건 이상 — 원장에 들어가면 영구히 남는다
3. 빈 상품 코드 라인 1건 이상 — 파싱이 틀렸다는 뜻이라 나머지 행도 못 믿는다
4. 날짜 결손
5. 캡 회차인데 처리 문서에 갱신 시각이 없음 — 커서가 동결된다

⚠️ **상세 캡에 걸린 것 자체는 쓰기 허용** — 커서가 캡 앞에서 멈춰 다음 회차가 이어받는다.

### 2단계 — 대조

매일 우리 원장과 Cin7 재고를 비교한다. 차이가 나면 왜 나는지 분류한다.

**이 단계가 가장 오래 걸린다.** 처음에는 차이가 많이 날 것이고, 하나씩 원인을 찾아 수집 로직을 고쳐야 한다.

**차이가 0이 되고 그 상태가 한 달 유지되면** 신뢰할 만하다고 본다.

⚠️ **WMS discrepancy 큐는 최종 진실이 아니다 (2026-08-19).** 작업자 보고와 매니저 실사가 다를 수 있고,
Cin7 조정은 **매니저 실사 기준**으로 이뤄진다. [실물] PO-01117 `CAN01547` — WMS apply_note 는
초과 16 을 클램프했다고 기록했으나, 매니저 실사는 24 였고 `ST-01220` 도 +24 로 조정됐다.
⇒ 대조에서 **「WMS 수량 ≠ 원장 수량」** 이 나와도 오류가 아니다. **구조적 차이**로 분류한다 —
두 시스템이 **다른 시점의 사실**을 기록하는 것이지 어느 쪽이 틀린 게 아니다.
📌 최종 재고의 기준은 **매니저 실사가 반영된 Cin7** 이고, 원장은 그것을 읽으므로 원장이 맞다.

- **회계 분개(/transactions)를 탐지 축에서 배제한 정량 근거** — 최근 60일 트랜스퍼:
  창고내 분개 있음 123 / 없음 1,882(94% 미포착) · 창고간 23 / 4. 빈 이동은 금액 변동이 없어
  분개가 안 생긴다. **다시 시도하지 않도록 이 숫자를 남긴다.**
- **Movements 검산 (SKU 단위 유일한 검산 축)** — 누적 = 현재 OnHand 3건 전수 일치:

   미리 묶는 것이 유일한 예방책이고, `1,200ms × 40 = 48초 < 60초 창`이다.
   ⚠️ 캡을 올리려면 **간격도 함께** 봐야 한다 — 캡 55 × 1,200ms = 66초로 창을 넘는다.
   ⚠️ **재시도 백오프를 고쳐야 한다** — 현재 1.5s→3s(최대 4.5초)는 실측 회복 31초의 1/7 이라
   사실상 재시도가 아니다. **`Retry-After` 를 읽어 그만큼 대기**(없으면 60초)로 바꾼다.
   ⚠️ **같은 키를 쓰는 주체끼리는 한도를 공유한다.** WMS 키를 `hello`(5분 폴링)·`receiving`·
   `inv-collect` 가 함께 쓰는지 **코드 확인이 남았다.** 공유라면 ⑤에서 pg_cron 시각을 폴링과
   어긋나게 잡는 것이 첫 수단이다.
   ⚠️ 위 간격·백오프는 **아직 문서 결정일 뿐 코드는 옛 값**(`_shared/cin7.ts`·`inv-collect` —
   ⑤ 작업 항목). 수동 dry 는 소스 하나씩 · 사이 90초. 판매 후보 932÷40 = 24회차 문제는 그 다음.
   **선택지: `inv-collect` 전용 애플리케이션 키 발급.** 한도가 키 단위이므로 원장 수집이 60콜을
   통째로 쓸 수 있고, `hello` 폴링·`receiving` Apply 와 완전히 분리된다. 캡을 올릴 여지도 커진다.
   ⚠️ **Cin7 약관상 허용 여부 미확인** — 계정당 제한의 취지를 키 발급으로 넓히는 셈이라,
   기술적으로 되는 것과 해도 되는 것은 다르다. 필요해지면 Cin7 지원팀에 문의할 것.
   ⚠️ 키가 늘면 교체·분실 관리 지점도 는다(2026-08-18 시크릿 노출·교체 경험 — 아래 4번).
   📌 **지금 당장은 불필요하다** — 1,200ms × 40콜 = 48초로 60초 창 안이고, 폴링이 회차당 2~3콜을
   쓰는 것을 감안해도 여유가 있다. **캡을 크게 올리고 싶어질 때의 카드**로 남긴다.
   ⚠️ **[실측 2026-08-19] 판매는 하루치 창(`from_since=2026-08-18`)에서 후보 145 — 캡 40의 3.6배다**
   (발주 1.5~1.8배보다 심하다). pg_cron 회차마다 40건씩 처리하면 **하루치를 따라잡는 데 4회차**가
   필요하다. 커서가 이어받으므로 유실은 없으나 **실시간성이 떨어진다** — 매일 shadow 대조를 돌릴 때
   전날 판매가 아직 안 들어와 있을 수 있다.
   ⇒ ⚠️ **해결은 캡 상향이 아니다.** `1,200ms × 40 = 48초`로 이미 60초 창의 80%를 쓴다 —
   캡 55면 66초로 창을 넘는다. **회차 주기를 짧게 가져가는 쪽**이 답이고, 소스별로 캡·주기를
   다르게 두는 안을 ⑤에서 정한다(판매·발주는 자주, 반품은 드물게 — [실측] 반품은 하루 4건).
2. **`since`(이벤트 날짜 필터)의 영속화** — 커서 시작점은 저장된 커서로 자동 영속되지만
   `since` 는 그런 경로가 없어 매번 파라미터다. cron URL 에 박으면 스냅샷 재촬영 때 cron 을
   손으로 고쳐야 한다 → `inv_sync_state` 에 담는 안 검토. ⚠️ 위 「날짜 커서 축」 절의
   `since`/`from_since` 이름 혼동 주의.
3. ⚠️ **문서 수정 시 중복 무시(DO NOTHING)가 수정을 버린다** — 증분 축 3종은 수정되는
   문서들이다. 갱신 축이 수정된 문서를 다시 물어와도 유니크 키 충돌로 조용히 버려져 **옛
   수량이 원장에 남고 대조에서 "설명 불가 차이"로만 나타난다.** 유니크 키는 재실행 멱등성용
   설계지 수정 반영을 고려하지 않았다. 정석 = 충돌인데 값이 다른 행 감지 → 시끄럽게 알림 →
   역분개 + 재기표.
   [2026-08-18 확인] **PO 번호는 수정으로 바뀌지 않는다.** 따라서 「수정 = 새 번호 = 새 키」
   기대는 성립하지 않고 **이 항목은 소멸하지 않는다.** 수정 유형별로 증상이 갈린다 —
   ① **수량 정정**(같은 빈·같은 CardID): 키가 동일 → DO NOTHING → 옛 수량이 남고 차이가
     조용히 묻힌다
   ② **빈 변경**: 빈이 키에 있어 충돌 없이 **두 벌**
   ③ **블록 VOID 후 재입력**: 새 CardID 로 **두 벌**(원장은 append-only 라 옛 행이 안
     지워진다 — 역분개 필요)
   ⚠️ 셋 다 감지 장치가 없고 대조 단계의 숫자 차이로만 드러난다. ⑤ 전에 최소한
   **「충돌인데 값이 다른 행」 감지·경고**가 필요하고, 실무 빈도에 따라 역분개 설계까지
   갈 수 있다. **쓰기를 처음 켜기 전에 결론이 나 있어야 한다.**
   📌 ~~실무 빈도 확인 대기(Caleb)~~ → **[실측 2026-08-19] 시나리오 ①(수량 정정)이 실재하며,
   예외가 아니라 정규 절차다.** PO-01117 의 PA 라인 `CAN01620` 이 **168 → 192** 로 바뀌었다 —
   **`CardID`·bin·문서번호 전부 동일**, 수량만 다르다(위 1부 「미달·초과 입고의 실무 흐름」
   3단계 = PO 를 닫기 위한 채움). `DO NOTHING` 이면 192 는 조용히 버려진다.
   ⚠️ **다만 긴급도는 낮아진다** — adjustment 가 절대값이라 뒤이어 오는 조정이 총량을 확정한다.
   168 이 남아도 `adjustment 177` 을 만나면 잔고는 177 이 된다.
   ⇒ **총량 정확도**: adjustment 가 흡수 · **bin 단위 정확도**: 어긋난 채 남음 · **구간 오차**:
   PO 채움과 adjustment 사이 구간은 틀리다(대조에서 **타이밍 차이**로 잡힌다).
   ⇒ **⑤ 전에는 「키는 같은데 값이 다른 행」 감지·경고만으로 충분하다.** 없으면 **bin 이 언제부터
   어긋났는지조차 알 수 없다.** 역분개(−168, +192) 설계는 자리 단위 원장으로 올릴 때로 미룬다.
   (②·③의 빈도는 여전히 미확인 — 빈 재배치는 별도 트랜스퍼 문서라는 실측이 있어(스킬 15건)
   **②는 안 일어날 가능성이 크다.**)
4. **수집 시크릿 교체** — 대화에 노출됨. 교체 시 cron 등록분과 검증 커맨드 동시 갱신.
   ✅ **`WMS_CRON_SECRET` 교체 완료 (2026-08-18)** — `cron.job` 4·5(`wms-image-sync`,
   `-retry`) 헤더도 함께 갱신했다고 기록돼 있다(`2026-08-18-purchase-putaway-axis.md` §7).
   ⚠️ **그러나 갱신이 실제로 먹었는지는 실행으로 확인되지 않았다 — 다음 실행 확인 필요.**
   실행 시각 **매일 08:30 · 09:30(토론토)** = `product-images` EF. 헤더가 옛 값이면
   **401 로 조용히 죽는다**(호출자가 사람이 아니라 cron 이라 아무도 모른다).
   확인: `cron.job_run_details` 에서 해당 jobid 의 최근 실행 `status`·`return_message`.
   실패 시 처방: `cron.job` 의 command 안 헤더 값을 새 시크릿으로 갱신.
   ⚠️ Supabase Secrets 는 저장값을 다시 보여주지 않으므로(digest 만) **값을 잃었으면 재교체가
   유일한 길.** 📌 jobid 1(폴링)은 이 시크릿을 쓰지 않아 무관 — 폴링이 도는 것을 근거로
   "cron 은 정상" 이라고 판단하지 말 것.

### 검토 중 — Advanced PO 기본값 (2026-08-18 · 두 번 논의하고 조사 직전 중단)

Cin7 설정 `Default load advance purchase order` 를 켜는 안. **판정은 아직 안 났다.**

**동기**: Simple PO 는 인보이스 수량과 입고 수량이 다르면 승인이 거부된다(`cin7-api` 스킬 14번
Simple 제약 절). 해소하려면 **사람이 매번 Cin7 에서 `Convert`** 를 눌러야 한다. 처음부터
Advanced 면 이 수작업이 사라진다.

**원장 쪽 이득**: `Type` 전환이 없어지므로 **모든 PO 가 두 번 `UpdatedSince` 에 잡히는 현상이
줄고**, `ON CONFLICT DO NOTHING` 위험(위 3번)의 한 축이 사라진다. 캡 압박(위 1번 — 후보가
캡의 1.5~1.8배인 원인이 전환에 따른 재등장)도 함께 완화된다.

**확인된 것 (2026-08-18 — 코드 실물 확인)**:
- ✅ WMS 의 Advanced 쓰기 경로는 이미 완비돼 있다 — stage1(`/advanced-purchase/stock` DRAFT →
  되읽기 → authorize) · stage2(`/advanced-purchase/put-away` **단일 AUTHORISED POST** 로 전 bin
  배치 후 `LocationID` 되읽기 검증). 그 앞에 **전 bin GUID 해석 pre-flight 하드 게이트**가 있어
  하나라도 못 풀면 불가역 지점 전에 전량 중단한다. **bin 이 빠질 걱정은 코드상 없다.**
- ✅ I&R 그룹 타깃 강제 · 외부 그룹 라인 감지 시 중단 — PO-01094 실사고 재발 봉쇄됨.
- ⚠️ **그러나 Advanced 는 「승인된 인보이스가 정확히 1개」가 아니면 Apply 자체가 중단된다**
  (`advInvoiceTargets` = `Status ∈ {AUTHORISED, PAID}` **이면서** `TaskID` 보유 → **0개 = throw ·
  2개+ = throw**, 다중 인보이스 부분 출하 미지원). Simple 은 Invoice First 게이트만 통과하면
  되므로 **Advanced 가 더 엄격하다.**
- ⚠️ **인보이스가 둘 이상인 PO 가 실재한다** — PO-00703(`InvoiceNumber: "5520110085, 5520110086"`).
  ⚠️ 단 이것은 대화 중 관찰이고 프로브 산출물로 기록돼 있지 않다 — 아래 조사에서 재확인된다.

**미확인 (다음 작업)**: **분할 인보이스 PO 의 비율.** GAS 로 최근 PO 들의 `Invoice` 블록 중
`Status ∈ {AUTHORISED, PAID}` 이면서 `TaskID` 를 가진 것의 개수를 세면 된다(**Advanced 게이트와
정확히 같은 조건** — 위 `advInvoiceTargets` 를 그대로 옮긴 것이라 조사 결과가 곧 Apply 가능
여부다). 판정 기준: **0~2% → 켜도 됨 · 3~10% → 예외 처리 설계 선행 · 10%+ → 켜면 안 됨**
(Convert 수작업보다 Apply 불가가 훨씬 나쁘다).

⚠️ **설정을 켜면 모든 PO 가 한꺼번에 그 경로로 간다.** 되돌릴 수는 있으나 그사이 잘못 들어간
입고는 손으로 정리해야 한다. **켜기 전에 Advanced PO 1건으로 실물 Apply 검증**을 거칠 것.

### 알고 시작하는 위험

**원가 0 재고** — 조정으로 재고를 새로 잡을 때 단가 0으로 들어오는 경우가 있다. 원가 단계에서 공짜 재고가 쌓인다. Cin7 쪽에서도 고치는 방법이 확립돼 있지 않다.

**원본 데이터 오류** — 상품 코드와 실제 포장 단위가 다른 사례를 발견했다. 원장은 이걸 그대로 물려받는다. 원장이 틀린 게 아니라 원본이 틀린 것인데, 나중에 구별하기 어렵다.

**부분 선적 시 과다 차감 가능** — 판매 수량은 Pick 기준인데 배송 문서에 수량 필드가 없어
선택의 여지가 없었다(1부 판매 출고 절). 부분 선적이 실재해도 API 로는 탐지 불가 —
Movements 대조가 유일한 발견 경로다. 감수하는 구조적 한계.

**전체 합계를 확인할 방법** — 상품 하나씩은 Cin7 의 이동 이력으로 검산이 된다(세 건 전수 일치 확인). 그런데 창고 전체 합계를 확인할 API 경로가 없다. 화면 리포트를 사람이 보고 대조하는 수밖에 없다.

**사람이 손으로 하는 단계** — 매니저가 오더를 WMS 로 넘기는 작업이 수동이다. 재고 움직임과는 무관하지만, 대조할 때 "왜 이건 WMS 에 없지"를 매번 설명해야 한다.
