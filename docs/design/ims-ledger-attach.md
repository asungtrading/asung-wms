# IMS 에 원장을 붙일 때 — 할 일과 뒤따라야 할 검증 (2026-09-19)

⚠️ **이 문서는 원장 축에서 본 것이다.** WMS·PO+원가 쪽에 이미 설계된 것이 있을 수
있으니, §1-3(할당) 과 §2-1(음수 게이트)은 **착수 전에 그쪽에 확인할 것.**

---

# 0. 지금 원장의 상태 — 무엇이 증명됐고 무엇이 안 됐나

## 0-1. ⭐ 증명된 것 — 한 달 실측(2026-08-20 ~ 09-19)

**어긋남 8건이 나왔고 전부 원인이 규명됐다. 「모르겠다」로 남은 것이 없다.**

| 원인 층 | 건수 | 예 |
|---|---|---|
| Cin7 쪽 변경 | 4 | 수량 수정(`ST-01306`) · 자리 변경(`TR-04729`) · Deprecated(`ANN07490`) · Ship undone(`SO-16531`) |
| 수집 층 | 2 | 홀드+캡 교착(`ST-01300`) · bin 해석 실패(`TR-04730`) |
| 기초 경계 | 2 | `SO-14986` · `PRO00124`(재기준선이 지운다) |
| ⭐ **원장 계산 오류** | **0** | — |

⇒ ⭐ **「받은 사건으로 잔고를 계산하는」 일에서 틀린 적이 없다.** 이벤트 규칙 ·
상쇄 관례 · 키 설계 · 음수 처리가 전부 정확했다.

⇒ ⚠️ **그래서 「30일 어긋남 0건」은 이 시스템에 맞지 않는 기준이다.**
업무 관행이 바뀌지 않는 한 어긋남은 계속 나온다(손님 취소 · 자리 변경 · DRAFT 방치).
⭐ **대체 기준은 「틀린 적이 없다」가 아니라 「틀렸을 때 왜인지 안다」**이고,
그것은 한 달간 실증됐다.

## 0-2. ⚠️ 증명되지 않은 것 — 지금 원장은 「장부」이지 「시스템」이 아니다

지금 원장이 하는 일은 **Cin7 이 이미 결정한 결과를 받아 쌓는 것**이다.
독자 운영에 필요한 층은 **아직 없고, 없어서 에러도 안 났다.**

| | 지금 | 독자 운영에 필요한 것 |
|---|---|---|
| 사건을 만드는 주체 | Cin7 | ⚠️ **IMS 가 만들어야 한다** |
| 수량 결정 | Cin7 이 계산해서 줌 | ⚠️ 원장이 직접 계산 |
| 가용 재고 | Cin7 의 `Available` | ⚠️⚠️ **개념 자체가 없다** |
| 할당(Allocated) | Cin7 | ⚠️⚠️ **없다** |
| 음수 방지 | Cin7 이 막아줌 | ⚠️ 원장은 **설계상 음수를 허용**한다 |
| 되돌리기 | 사람이 SQL 로 상쇄 | ⚠️ 화면에서 해야 한다 |

⇒ ⭐ **둘로 나뉜다:**
- **설계가 없어서 못 붙이는 것** — 가용 재고 · 할당 · 음수 게이트
- **붙여봐야 아는 것** — 동시성 · 성능 · 되돌리기 흐름

⚠️ **앞의 것이 먼저다.** 설계 없이 붙이면 「붙여봤는데 안 되더라」가 아니라
**「붙일 것이 없다」**가 된다.

# 1. 붙이기 전에 정해야 할 것 (설계 판단)

## 1-1. ⭐⭐ 잔고의 세 층을 나눈다

원장은 지금 **한 가지 수량**만 안다 — 「사건을 쌓은 결과」다.
운영에는 **셋**이 필요하다:

| 층 | 뜻 | 지금 원장에 |
|---|---|---|
| **실물(On hand)** | 창고에 실제로 있는 것 | ⭐ **있다** (`inv_balance.qty`) |
| **할당(Allocated)** | 오더에 묶여 있지만 아직 안 나간 것 | ⚠️ **없다** |
| **가용(Available)** | 실물 − 할당 = 새 오더에 쓸 수 있는 것 | ⚠️ **없다** |

⇒ ⚠️ **원장은 Ship 시점에 차감한다**(스킬 §확정 사실). 픽·팩 단계는 Cin7 에서
`Allocated` 였고 원장은 그것을 몰랐다. ⇒ IMS 에서는 **그 구간을 누가 들고 있을지**
정해야 한다.

⬜ **판단할 것:**
1. 할당을 **원장 사건으로 쌓을 것인가**(`allocate` / `deallocate` event_type 신설),
   아니면 **별도 표**로 둘 것인가
   - ⚠️ 원장에 넣으면 「원장 = 실물 이력」이라는 성질이 흐려진다
   - ⚠️ 별도 표로 두면 「원장만 보면 된다」가 깨진다
   - 📌 WMS 가 이미 픽·팩 상태를 들고 있으므로 **그쪽과 겹치는지 먼저 확인**
2. 할당이 **bin 단위인가 창고 단위인가**
   - ⚠️ 픽은 bin 에서 하지만, 오더 할당 시점에는 bin 이 안 정해질 수 있다

## 1-2. ⚠️ 미확정 문서를 어디에 둘 것인가

Cin7 의 DRAFT·ORDERED 가 커서를 붙잡아 사고를 두 번 냈다(§0-1 수집 층 2건).
⭐ **IMS 에서는 커서가 없으니 그 사고는 사라진다.** 그러나 **미확정 문서 자체는 남는다.**

⬜ **판단할 것:**
- 미확정 문서를 **원장에 넣지 않는다**는 것은 명확하다(확정 전 수량이 잔고에 반영되면
  안 된다). ⇒ **어디에 두는가**
- ⚠️ **방치 감시** — `ST-01300` 은 9/3 작성 후 **13일간 아무도 몰랐다.**
  IMS 에서는 막히는 게 없으니 **더 조용해진다.** 「미확정이 N일 이상」을 보이게 할 것
  📌 다만 ⚠️ **이건 업무 관행 문제이지 시스템 결함이 아니다.** 알림은 돕는 것이지
  책임지는 것이 아니다

## 1-3. ⭐ 반품 리스탁 bin (이미 확정된 요구사항)

> **반품 리스탁은 「판매 시점의 bin」이 아니라 「그 SKU 가 현재 있는 bin」으로
> 들어간다.** 원래 자리에 재고가 남아 있으면 거기로, 옮겨졌으면 **옮겨진 자리로.**

📌 근거: [실측 `ABE52708` 09-14] Cin7 은 판매 시점 bin 으로 되돌려서, 이미 비워진
`E020202` 에 4개가 복귀해 **재고가 두 칸으로 갈라졌다**(`E020202` 4 / `E020302` 201).
⚠️ 그 결과 「12개를 어디서 뽑았나」를 규명하는 데 한참 걸렸고, **피커가 헷갈린다.**

⇒ 정본: `docs/design/ledger-design.md` §「⬜ IMS 설계 요구사항(미구현)」

# 2. 붙일 때 만들어야 할 것

## 2-1. ⚠️⚠️ 음수 게이트는 원장이 아니라 그 위층이다

원장은 **설계상 음수를 허용한다** — 사건을 쌓는 장부이므로 맞다
(⚠️ `inv_layer` 는 반대로 `qty > 0` CHECK 가 있다).

⇒ ⭐ **「재고가 없는데 출고를 만들려 할 때 막는 것」은 원장의 일이 아니다.**
사건을 **허용할지 판단하는 층**이 원장 위에 있어야 하고, 그 층이 지금 없다.

⬜ **판단할 것:**
- 막을 것인가 경고만 할 것인가 — ⚠️ 실무에서 「재고가 0인데 실물은 있다」가 흔하다
  (`ANN07490` 이 그 예). 무조건 막으면 업무가 멈춘다
- **가용 기준인가 실물 기준인가** — §1-1 의 세 층 중 무엇으로 판정할지

## 2-2. 사건을 만드는 경로

지금 원장에 들어오는 `event_type` 전수(⭐ **IMS 가 전부 만들 수 있어야 한다**):

| event_type | 뜻 | IMS 에서 만드는 곳 |
|---|---|---|
| `sale_out` | 출고 | SO 모듈 |
| `po_in` | 입고 | PO 모듈(진행 중) |
| `transfer_out` / `transfer_in` | 창고 간 이동(4-leg · IN_TRANSIT 경유) | ⬜ |
| `adjust_new` / `adjust_existing` | 재고 조정 | ⬜ 조정 도구 |
| `assemble_in` / `assemble_out` | 조립 | ⬜ |
| `credit_in` | 반품 입고 | ⬜ |
| `manual_reversal` | 정정(다른 키로 재기표한 것 무효화) | ⭐ 아래 §2-3 |

⚠️ **조립은 소진과 유입이 한 문서에 함께 들어온다** — `net` 으로 검산하면 안 된다
(`FG-00130`: −24 투입 + 1 완성 = −23).
⚠️ **트랜스퍼는 4-leg** — 출발 창고 → IN_TRANSIT → 도착 창고. `warehouse` 를 키에서
빼면 이동 자체가 사라진다.

## 2-3. ⭐ 정정을 화면에서 할 수 있게 한다

지금은 사람이 SQL 로 상쇄한다. IMS 에서는 실무자가 화면에서 해야 한다.
⚠️ **기존 관례를 그대로 쓸 것**(한 달간 다듬어진 것이다):

| 상황 | 방식 | 접미어 |
|---|---|---|
| 같은 사건을 **다른 키로 재기표**해 옛 벌 무효화 | `event_type='manual_reversal'` | **없음**(타입이 구분) |
| 사건 자체를 **취소·정정** | **원래 타입 유지** · 부호 반전 | **`:reversal`** |
| Cin7 이 수량을 고쳐 **차액만** 보정 | 원래 타입 유지 · **차액만** | **`:qtyfix`** |
| bin 해석 실패로 빈 bin 행이 생긴 것 | `manual_reversal` | **`:binfix`** |

⚠️⚠️ **물리 삭제 금지.** append-only 의 첫 위반이 「사소한 1건」인 것이 가장 위험하다.

# 3. 붙인 뒤 반드시 해야 할 검증

⚠️ **순서가 중요하다.** ①②는 붙이자마자, ③④는 실물 부하가 있어야, ⑤는 상시다.

## 3-1. ⭐⭐ ① 재생성 일치 — 가장 먼저

> **원장을 처음부터 다시 계산해도 같은 잔고가 나오는가.**

```sql
-- 기준: inv_balance = baseline(inv_snapshot) + delta(inv_ledger)
-- ⚠️ source 로 필터하지 말 것 — manual 상쇄가 사라진다
select b.sku, b.warehouse, b.bin, b.qty as view_qty, r.qty as recomputed
from inv_balance b
join ( /* 독립적으로 재계산한 결과 */ ) r using (sku, warehouse, bin)
where b.qty is distinct from r.qty;
```
⭐ **0행이어야 한다.** ⚠️ 이건 `inv_layer` 의 「완전 재생성 가능」 불변 조건과 같은
성질이고, 이미 그쪽에서 검증 경로가 있다 — **재사용할 것.**

## 3-2. ⭐ ② 이중 기록 방지 — 같은 사건을 두 번 저장해본다

⚠️ **한 달간 어긋남 8건 중 3건이 「같은 사건이 두 번 들어온 것」이었다.**
IMS 에서는 폴링이 없어 재수집은 사라지지만, **사용자가 두 번 누르는 것**은 남는다.

**시험할 것:**
1. 같은 출고를 **두 번 확정**해본다 ⇒ ⭐ 두 번째가 거부되거나 무시돼야 한다
2. 같은 라인을 **다른 bin 으로** 두 번 확정해본다
   ⇒ ⚠️⚠️ **유니크 키에 `bin` 이 있어 지금은 두 행이 공존한다.**
   `TR-04729`(자리 변경) · `TR-04730`(bin 해석 실패)이 둘 다 이 구조였다
   ⇒ 📌 IMS 는 **「이 `line_ref` 에 이미 행이 있나」를 bin 과 무관하게** 확인해야 한다

⚠️ 키에서 `bin` 을 빼는 것은 **안 된다** — bin 이동을 표현할 수 없게 된다.
⭐ **막는 것은 키가 아니라 쓰기 경로다.**

## 3-3. ③ 동시성 — 실물 부하가 있어야 안다

⚠️ 지금은 수집기 하나가 순서대로 쓴다. IMS 는 여러 사람이 동시에 쓴다.

**시험할 것:**
- 두 사람이 **같은 재고를 동시에 할당**할 때 두 번 쓰이지 않는가
- 두 사람이 **같은 문서를 동시에 확정**할 때 어떻게 되는가
- 📌 WMS 에 「같은 사람 다중 기기」 세션 잠금이 이미 있다(`20260910230704`) —
  ⭐ **그 패턴을 재사용할 수 있는지 확인할 것**

## 3-4. ④ 성능 — 1년치를 가정하고 잰다

⚠️ 지금 잔고는 **사건 전량 합산**이다. 데이터가 쌓이면 실시간 조회에 못 쓴다.

**재야 할 것:**
- 단일 SKU×bin 잔고 조회 응답 시간
- 전 창고 잔고 화면 로딩 시간
- ⚠️ **1년치 사건을 넣고** 다시 잰다(현재 한 달 데이터로 재면 의미가 없다)
- 📌 참고: `inv_layer` 전량 재생성이 지금 7.8초다

⬜ **판단할 것**: 느리면 **스냅샷 주기를 줄일 것인가**(지금 하루 1회),
아니면 **증분 집계 표**를 둘 것인가.

## 3-5. ⑤ 대조는 계속한다 — Cin7 이 남아 있는 동안

⚠️ **병행 기간에는 지금의 아침 점검을 그대로 돌린다.** IMS 가 만든 사건과 Cin7 이
만든 사건이 **같은 원장에 섞이므로**, 어긋남이 나면 **어느 쪽에서 왔는지** 먼저 갈라야
한다.

⇒ ⭐ **`source` 컬럼이 그것을 가른다**(`cin7` / `manual` / ⬜ IMS 용 새 값 필요).
⚠️ 다만 **잔고 계산에서는 절대 필터하지 말 것** — 한 달간 두 번 그 함정에 빠졌다.

# 4. 붙인 뒤 아침 점검에 추가할 항목

기존 15항목(⓪~⑫ · ⑦-b · ⑩-b)에 더해:

| 새 항목 | 보는 것 | 왜 |
|---|---|---|
| **IMS 사건 유입** | IMS 가 만든 사건이 정상 기록되는가(`source` 별 건수 · 시각) | ⚠️ 조용히 안 들어오면 모른다 |
| **가용 = 실물 − 할당** | 세 층이 정합한가 | ⭐ 할당이 새 축이라 새 어긋남이 난다 |
| **미확정 문서 방치** | N일 이상 확정 안 된 조정·오더 | 📌 `ST-01300` 13일 전례 |
| **음수 잔고** | `inv_balance.qty < 0` 인 칸 | ⚠️ 원장은 허용하지만 **실물에는 없다** |

⚠️ **커서 관련 항목(⑤ 3일 규칙 · ⑦ 캡·홀드)은 Cin7 축이 남아 있는 동안만 유효**하다.
마지막 축이 IMS 로 오면 통째로 뺀다.

# 5. ⬜ 열린 항목 (붙이기 전에 정리하면 좋은 것)

1. ⚠️⚠️ **Ship-undone 감시 부재** — `sale` 축은 `DATE_SOURCES`(②-b)로 따로 돌아
   `detectVoided` 가 아예 없고, ⚠️ **있어도 `Status === "VOIDED"` 만 봐서 못 잡는다**
   (`SO-16531` 은 `AUTHORISED` 였다). 신호는 `index.ts:2000` 에 도착해 있는데
   원장과 대조하는 코드가 없다
   ⇒ ⭐ **판매 취소는 가장 빈번한 축이다**(Caleb 확인 · 손님 변심 · 결제 후 픽업 전
   fulfillment 선생성 후 취소). 지금까지 안 보인 것은 **타이밍 운**이다
   ⇒ ⬜ **구현 전에 `CombinedShippingStatus` 어휘 실측 필요**(부분 배송 오탐을 가른다)
   📌 IMS 로 가면 이 축도 사라지지만, **병행 기간에는 필요하다**
2. **`cursor_stalled_alert` 가 13일간 안 울렸다** — 발화 조건 미확인
3. **⑩-b 사각지대** — 빈 bin 쪽 이중을 못 잡는다(`TR-04730`)
4. **`transfer` 경고 4건** — 열흘째 미특정
5. **재기준선** — 잡으면 기초 경계 축(`PRO00124` · `SO-14986` 계열)이 통째로 사라진다.
   ⚠️ 원장이 shadow 를 벗는 시점과 함께 판단할 것
